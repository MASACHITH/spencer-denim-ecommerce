## 2. Decisions worth knowing about

**The dialog exists to settle a variant, and nothing else.** No wishlist heart (the card's is right
beside the trigger and is still browser-local until W2-08), no reviews, no delivery estimate, no
related products, no size guide. All of those are the product page, and a modal that restated the
card would be a second way to read the same four lines.

**The selection is *not* in the URL, which is the opposite of the product page's rule.** It cannot
be: a listing's query string already owns `?colour=` and `?size=` as **filters** (PLP-02), so
writing a colourway *id* into `colour` would re-run the listing against a filter value that is not
a colour-family slug. The selection is local to the dialog, and "View full details" is what makes
it shareable — it carries `?colour=&size=` into the product page, which does own those names.

**The shared `ui/modal` was adopted, not copied.** That component's own `TODO(QV-01)` asked for
exactly this. It already does the focus trap, Escape, the scroll lock, `aria-modal` and returning
focus to the trigger, so none of it was rewritten; the dialog is `@if`-gated in the card, so a
listing of twenty-four cards creates nothing until something is pressed, and the modal's
`DestroyRef` hook is what releases the trap and the scroll lock.

**A successful add closes the dialog.** The mini bag opens itself when `CartStore.lastAdded` moves
(CART-02), so without this there would be two dialogs trapping focus against each other and two
claims on `body.sd-no-scroll`. Measured in a real browser: the dialog goes, the drawer opens, focus
ends up inside the drawer, the page behind stays frozen. A **failed** add keeps the dialog, because
the message and the control that caused it belong on the same screen.

**`CartStore.error` is a root signal, so the dialog gates it.** It holds the last thing that went
wrong anywhere — a failed `GET /api/cart` from the header on page load is enough — so binding it
straight to the template opened a brand-new dialog already showing a red message about something
else. The error line now only appears once *this* dialog has asked the bag for something.

## 3. The spec gap, and how the card's Add to Bag actually works

CARD-01 lists Add to Bag on the card. **`ProductCardDto` carries colours and no variants at all**,
so a card cannot know whether a size has to be chosen — and a card that guessed one would put the
wrong thing in a bag.

So both triggers open the one dialog, and the dialog decides, because it has the variants:

- `intent="view"` — opens and waits.
- `intent="add"` — opens, and if the product has **exactly one buyable variant** it adds it and
  closes itself. Anything else stays open on the size list with the reason showing.

The visible difference between the two triggers is therefore one request long. The alternative is a
`variantCount` on the card projection (`ProductCardDto` + the API's card query), which would let
the card decide without a fetch — **filed, not built**, because the brief said to report a backend
need rather than invent one, and nothing a shopper sees is wrong without it.

Worth knowing for whoever picks that up: **every product the e2e catalogue stub serves has three
sizes**, so the single-variant shortcut is unreachable in `quick-view.e2e.ts` by construction. It is
pinned in `quick-view.spec.ts` instead, and the e2e file says so where it would otherwise look like
a gap.

## 4. A real bug found in the product page, and fixed

`ProductPage.addToBagReason` asked `stock().status === 'OutOfStock'` **before** it asked about the
chosen variant. `stockFor` narrows to the selection, so picking a sold-out size made that true for a
product with plenty of the other sizes — the shopper was told **"This product is out of stock"**,
which is false, and the sentence written for the case ("That size is out of stock. Choose another
size.") was unreachable. No test pinned it.

The two branches are now the other way round in `product-page.ts`, and Quick View was written with
the corrected order from the start. Found only because the dialog was built from the same logic.

## 5. The CSS hoist, and why it is not refactoring for its own sake

`.swatch`, `.swatch__dot` (including the sold-out slash), `.size` and `.qty` moved from
`product-page.ts`'s scoped styles into the storefront stylesheet. The markup in both components is
identical, so the class names are the contract; keeping two copies is how a sold-out swatch ends up
slashed on one screen and plain on the other. It is the same move, for the same stated reason, that
`.price` already made out of the card's own styles.

It also buys back room against the `anyComponentStyle` 4 kB budget, which `product-page.ts` was
already writing comments about.

## 7. Traps, for whoever is next

**`horizontalOverflow` is blind while a dialog is open.** An open modal puts `sd-no-scroll` on the
body, and `overflow: hidden` hides exactly the symptom that helper measures. `quick-view.e2e.ts` has
a `dialogOverflow` that looks where the overflow can actually be — the panel past the viewport edge,
and the panel's own scrolling body — and still reports the document as well. I nearly "verified" a
324 px panel in a 320 px window this way; it turned out the window was 355 px wide, but the
measurement would not have told me either way.

> **Round 2 note on the paragraph above.** Every number `dialogOverflow` reported was *horizontal* —
> and the dialog was hanging 137 px off the **bottom** of a 390 px phone the whole time, with Add to
> Bag unreachable. The helper was built carefully against one axis and was structurally blind to the
> other. Worth remembering as its own lesson: a measurement written to catch one failure is not
> evidence about the failures it was not written to catch, however carefully it was written.

**A backtick inside a CSS comment in a `styles:` template literal breaks the Angular compiler**, and
the error it gives is `Failed to resolve @Component.styles to a string` with no file or line for the
real cause. Cost three builds. Markdown-style backticks are fine in `/** */` docblocks and fatal
inside `styles:` or `template:`.

**A required input cannot be read in a constructor** (NG8118), so the detail fetch is issued from an
`effect` instead of synchronously. Harmless here — the dialog is created by a click, so there is
never a server render to be in flight during — but the product page's "issue it from the
constructor" pattern does not transfer to a component whose input *is* the thing being fetched.

**Hidden is not the same as not laid out.** At ≥1024 px the action pair is `opacity: 0` **and**
`translateY(6px)` until hover, so measuring its geometry un-hovered measures the animation's first
frame and reports it hanging below the photograph. Four of my breakpoint tests failed on exactly
that before they hovered first.

## 8. Round 2 — the tester's FAIL, and what it cost

The independent tester failed this task on **three Majors, all shopper-facing, all on a phone**.

**MAJOR 1 — the panel hung off the bottom of the screen and Add to Bag was unreachable.** Not in
Quick View: one line in the shared `ui/modal`. The host is `display: grid; place-items: center`, and
`place-items` sets `align-items`/`justify-items` and **never `align-content`** — so the single
*implicit* row sized itself to the panel's **unclamped** content height (981 px against an 844 px
viewport at 390 px), and the panel, clamped to `92vh`, was centred inside that oversized row. Half
the overflow went off the bottom. 137 px at 390x844, 223 at 375x667, 127 at 375x844, 91 at 320x844,
and because the thing that overflowed was the *host* rather than the panel's own scrolling body,
scrolling to the end of the panel did not reach the button and neither did keyboard focus. Latent
since PDP-04: the size guide's content never exceeds 92vh, so Quick View is the first panel tall
enough to trigger it. At 1280x900 — which is where every add test in this file ran — nothing is
wrong at all, which is why nobody saw it.

Fixed with `grid-template-rows: minmax(0, 1fr)` on the host. Chosen over `align-content: center`,
which the tester verified works: it leaves the track oversized and merely centres the overflow, so
it fixes this panel and not the next one. `1fr` alone keeps an automatic min-content minimum and
blows the track out again; the zero minimum is the whole of it. It also makes the panel's
`max-height: min(100%, 92vh)` mean what it says, since `100%` now resolves against the room
available rather than against the content's own height. Verified at all eight breakpoints plus
375x667 and 1280x600, and the size guide — which shares the file — still passes 15/15.

**MAJOR 3 — pressing Add to Bag dropped focus to `<body>`.** `[disabled]` on the element that
currently holds focus makes Chromium blur it and fire **no `focusin`**, so `Modal.onFocusIn` never
re-trapped: a **refused** add left the shopper outside a dialog that was still open. A successful
add masks it, because the mini bag takes focus. This is the identical root cause as the ADM-22
settings defect already fixed on `main`, and it took the identical remedy — `aria-disabled` instead
of `disabled`, the element stays focusable, and the handler refuses the activation. The product
page's Add to Bag carried the same bug pre-existing and is fixed in the same commit. `.btn:disabled`
in the shared `base.css` can no longer match either button, so the unavailable *look* moved into the
storefront stylesheet; it belongs beside `.btn:disabled` and is not there yet for the reason
`ui/modal` has not moved either — a shared-library change lands in every open branch at once.

**MAJOR 2 is not fixed, by instruction.** The floating WhatsApp button (`.wa-float`, 56 px, fixed,
bottom-right, site-wide per GLB-08) covers a card's Add to Bag at `scrollY 0` on a 320 px phone —
the first card a shopper sees has a dead button that opens WhatsApp. It is a genuine conflict
between docs/04 §4 decision 5 (icon buttons on the photo) and decision 6 (floating WhatsApp
bottom-right), which nothing in the design system reconciles. **Awaiting an owner decision; nothing
here designs around it.**

Also in round 2: the `addToBagReason` branch reorder — this branch's one real bug fix, §4 — **had no
test at all**, and reverting it left 61/61 product-page tests green; pinned on both sides now.
`dialogOverflow` gained a vertical measurement and a new `unreachable()` companion to `undersized()`
in `support/measure.ts`, because a 48 px button eight pixels below the fold passes a 44 px target
check. `.swatch` and `.size` became `.sd-swatch` and `.sd-size`, since hoisting them had made two of
the most generic names in CSS global. `bag-page.ts` lost its byte-identical copy of the `.qty`
rules. And choosing a sold-out size announced nothing — `quantityNote()` returns `''` for an
`OutOfStock` selection, emptying the only live region on the screen, while the line that did change
was not a live region at all; the reason line is the live region now, and it stays in the DOM,
because a region that appears already holding its text is not a change either.
