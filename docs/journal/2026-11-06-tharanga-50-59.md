## #59 — which writes are audited (survey of `main`, 2026-11-06)

When #59 was filed only sign-in wrote audit rows. Since then almost every admin write enlists one with its change
(issue #59's `IAuditLogWriter.Enlist`): catalogue (departments, categories, products, prices), content (pages,
announcements, home, mega menu, size guides), marketing (promo codes, sale campaigns, newsletter export and
unsubscribe), settings (every panel), payments (bank details, PayPal, provider switch, bank-transfer reviews), orders
(transitions, cancellation, couriers, invoice settings), inventory, reviews, delivery, alerts, staff users and roles,
staff and customer account events. Handlers without audit are reads, starting 2FA setup and sending an SMTP test.

**The one gap #59 named first was still open: the media library.** Fixed here:
- Upload: one `Create` row (`EntityType = MediaAsset`, the asset id, who, file name, public id) enlisted when the asset
  is **published**, in the same save, so the trail says what is in the library, not what was attempted. A lost
  de-duplication race drops the pending row before its stand-down save. Private assets (customer bank slips) are not
  library uploads and are audited where they are reviewed.
- Delete: one `SoftDelete` row in the delete's own transaction. The delete runs inside the execution strategy and saves
  with `acceptAllChangesOnSuccess: false`, so a retried attempt **replaces** the pending row rather than adding one.
- Nothing changed → nothing audited: a duplicate upload (200) and a refused delete (409, in use) write no row.

Roles have no CRUD yet (#105); when it lands it writes `PermissionChange` as doc 11 P14 says.

## #50 — redaction at the writer, not attributes

Doc 08 DB24 describes `[AuditIgnore]` / `[AuditRedact]` attributes for a **generic** entity-change interceptor. This
codebase has none and deliberately writes every row by hand in the use case, so an attribute would protect nothing.
DB24's goal is enforced instead where every row passes: `AuditLogWriter.Enlist` → `AuditRedaction.Apply`.
- Never logged (removed at any depth, any casing): the DB24 columns, the UserTokens contents a hand-written row could
  copy (authenticator key, recovery codes) and any password field. Exact names only — `mustChangePassword` is kept.
- `ProofAssetId` → `"[changed]"`. Settings secrets stay with `SettingsAuditTrail` (only it knows which are secret).
- A clean row is written as the same instance; a dirty one is copied field for field (a test pins that the copy covers
  every settable column of `AuditLog`, so a new column cannot be silently dropped).
- **For the owner:** DB24's wording (attributes + interceptor) no longer describes the mechanism; proposed wording in
  the PR.

## 2026-11-13 — rebased, independent tester, two fixes

Rebased onto `main` 19a931b2 (#276, #253, #254, #248, #262). #254's recovery rows (`mustChangePassword`,
`sessionsEnded`, `lockedOut`, `twoFactorEnabled`, `authenticatorRemoved`) hit no listed name, so they are written whole.

- **Tester round 1: PASS** — 484 targeted integration tests (Media/Audit/Recover/Settings) plus 9 new media audit
  tests: de-dup race lost at the unique index, a publish that fails after enlisting, video + poster, private asset,
  delete retried after a lost acknowledgement and after a commit that really failed. Kept as `MediaAuditTrailTests`.
- **Should-fix, fixed:** a listed name written with a JSON escape (`pass\u0077ord`) in text the parser refuses
  (duplicate keys, which `ISJSON` accepts) passed the plain-text fail-closed check. The fallback now also reads the
  names with `Utf8JsonReader` (accepts duplicates, `GetString` unescapes); text it gives up on inside an object or
  array fails closed if it has any escape. Text that never opens one is still returned as written, so non-JSON keeps
  failing loudly at `ISJSON`.
- The column-copy test now fills every column by reflection and runs `Apply`, instead of comparing a hand-kept list.
- **Tester round 2: PASS** — 35 attacks on the fail-closed path, kept as `AuditRedactionUnreadableTextTests`.
- **Nits left, for later:** an unattached customer bank slip deleted through the admin endpoint writes no audit row;
  a redacted row re-serialises non-ASCII as `\uXXXX` (same value when parsed); `DeleteAsync` parameter order; text
  with duplicate keys and an unlisted name *containing* a listed word (`mustChangePassword`) is over-redacted (safe
  side; nothing writes duplicate keys).
