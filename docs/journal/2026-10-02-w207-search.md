## Decisions

- **No new backend endpoint.** `GET /api/catalog/search` shipped with W1-02 and its relevance score
  (doc 08 §7.6: name prefix 100, name 50, category or colour 20) means six rows of it *are* the
  "TOP 6 by `NameText` prefix or word prefix" that section asks for. Category suggestions need no
  server at all: the department tree is already in hand for the mega menu, the breadcrumb and the
  route guards, so they cost no request and are correct on the keystroke.

- **No migration.** One is pending merge elsewhere and Tharanga may be adding the `sales` one; the
  rule is one at a time.

- **"Popular searches" is not delivered, and is not faked.** Doc 08 §1.7 already names the source —
  "Popular searches come from `analytics.SearchQueriesDaily`" — and §7.6 specifies the query and §3
  the table and its DB25 rules. The **design exists; the table and the recording do not** (no
  `analytics` schema anywhere in `src/backend`), so the follow-up is wiring, not design. The empty
  overlay offers the live catalogue's own entrances under **"Browse the shop"** instead, and two tests
  assert the word "popular" appears nowhere in it. Recorded against ADM-20 as **#78**, which also
  carries the tester's point that the recording half has a 30-day warm-up and must land *early* in
  that milestone or the feature ships empty. SRCH-01 is carried as **partial**.

- **Recent searches live in `localStorage`** (doc 08 §1.7 decided it), read in `afterNextRender` so
  the server never renders a history it cannot have, recorded only for **submitted** searches — the
  same event `SearchQueriesDaily` records — and clearable in one action. No per-entry delete: the
  standard "×" would be a button inside a `role="option"`, which a listbox may not hold, and a second
  tab stop per row.

- **The popup opens from typing, ArrowDown and a click — never from focus**, which is what keeps it
  out of #20's shape. **Escape is `preventDefault()`ed whether the popup is open or not** (see below)
  and `stopPropagation()`ed only when it was open, so one Escape dismisses the suggestions and a
  second reaches `SiteHeader` and closes the panel.

- **The popup is a dropdown at every width, not a full-screen sheet on phones.** The header is 170 px
  tall and sticky at 320 px, so a sheet needs its own scroll lock and focus trap; the list is eight
  rows that scroll inside a capped box. Measured at all eight breakpoints.

- **Arrow keys wrap** at both ends; `Home`/`End` are left to the browser so they still move the caret.

- **The results page is `noindex` with no canonical address, and always 200.** An internal results
  page is unbounded crawl space over products already indexed at their own addresses. It takes neither
  of the two behaviours the listing routes grew in #30: no `canMatch`, so no path to 404 or 503. A
  search with no hits and a term too short are both a 200.

- **`/search` is listed ahead of `:department`.** The guard happens to save it today — `search` is not
  a department slug — so the ordering is only load-bearing for a catalogue that *has* a department
  called "search". The regression test makes the feed claim exactly that, because otherwise the
  ordering would be untested.

- **On a search page the department and category are filters, not the page**, so they travel in the
  query string, get chips, and "Clear filters" takes them off. Removing the department chip removes
  the category with it: a category slug is unique only per department and parent, so "jeans" alone
  names two and the API answers 400 naming it.

## Worth writing down, because it would cost the next person time

- **A unit test cannot see Chrome's native search-field clear, and that is how Major 1 survived.**
  jsdom gives `input[type=search]` no Escape-clear, so a synthetic Escape in a `.spec.ts` proves the
  popup closed and nothing else. The mechanism *is* assertable in jsdom — `event.defaultPrevented` on
  both presses — and the user-visible behaviour needs a real browser. Both now exist. The general
  lesson: when a fix is "prevent the browser's default", the unit test asserts that the default was
  prevented, not the outcome the browser would have produced.

- **An anchored privacy pattern is barely a privacy pattern.** `/^…@…\.…$/` only matched a term that
  *was* an address. Nobody types a bare address into a search box; they type "my email is …". The
  replacement is "any at-sign character, in any of its three spellings" — deliberately blunt, because
  every narrower answer loses to a space (`john ＠ example.com` is an address to a human and not to a
  regular expression), and nothing a shopper searches a clothing shop for contains an at-sign. The
  keep-side is tested as hard as the drop-side so the rule cannot quietly eat the feature.

- **`\d` and `\D` are ASCII-only even under the `u` flag.** A telephone number in Arabic-Indic or
  fullwidth digits counted as **zero** digits. `\p{Nd}` is the fix. This will matter again anywhere a
  digit is counted rather than parsed.

- **This rule is owed to the server.** The same test decides what reaches
  `analytics.SearchQueriesDaily`, which keeps rows for **13 months** — so the anchored version would
  have kept a shopper's email address on the server for over a year rather than only on their own
  device. **#78** carries that obligation.

- **A stub that mirrors one half of an API hides the half you wrote code for.** The first version
  mirrored the `q` rules and nothing else, so it answered 200 to all thirteen query strings
  `ProductListQuery.Create` rejects — which meant `searchFailure`'s `'query'` branch, the one that
  shows the API's own message about an ambiguous category, **could not be reached from a browser at
  all**. `ProductListQuery.Create` and `ResolveFiltersAsync` are mirrored now, and there is a browser
  test that lands on that branch. `productsFor` deliberately still does not use them: three suites
  are written against its current looseness (`E2E_DEPARTMENTS=empty` serves `[]`, so a faithful
  resolver would answer "no such department" to the very tests that check a department renders from the
  storefront's fallback). Narrowing that is its own change with its own regression run.

- **A stub's corpus has to be the same *shape* as the real index, not merely rich.**
  `ProductSearchIndex.SearchText` is name + category **path names** + colour names and families +
  material + fit + occasion + code + SKUs, and `PathNames` walks `ParentCategoryId` only — so it holds
  **no department name and no slugs**. The first corpus joined `departmentName` and `categorySlug` in,
  which made `q=women` match all 120 here and ~0 in production, and made `q=linen` — which the whole
  e2e file used to mean "matches nothing" — match every linen product in production. The meaning of
  those tests inverted on the real API. Materials are in the corpus now, which also makes the
  no-results copy's own promise ("a product name, a category, a colour or a material") reachable.

- **A status-code assertion cannot tell you which page answered.** `/search?q=%ED%A0%BD` is a **200
  rendering the home page**: Angular's `DefaultUrlSerializer` calls `decodeURIComponent`, which throws
  `URIError` on half a surrogate pair, the router logs NG04018 twice and falls through to
  `{path:'**', redirectTo:''}`. My round-1 report said "< 500, so there is no site-wide query-string
  hazard" — wrong, and wrong in the way a status-only assertion makes easy. It is site-wide and
  pre-existing (`/?q=`, `/women?colour=`, `/product/x?y=` all do it) and is filed as **#79**. Every
  hostile-term test now asserts `<sd-search-page` is in the HTML, and the surrogate case is a
  `test.fail()` asserting the behaviour the storefront **must** have — so when #79 lands it reports
  "passed unexpectedly" and the marker comes off, rather than locking the wrong answer in. A genuine
  U+FFFD (`%EF%BF%BD`) renders the search page fine, which is what proves U+FFFD is not what arrives.

- **A `let nextId = 0` at the top of a component file is per-process, not per-request.** On the SSR
  server the ids climbed across renders (`sd-search-76/77/78`, then `79/80/81`) while every browser
  that hydrated one started again at 0. No accessibility defect — the ids are internally consistent
  within each document — but it is per-request state in a long-lived process, and the server's HTML and
  the browser's DOM disagreed about every generated id the instant hydration finished. Fixed with a
  root-provided `UniqueId`, which on the server is a new injector per request. **`listing-filters.ts`
  still has the module-level form (`nextPanelId`)** — same shape, left alone because it is outside this
  diff, and `UniqueId` is where it should move when someone touches that file.

- **"Only one is visible" is a fact about the stylesheet.** `SiteHeader` renders the search box twice
  and the results page a third time, so there are three `role="search"` landmarks in the DOM. Exactly
  one of the header's two is ever visible, so in effect a screen reader never meets a duplicate — but
  that is a media query, not a name. The landmark name is now separate from the field label
  (`landmarkLabel`), the panel instance is "Search products, header panel", and an e2e test asserts
  three landmarks with three distinct non-empty names.

- **A copied test needs its copied budget.** `search-page.spec.ts`'s 480-card ceiling test was copied
  from `listing-page.spec.ts` without its `HEAVY_RENDER_TIMEOUT_MS = 20_000`, and vitest's 5 s default
  ate it on a busy machine (9,426 ms). Worse, `test:ci` chains the three projects with `&&`, so the red
  storefront suite stopped `ng test admin` from running at all. The comment two directories away had
  already explained this; the lesson did not travel with the code.

- **The suggestion list settles in two stages, and a test that reads it between them is racy.**
  Category suggestions come from the cached tree on the keystroke; products arrive from the API a
  debounce later. "An option is visible" is true while the list holds only categories, so three tests
  were reading ids that were about to change underneath them. The `search()` helper waits for a named
  product label instead. Two more tests opened the popup on a page whose box already held a term,
  which asks for suggestions for *that* term and made the request count depend on machine speed; they
  start from `/search` with an empty box now.

- **Two measurement guards that look fine and cannot fail.** `undersized` in `e2e/support/measure.ts`
  returns `[]` both when everything passes and when its selector matched nothing, so every call site
  counts what it matched first. A compound selector defeats even that: `count()` over
  `a, b, c, d` passes on the first clause alone, so each clause is now guarded on its own. The helper
  itself is **#80** — fixing it there would turn three other suites red inside a feature diff.

- **Backticks inside an Angular inline template terminate the template literal.** Two comments with
  `` `aria-controls` `` in them produced `Parsing error: ',' expected` from a TypeScript parser, which
  is a confusing way to be told about a backtick. An `@` in an HTML comment is fine; a backtick is not.
