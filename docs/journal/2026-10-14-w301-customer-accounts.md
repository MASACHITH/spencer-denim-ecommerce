### `IEffectivePermissionsProvider` and the security stamp

A customer password reset and a customer password change both call
`UserManager.UpdateSecurityStampAsync`, which is the mechanism that provider's five-minute
`(userId, SecurityStamp)` cache is keyed on, and the mechanism both cookie schemes revalidate against.
`CustomerPasswordEndpointTests.Resetting_a_password_replaces_it_and_ends_every_other_session` proves it
from the outside: a second browser's session ends within one revalidation interval.

### Three overlaps to merge later, named now

1. **`CustomerAccountLockout` and #146's `StaffAccountLockout` will be near-identical.** #146 is open, not
   merged, and it also replaces the EF user store with an `AppUserStore` — a change to a shared startup
   path in the middle of his review. So this branch does not touch the store: every statement in

   not use `IdentityOptions.Lockout` at all. **The document's sentence is still unimplemented in the

3. **`IdentityOptions.Password` is at Identity's defaults** — six characters with four character classes

   Identity's validators. **Staff passwords are still six characters**, which is the weaker of the two and
   the one that matters more.

## Decisions, and why

### Registration issues no session

Doc 11 P11 keeps step A (register) and step B (sign in) separate, and the reason is sharper than it
looks: a response that sometimes carried a session and sometimes did not **is** the enumeration oracle
that doc 08 §3.1 DB10's generic sentence exists to close. So registration answers one sentence and 202
for a free address, an address that already has a customer account, and a staff address alike — compared
**byte for byte** in `Registration_answers_identically_for_a_free_a_taken_and_a_staff_address`, because
four 401s with four different sentences would be the same leak in a uniform.

The difference lives in the inbox, which is the only place the person entitled to know will see it: a
customer match gets `AccountExists`, a staff match gets nothing at all (doc 08 D7 — a staff member who
shops uses another address).

### No reply promises an email

Doc 08 §3.8's transport is unconfigured until the client's mail credentials arrive. W3-02 removed "we
will email your order number" from checkout for this reason and `checkout-page.spec.ts` pins its absence;
the brief records two Majors from exactly that. So:

- registration answers *"If that email address can be used, we have queued a link to it. You can sign in
  now with the password you chose."* The second clause is doc 11 §7 **G-24** being useful: an unconfirmed
  customer can sign in, shop and check out, so the shopper has a next step that does not depend on an
  email arriving at all.
- forgot-password answers *"…we have queued a reset link to it. If nothing arrives, please get in touch
  with us."*

`No_reply_claims_an_email_has_been_sent` asserts the absence of "we have sent", "we've sent" and "check
your inbox" **and** the presence of "queued", so the wording cannot drift into vagueness either.

### What happens to a reset when SMTP is unconfigured

Two cases, and they are different:

- **`Email:StorefrontBaseUrl` set, SMTP not configured.** The token is minted, the message is queued, and
  `SendEmails` leaves it alone and spends no retry — doc 08 §3.8's designed behaviour. The customer gets
  nothing. This is correct and is not a bug.
- **`Email:StorefrontBaseUrl` unset.** There is no link to build, so **nothing is queued and no token is
  minted**. Minting one would replace a link the customer might still be holding with one nobody can ever
  use. `With_no_storefront_origin_no_reset_is_queued_and_no_token_is_minted` asserts both, including that
  the previously stored token value is byte-identical afterwards.

**The deployment consequence an operator has to know**, and it is in the task report as well: with no
configured origin, a customer can never confirm their address, so doc 08 §3.1 D5's guest-order linking
can never happen for them. `CustomerAccountLog.RegistrationWithoutConfirmationLink` says so at warning
level, once per registration.

### One-time tokens, and why not Identity's own

`CustomerAccountTokens` mints `{userId}.{32 random bytes, base64url}` into `identity.UserTokens`, stores
only the SHA-256 of the verifier plus the expiry (plus, for a confirmation, the address it was minted
for), and redeems with a conditional delete whose affected-row count **is** the claim — #146's pattern.

Identity's `AddDefaultTokenProviders` was not used, for two reasons:

1. **Neither of its tokens is single-use.** A reset token is spent incidentally, because the reset bumps
   the stamp; a *confirmation* token is not, because confirming an address does not rotate the stamp. So
   Identity's confirmation link stays live for its whole lifetime and can be replayed.
2. **Nothing can revoke either.** A customer who presses "send me a new link" twice has two live links,
   and a customer who suspects their mailbox was read has no way to invalidate the one that was sent.
   With a row, the row *is* the token: a new mint overwrites it, a redemption deletes it.

The selector in front of the dot is a lookup key, not a secret: it buys a keyed read on the `UserTokens`
primary key instead of a scan of a table whose other rows are staff authenticator keys. It leaks an upper
bound on how many accounts the shop has, to somebody who already holds their own link. That is the whole
cost.

### A defect this found: a stale link deleted the live one

The first version spent the stored token row whenever a redemption failed, restricted to the stored
value. So opening a **stale** confirmation link — one the customer had replaced by asking for a new one —
deleted the row holding the **new** token, and anybody holding any old link could invalidate a stranger's
pending confirmation or reset.

`Asking_for_a_new_link_invalidates_the_previous_one` caught it. The row is now spent only when the
verifier matched and the token has merely expired. Both stores had it; both are fixed, and
`stale-link-kills-live-one` is in the mutation list.

### Audit rows: `Lockout` and `LinkGuestOrders`, and deliberately not `Login`/`LoginFailed`

Doc 08 §3.1's explicit security-event list is about staff (`StaffDeactivated`, `AdminPasswordReset`,
`RoleAssigned`…) and gives `LastLoginAtUtc` as the column for "when did this user last sign in", which
the authenticator writes with a one-column set-based update. Two rows are **not** written for customers:

- **`Login` per shopper per visit** would be the highest-volume thing in `ops.AuditLogs` with no screen
  that reads it — ADM-15's customer detail shows order history, not sign-ins.
- **`LoginFailed` on a public form** would store an address somebody *typed*. For an address with no
  account that row carries `UserId = null`, so doc 08 §3.1 step 6's anonymisation — which scrubs by
  `EntityType` and this user's ids — **cannot find it**. A table of addresses that do not have accounts,
  un-scrubbable, is the enumeration these endpoints exist to prevent, written down.

The sign-in `Lockout` row also carries **no user id and no email**, because the authenticator reports a
lockout without reporting which account: a result that named it would make the reply "this address exists
and is now locked". The change-password `Lockout` row *does* carry the id, and the difference is the
point — that caller already holds a valid session for the account.

**Both are decisions rather than transcriptions**, and an owner who wants the volume for fraud work can
have it with a retention rule of its own.

### No antiforgery token on the customer routes

The admin app registers a single `AddAntiforgery` with one cookie name and one header, and a second
configuration is not something this task may add to a shared startup path. What protects these routes
instead is two things together: the session cookie is `SameSite=Lax`, so a browser withholds it from
every cross-site `POST`, and every route reads a JSON body, which a cross-site HTML form cannot send. The
one thing `Lax` permits is a top-level cross-site **GET**, and no route here changes anything on a GET.

`Lax` rather than the admin cookie's `Strict` is itself deliberate: the storefront is reached from search
results, from shared links and — the case that decides it — from the shop's own emails, and `Strict`
would drop the cookie on every one of those, so a customer following their order link would arrive signed
out.

**This is reasoned, not inherited, and the task report asks for a second opinion on it.**

### Rate limits, which nothing in this build had on an authentication endpoint

`AccountRequestThrottle` gives four separate budgets per caller per ten minutes, partitioned by
`ClientAddressPartition` (so an IPv6 subscriber cannot walk a /64 — W0-15's tester sent 25 newsletter
signups from 25 addresses in one /64 and every one was accepted):

| Endpoint | Budget | Why that number |
|---|---|---|
| sign-in | 30 | a person signs in once and mistypes twice; the margin is for carrier-grade NAT and shared connections |
| register | 5 | each writes a user row and queues two messages |
| forgot-password / resend | 5 each | the cost lands in *somebody else's* inbox |
| redeem a link | 20 | the verifier is 256 bits, so this stops walking a list of leaked links rather than guessing |

Taken **before** the use case, unlike `INewsletterSignupThrottle`, which is deliberately asked late
because its cost is a row: here the cost is a password hash and cannot be reclaimed. A refused request
does no database work and counts towards no account's lockout.

**It is not the lockout and does not replace it.** The lockout protects one account from being guessed
at; this protects the shop from one source trying many accounts, which a per-account lockout cannot see.

The four budgets live on `CustomerSecurityOptions` rather than being constants, for two reasons: a
deployment whose proxy headers are not trusted has every visitor in one bucket and raising these is the
stopgap while that is fixed; and a test cannot raise a constant — the 30-attempt sign-in storm was
measuring the rate limiter rather than the lockout until they moved.

### Doc 11 §7 G-41 is still outstanding

It asks for the slip-upload rate limit to be applied to guest **order-link** views as well, and names doc
08 as the place to write it down. Nothing rate-limits `GET /api/orders/{token}`. W3-01 did not do it —
that endpoint is W3-02's and the token is a guest's only credential, so changing its refusal behaviour is
a decision for the task that owns it. It is still open.

### The HTTP race tests could not fail, and that is worth recording

`CustomerSignInRaceTests` and `CustomerAddressEndpointTests` fire concurrent requests through
`WebApplicationFactory` behind a `TaskCompletionSource` gate. Both **survived** the mutations they were
written for:

- replacing `CustomerAccountLockout`'s atomic `SET [AccessFailedCount] = [AccessFailedCount] + 1` with a
  read-then-write — the exact bug #146 measured as 60 parallel failures leaving a count of 4;
- removing `sp_getapplock` from `CustomerAddressStore`.

Tried, in order, and each one still green: 8 racers instead of 4; `RunContinuationsAsynchronously` on the
gate (a plain `TaskCompletionSource` runs its continuations synchronously on the thread that calls
`SetResult`, so the tabs resume one after another); `Task.Run` per caller; and a 150 ms delay injected
into the address `COUNT` through a `DbCommandInterceptor` — #146's own technique, "with delayed token
writes to force the worst case". Diagnostic output from the address race under mutation:
`statuses=[409,201,409,409,409,409,409,409]`. The requests in that harness do not overlap.

So two tests drive the stores from parallel DI scopes, each with its own `AppDbContext` and connection:

- **`CustomerLockoutConcurrencyTests`** — 24 concurrent failures against a threshold of five. **This one
  kills the read-modify-write mutation**, so the atomic counter is proven load-bearing rather than argued
  for.
- **`CustomerAddressConcurrencyTests`** — eight concurrent callers cannot exceed the cap.

### A test-setup trap worth recording

`UserManager.CreateAsync` **forces `LockoutEnabled = true`** on every new user, because
`IdentityOptions.Lockout.AllowedForNewUsers` is true. Setting the property on the instance does nothing.
`An_account_exempt_from_lockout_is_never_reported_as_locked` failed on its first run because the product
was right and the test had been handed an account that was not exempt at all.

## PDPA

Everything W3-01 adds is reachable by doc 08 §3.1 step 2's deletion list:

- `identity.CustomerAddresses` — named in step 2, and the table has **no cascade** from `Users`, asserted
  in `CustomerAddressSchemaTests.Neither_foreign_key_cascades`. A cascade would mean the one path nobody
  expects — a hard delete of a user — silently taking addresses with it and bypassing the audited routine.
- `identity.UserTokens` — the customer tokens use login provider `SpencerDenim.Customer`, and step 2
  deletes `UserTokens` wholesale.
- `ops.EmailOutbox` — step 2 deletes rows for the email, and the account emails carry no
  `RelatedEntityId`, deliberately: the only thing it could hold is the customer's user id, which would be
  a durable pointer to a person on a table doc 08 §3.8 lists as "never audited" precisely because its
  bodies are sensitive, and it would survive the body being destroyed.
- `ops.AuditLogs` — the only customer rows are `LinkGuestOrders` (entity type `User`, carrying the user
  id, so step 6 finds it) and `Lockout`.
- **No log line carries an email address, a password, a token or a link.** `CustomerAccountLog` says so
  and every message there is keyed on the user id, which is the one identifier step 6 can scrub.

**The §3.1 step 2 acceptance test was not re-run against this branch**, and that is a gap the tester
should close: the routine does not exist in code yet (it is ADM-15/P17's), so there is nothing to run —
but when it is built it must cover `identity.CustomerAddresses` and the two new `UserTokens` names. The
brief warns that that test's phone clause searched for the literal `@p0` against a null column until
yesterday; nothing here inherits it.

## Corrections to the brief

Listed in the task report in full. The short version:

1. **`SqlQuery<T>` cannot run an `UPDATE … OUTPUT`** — `EmailOutboxStore` records why ("`SqlQuery`
   composes the SQL into a subquery, which an `UPDATE` cannot be"). The first `CustomerAccountLockout`
   was written that way and had to be replaced by two mutually exclusive conditional `UPDATE`s, which
   give the same guarantee with no raw `DbCommand`, no manual execution strategy and no connection
   management.
2. **The brief's database list is accurate.** Verified against `sys.databases`: ten
   `SpencerDenim_Test_*` (nine plus the orphan it names), eight `SpencerDenim_W113_*`,
   `SpencerDenim_Dev`, `SpencerDenim_W103_Tester`. Nothing was dropped.
3. **"Run the whole Playwright suite if you touch a shared stub"** — no shared stub was touched, so it
   was not run. Said plainly rather than silently.
