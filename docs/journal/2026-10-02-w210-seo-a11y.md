## 1. What was built

### robots.txt — served by Express, ahead of the Angular router

`projects/storefront/src/server/robots-txt.ts`, mounted in `src/server.ts` **before** the static
middleware and before the render handler.

Position is the requirement, not a preference. There was no such file anywhere in the build, so the
request fell through to the router; **a crawler answered 5xx for `robots.txt` treats the whole site as
disallowed** until it can read one, and a route table is the last place that answer should be able to
come from. It is mounted ahead of `express.static` too, so a file dropped into `public/` later cannot
shadow it — the file has to be generated, because the `Sitemap:` line carries the deployment's own
origin and nothing checked into the repository can know what that is (doc 03 §5).

Proved by request on three servers: the healthy pair, the pair whose product queries all answer 500,
and (in `catalog-availability.e2e.ts`) the pair whose departments feed is destroyed mid-run. 200 and
`text/plain` in all three.

**`/search` is deliberately *not* disallowed**, and that is the one line in the file most likely to be
"tidied up" wrongly. It answers `noindex` (SRCH-02, on W2-07's branch). `Disallow` and `noindex` read
as the same wish and are opposites in effect: a crawler that may not fetch the page never reads the
`noindex`, and a link to the URL from anywhere else is enough for it to be listed without a snippet.
Allowing the fetch is what makes the `noindex` work. There is a comment in the file, a unit test and an
e2e test, all three saying so, because this is the kind of thing that gets corrected by someone being
helpful.

### sitemap.xml — from the live catalogue, bounded, cached, and 503 rather than empty

Three pieces:

1. **`GET /api/catalog/sitemap`** (`CatalogEndpoints` → `GetCatalogSitemapQuery` →
   `ISitemapCatalogReader` → `SitemapCatalogReader`). It answers **slugs and timestamps, not URLs**:
   the storefront owns its route table, and an API that published finished paths would hold a second
   copy of it, so a route change would be a silent sitemap bug.
2. **`CatalogVisibility`** (new, `Infrastructure/Catalog`). The predicates for "a shopper may see
   this" were written out inline in `ProductCatalogReader.BaseQuery()` and in
   `DepartmentCatalogReader`. Both now compose this, and so does the sitemap reader. The brief asked
   for the storefront readers to be used rather than a second definition of "visible", and this is how:
   there is exactly one. It matters as of W1-12 — the client can now deactivate and soft-delete
   categories, so a sitemap with its own rule would start drifting immediately and silently, offering
   a crawler listings that answer 404. The chained `Where` calls became one conjunction, which EF
   translates to the same `WHERE … AND …`, so DB28's filtered indexes still match. Soft deletion is
   deliberately **not** repeated: `AppDbContext.SoftDeleteFilter` is global.
3. **`projects/storefront/src/server/sitemap-xml.ts`**, which turns that into the document.

Size and caching, as asked:

- **Bounded in SQL.** `Catalog:SitemapMaxProducts` (default 45,000) with `Take(limit + 1)`, so
  "there are more than we will publish" is read off the database rather than guessed, and
  `ProductsTruncated` says so in the response and in an XML comment in the document. 45,000 and not
  50,000 because 50,000 is the protocol's own hard limit for one file, and a limit a document may
  reach exactly is a limit it will one day be one row past; the margin is the room to notice before a
  crawler's error report does. Reaching it means a sitemap index with several files, which is a change
  to make on purpose.
- **Three queries whatever the catalogue holds** — departments, categories, products — asserted in
  `CatalogSitemapTests.It_reads_the_whole_catalogue_in_three_queries` with the command-counting
  interceptor. It is the one read in the system whose result set grows with the whole shop, so an N+1
  here is a crawler hitting the database once per product. Nothing fetches media, variants or stock.
- **Cached as a rendered document for 15 minutes**, in the SSR process, with concurrent misses sharing
  one fetch. Long enough that a crawler cannot turn a public URL into a catalogue scan, short enough
  that a product published this morning is offered by lunchtime; crawlers re-read a sitemap on their
  own schedule, measured in hours, so nothing is lost. The payload is cached and the document rendered
  per origin from it, so a change of public origin cannot serve stale `<loc>`s.
- **503 with `Retry-After` when the catalogue cannot be read**, never 500 — and never an empty
  `<urlset>`, which is the trap. An empty urlset is a *valid* document saying this shop has no pages,
  and a crawler has no way to tell it from the truth; a 503 keeps every URL it already holds. That is
  #30's lesson applied to a document rather than a page, and `RETRY_AFTER_SECONDS` is imported from
  `service-unavailable.ts` so the site still speaks with one figure. The last good document is served
  through an outage for up to 24 hours first (with a short `max-age`, so the next crawler gives the
  catalogue another chance); past a day the outage is not a blip and the 503 is the honest answer.
- The API's own words never reach a response body — only `console.warn`.
- The body is vetted before it is believed (#30's `garbage` mode: a proxy answering 200 with something
  else entirely). A body that is not the shape we asked for is a failure, and the last good document
  stands.

### Open Graph and canonical — one service, not a second way to do it

`core/platform/page-metadata.ts` (`PageMeta`) sets the title, the description, the canonical address
and the whole social card, and clears the card and the canonical on the way out. The home, listing and
product pages each had their own `title.setTitle` + `meta.updateTag` + `canonical.set` trio; they now
make one call.

**It uses `CanonicalLink` and leaves `RobotsMeta` alone.** The brief is right that this area has been
got wrong before and that there must not be a second way to do the same thing. `CanonicalLink` still
owns the one `<link rel="canonical">` and it is still **relative** on purpose (its own docblock says
why). `RobotsMeta` still owns `noindex`, and it is deliberately not folded in: whether to be indexed
is a decision about a status code — a 404 asks for it, a 503 must never (#30) — not about metadata.
Nothing in this change sets or clears `robots` anywhere new.

**`og:url` and `og:image` are absolute while the canonical stays relative**, and both halves are
asserted in one test so neither gets "tidied" into matching the other. A crawler resolves a relative
canonical against the document; the Open Graph consumers do not resolve relative URLs at all — they
drop the tag, and the share card goes with it.

The absolute origin comes from `SITE_ORIGIN` (`core/platform/site-origin.ts`): `location.origin` in
the browser, and on the server from `src/server/origins.ts`, which is the part worth reading:

> `Host` and `X-Forwarded-Host` are sent by the client. This project has already shipped one defect of
> exactly that shape — W1-01 round 3, a forged `X-Forwarded-For` written straight into
> `ops.AuditLogs` — and the fix there was to stop trusting the header rather than to sanitise it. A
> forged `Host` here would put a stranger's domain into the `Sitemap:` line and into every `og:url`:
> this shop asking a crawler to go and index someone else's site in its name.

So the order is `PUBLIC_SITE_ORIGIN` (the deployment's own answer, and the only thing that knows the
public name behind Caddy) → the request host **only when it is a loopback name or listed in
`NG_ALLOWED_HOSTS`**, which is the allow-list the Angular engine already validates renders against →
`https://` plus the brand domain. A configured value with a path, a query, credentials or a non-HTTP
scheme is rejected rather than repaired, because `PUBLIC_SITE_ORIGIN` with a trailing path silently
doubles a segment into every URL in the sitemap. Measured live with `curl -H "Host: evil.example.com"`:
the `Sitemap:` line comes back `https://colombowardrobecompany.com/sitemap.xml`.

Pictures: the product page's share image is the product's own first photograph **for the colourway
`null`**, not the selected colourway, because the canonical address is the product rather than the
colourway and a card showing whichever colour happened to be selected would illustrate a different
URL. The listing uses the same picture it draws at the top of itself. The home page has no picture of
its own — everything on it is ADM-17 content — so it takes the hero's still (`videoPosterUrl`, which
is the frame the client chose, since a share card cannot play a video), falling back through the
section images; `PageMeta` shrinks the card to `summary` rather than publishing an empty `og:image`
while the content API is still in flight.

`PUBLIC_SITE_ORIGIN` is a **new deployment variable** and production must set it. Until it is set the
server falls back to the brand domain, which is right for production and wrong for staging — so it
belongs in W1-07's and W0-15's environment files. Noted below.

## 2. The defects

### #28 — a mistyped department answered 200 with the home page

`**` → `redirectTo: ''` is now `**` → `NotFoundPage`, which answers a real 404 with `noindex`.

**The brief and #28 disagree about whether this was possible yet, and #28 is right about the obstacle
but wrong that it blocks the fix.** #28 says to wait for GLB-10, W2-08 and W2-09, because the single
segments the catch-all was swallowing include `/bag`, `/wishlist`, `/account`, `/about`, `/contact`,
`/shipping`, `/returns`, `/privacy` and `/terms` — every one of which the header, the footer or the
search form links to **on every page of the site**. Pointing the catch-all at the 404 page on its own
would have answered 404 on a link the shop's own footer offers, which is worse than the soft 404.

The answer is the allow-list the project already anticipated — `catalog-route.guards.ts` records the
same shape as "W1-12's to answer with an allow-list of its own". `UNBUILT_PATHS` in `app.routes.ts`
holds the eleven addresses the shell links to and has not built; each keeps `redirectTo: ''`, each is
deleted by the task that gives its page a real route, and a leftover entry is harmless because a real
route declared above it wins.

**`pathMatch: 'full'` on those routes is load-bearing, and leaving it out was a real defect I
introduced and then measured.** A route's default is `'prefix'`, so `path: 'account'` also matched
`/account/orders`; Angular redirected to the matched prefix's target and kept the rest, and the answer
was a **404 with a zero-byte body** — a blank screen for a shopper and nothing at all for a crawler,
which is worse than what #28 is about. Measured on `/account/orders`, `/bag/checkout` and `/about/x`,
all three 404 at `len=0`. It was caught by widening my own assertion to the body rather than the
status; there is now a test for it on the wire and a `pathMatch` assertion in the route spec.

**#30's 503 is untouched, and the single-segment case is deliberately routed differently rather than
overlooked.** The 503 routes claim every two- and three-segment address whose first segment is a
department the tree in hand already holds, and they are matched before the catch-all, so a listing the
catalogue could not be asked about still answers 503 with `Retry-After`. For a **department** the
ambiguity #30 exists for does not arise: nothing creates one at runtime — the admin API has no
create-department endpoint (only update, reorder and set-active), and W1-12 settled that a
department's name and slug are not editable (docs/02 §I2) — so the seeded list is closed,
`navigation.data.ts` mirrors it, and a single segment the tree in hand does not have is not a
department whichever tree that was. Written down because it is the one way this could become wrong:
**if a later migration seeds a sixth department, that fallback has to gain it in the same change**, or
its listing will 404 for the length of an outage. There is a test for the property in
`catalog-availability.e2e.ts` and the reasoning is in a comment beside it.

Two existing suites asserted the old behaviour and were updated rather than deleted — see §4.

### #76 and #20's SH11 — the `h1` came after the mega menu's headings

One defect seen from two distances, fixed together as the brief says.

- `main-nav.ts`: the `h3` group titles are `<p class="mega__title">` with the child `<ul>`
  `aria-labelledby` them. #20's own suggestion; the relationship the heading carried is kept and only
  its place in the heading outline is given up.
- `drawer.ts` (shared): the `h2` "Menu" is a `<p>` keeping its id. The dialog already takes its name
  from that text through `aria-labelledby`, and a name is what the text is for.
- Both gained `line-height: 1.2`, because the reset gives `h1`–`h4` a tighter line-height than body
  text and the look had to survive the change.
- `navigation.model.ts`'s docblock said "heads the group as a heading". Corrected, so the model does
  not describe markup that no longer exists.

Measured over the **DOM order of every heading in the document**, not over what is visible: the drawer
and the mega menu are in the markup of every page whether they are open or not, and the whole defect
was that being in the markup earlier was enough.

### #20's SH8 — the mega menu re-opened when focus came back after Escape

`main-nav.ts:onFocusOut` cleared the dismissed guard whenever focus left a **list item**. Focus Women,
Escape (guard = `women`), Tab to Men — Women's item lost focus, the guard was wiped — Shift+Tab back
and focus re-opened what Escape had just closed. It is now cleared only when focus leaves the **whole
nav**, which is #20's own prescription.

I read W2-07's search combobox first, as the brief asked, with `git show origin/feature/W2-07-search:…`
rather than entering that worktree. **Its docblock is about SH8, not SH12** — "the popup never opens
from focus alone … that is what keeps it out of the class of bug #20 records one component over". Its
shape cannot be adopted here and the difference is not a preference: the mega panel is `[hidden]` when
closed, so its links are not in the tab order, and opening on focus is the *only* way a keyboard
reaches the categories from the desktop nav (the drawer is hidden above 1024 px). That is why GLB-05
and the component's docblock both say it opens on hover *and* on focus. So the guard is the right
shape for this component, and the fix is to scope it correctly rather than to delete the behaviour.
Five tests cover the surrounding behaviour so the guard cannot be over-applied: the next department
still opens on the way past, hovering the dismissed one opens it, and leaving the nav and coming back
opens it.

### #20's SH12 — the announcement text wrapped to three lines at 320 px

**Only `Previous` is hidden below 375 px, and the issue's suggestion to hide `Previous` and `Next` is
the thing not to do.** Under `prefers-reduced-motion` the bar does not rotate, so `canRotate()` is
false and the pause control is **not rendered at all**; with both arrows gone as well, the second and
third messages would be unreachable on a 320 px phone. That is content a visitor cannot get to rather
than a layout nicety. `Next` on its own still reaches every message, because it cycles — so the one
control whose job another control already does is the one that goes, the WCAG 2.2.2 pause stays, and
the 44 px floor is untouched for everything still on the row. Measured: the message is two lines at
320 px, and a reduced-motion test walks all three messages with `Next` and checks the visually hidden
status announces the third.

### #38 — the product card's wishlist heart had no visible focus ring

The card drew one on a `::after` with `inset: 2px` — **inside** its own border box. The comment above
it cited lesson L4 ("the `::before` fill would paint over an inset outline"), which was right about
`::before` and wrong about the outline: the global rule in `base.css` draws it at
`outline-offset: 2px`, clear of the border box, where a `::before` at `inset: 6px` cannot reach it. So
the override was never needed and it put the ring somewhere invisible from outside the control.

Now the global ring, as every other control on the site uses it, plus a `box-shadow` filling the 2 px
the offset leaves with `--color-on-primary` — the white band is what makes a dark ring legible over a
dark photograph, which is what the old `::after` was really for. Both are outside the border box, so
neither can be painted over.

Measured with `edgesWithoutRing`, as #38 instructs, on the listing **and** on the home page, which is
where it was found. Before: `["top","bottom","left","right"]`. After: `[]`.

### #65 — axe-core was in `docs/06` and in nothing else

`@axe-core/playwright` and `axe-core` (both 4.13.0, pinned exact) are dev dependencies, and
`e2e/accessibility.e2e.ts` runs axe over the home page, a department listing, a category listing, a

## 3. Everything axe found

One violation, on every storefront page, at **moderate**:

```
{"id":"region","impact":"moderate",
 "targets":[".sr-only[_ngcontent-ng-c3124413000=\"\"]"]}
```

This is the one #65 names. The node is the floating WhatsApp button's visually hidden label
(`whatsapp-button.ts`). `app.ts` renders that button after `<sd-site-footer />`, so it sits outside
`banner`, `main` and `contentinfo` alike, and content outside every landmark is content a screen-reader
user navigating by region never arrives at.

**Fixed rather than allowed.** The button is now its own named landmark
(`host: { role: 'complementary', 'aria-label': 'Chat with us' }`). It cannot simply move: it is
`position: fixed` and site-wide, so `main` is the wrong place (that is the page) and it cannot be
nested inside the footer component's own `<footer>` from `app.ts`. A named complementary landmark is
the honest description — a site-wide way to get in touch, beside the page rather than part of it — and
it costs one entry in a landmark list. `axe over the storefront › … leaves nothing outside a landmark`
now holds it fixed on all five pages, separately from the serious/critical gate, so this specific rule
cannot come back silently without tightening the documented gate.

**After the fix: zero violations at any impact** on the home page, both listings, the product page and
the 404 page, and zero serious/critical on the open mega menu, the open drawer, the 503 page and the
admin sign-in.

Found by hand, not by axe, and fixed: **the 404 page's "Back to the home page" link measured 175×20 at
all eight breakpoints.** WCAG 2.2's 2.5.8 floor is 24 px and this project's own is 44. It had gone
unnoticed because nothing measured the links on that page — the five department links beside it are
`.btn btn--secondary` and pass, so an assertion scoped to the buttons could not have failed. It matters
more now than it did yesterday, because the #28 fix sends every mistyped address to this page. Fixed
the same way the sibling 503 page fixes its own (`unavailable__links a`), with `width: fit-content` so
the row is not a 175 px-wide target that is mostly empty.

## 4. Tests that changed rather than were added

Three existing assertions described behaviour this task deliberately changed. None was deleted; each
kept its intent and changed its expectation, with the reason in a comment beside it.

1. `listing-page.spec.ts` — "`/not-a-department` goes back to the home page, not to the listing". The
   path moved out of the shared loop into two tests of its own asserting the 404 page. The property it
   protected (a mistyped department must not render the listing's empty state and claim a department is
   gone) is unchanged; the home page at HTTP 200 *was* the defect.
2. `catalog-unavailable-page.spec.ts` — "still sends a first segment that is not a department to the
   home page" → "answers 404 for a first segment that is not a department, never 503". The half this
   file exists for — it is not swept into the 503 route — is what is now asserted.
3. `catalog-availability.e2e.ts` — "addresses that are not listings keep answering as they did" →
   "… are never a 503". Nine paths that asserted `200` at `/` now assert `404` with no `Retry-After`.
   `/wp-admin/setup-config.php` is the clearest case of why that is an improvement: a scanner's probe
   was being answered with the shop's front page. The `well-known files` canary was also corrected:
   `robots.txt` must be 200 whatever is wrong, but `sitemap.xml` is a catalogue read and **may**
   legitimately be 503 with `Retry-After`, so asserting 200 for it would have contradicted the design
   in the same file.

One shared test-config change: `projects/storefront/tsconfig.spec.json` gained `"node"` to its `types`,
because the SSR server's own modules under `src/server` are the only code in the project that reads
`process.env` and their specs read it too. `tsconfig.app.json` already lists it for the same reason.

## 7. Where this brief was wrong, and other things worth saying

1. **#28 cannot be fixed the way #28 describes, and the brief inherits that.** The brief says to fix it;
   #28 says to wait for GLB-10, W2-08 and W2-09, which the brief excludes. Both are reconcilable only
   with the `UNBUILT_PATHS` allow-list, which is what I built — `catalog-route.guards.ts` already
   anticipated needing one. Without it, pointing the catch-all at the 404 page would have 404'd ten
   addresses the site's own header and footer link to on every page.
2. **The note about W2-07's combobox is filed under SH12 and belongs under SH8.** That component's
   docblock is about a menu re-opening on focus after Escape, not about a 320 px row. I read it anyway
   (`git show origin/feature/W2-07-search:…`, never entering that worktree) and it did change what I
   checked for SH8 — but its shape cannot be adopted, because the mega menu's focus-opening is the only
   keyboard route to the categories. Reasoning in §2.
3. **#20's suggested fix for SH12 would have cost content.** Hiding `Previous` *and* `Next` below
   375 px leaves a reduced-motion visitor on a 320 px phone unable to reach the second and third
   messages, because the pause control is not rendered when the bar does not rotate. Only `Previous` is
   hidden.
4. **#38's description does not match the code as it stands on `main`.** The issue says
   `button.card__wish` computes `outline-style: none` "with no `box-shadow` standing in"; there *was* a
   `::after` ring, added in the same PR that created the card (#31). It was simply drawn inside the
   control, so the issue's measurement — and `edgesWithoutRing` — were right about the symptom and the
   stated cause was incomplete. The fix addresses the real cause.
5. **`/sitemap.xml` legitimately answers 503 during an outage, which contradicts an assertion the
   #30 suite already had.** `catalog-availability.e2e.ts` asserted `{'/robots.txt': 200,
   '/sitemap.xml': 200, '/favicon.ico': 200}` as a canary written when neither file existed. Corrected
   rather than worked around: `robots.txt` must be 200 whatever is wrong; `sitemap.xml` is a catalogue
   read and 503 with `Retry-After` is the right answer when it fails.
6. **`PUBLIC_SITE_ORIGIN` is a new deployment variable.** Not setting it is safe but wrong on staging:
   the server falls back to the brand domain, so staging would publish production addresses in
   `og:url` and in the `Sitemap:` line. It belongs in W0-15's compose files and W1-07's staging
   environment.
7. **A pre-existing dependency advisory that this project is exposed to.** `npm audit` reports
   `@angular/router` **high**: *"Angular Server-Side Rendering (SSR): Denial of Service via Numeric URL
   Matrix Parameters"*. This storefront is an SSR Angular app with a public catch-all route, so it is
   precisely the shape the advisory describes, and the #28 change means more addresses now reach the
   router's matching rather than a redirect. Also `@angular/build` and `piscina` at critical, both
   build-time. None of the three comes from axe (which added exactly two packages). Not touched here —
   an Angular upgrade is not this task — and raised as **#84**.
