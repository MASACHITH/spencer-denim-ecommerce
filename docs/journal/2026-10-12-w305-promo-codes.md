## The per-customer race, and the test that could not fail

**Doc 08 §3.6's `sp_getapplock` is the only thing between two simultaneous checkouts by one email**, and
the first version of `CheckoutPromoRaceTests` proved nothing about it.

The four shoppers shared **one variant**. Each checkout's conditional stock `UPDATE` takes a row lock on
the same `inventory.StockLevels` row and holds it to commit, so the four were serialised *before* they
reached the promo section — and the per-customer count was then correct because of a row lock on an
unrelated table. **With the `sp_getapplock` statement deleted, the test stayed green.**

Two changes:

1. **Each shopper holds a different variant**, so four different stock rows are locked and nothing
   serialises them before the promo section.
2. **`CommandCountingInterceptor` can now watch a substring of the command text**, and the test asserts
   how many attempts *reach* the contended statement — not just the end state. The fragment is the
   statement's own alias, `AS HeldUses`, so it cannot drift out of the production SQL without the SQL
   changing; if someone renames it the watch counts zero and the race tests fail on the instrumentation.

**Measured on this machine, six rounds per run:**

| | arrivals at the contended statement | orders placed | `UsageCount` |
|---|---|---|---|
| As written | **4 of 4** | 1 | 1 |
| `sp_getapplock` deleted | 4 of 4 | **4** | 4 |
| One shared variant (the first version) | 4 of 4 | 1 | 1 — **and still 1 with the lock deleted** |

### The ordering, which is not doc 11's

Doc 11 P6 step 9.2 says "total limit, then per-customer limit". `OrderPromoUse.TakeAsync` checks the
**per-customer limit first**, and that is the whole correctness argument: the total limit is applied by an
`UPDATE`, whose row lock on `marketing.PromoCodes` serialises every concurrent checkout using the code.
Run first, it would make the per-customer count correct for a reason nobody wrote, and the app lock would
again be deletable with nothing going red.

The cost is which sentence a shopper sees when both limits are breached at once: this answers
`AlreadyUsedByCustomer` rather than `FullyUsed`. Both are true and both refuse.

### The total-limit race asserts a floor, not an equality

The instrumentation showed **2 of 4** arrivals, and that is correct: the total limit *is* one of
`PromoEvaluator`'s checks, so a contender starting after the winner commits is refused by the
pre-transaction re-validation (doc 11 P3 step 12) and never opens a transaction. An equality of four
there would have been an assertion about thread scheduling. Two is still a contended `UPDATE` — both read
`UsageCount = 0` before either committed — and deleting the limit clause makes `UsageCount` 4 against a
limit of 1.

## Decisions

- **The code travels on the request, not on the cart.** Doc 08 §3.5 gives `Carts.PromoCodeText` a column
  and W2-09 left it out of its migration. What doc 11 P3 step 12 actually requires is that the code be
  "re-validated on every bag read and again at placement", and a code the client resends on every read is
  revalidated on every read by construction. It also keeps the code out of the one row two tabs share.
  **Cost: the code does not survive closing the tab.** Cheap to change later — one column and one setter.
- **The box is on checkout only, not on the bag.** Doc 11 P3 step 9 says "in the bag **or** at checkout".
  The bag deliberately has no delivery fee and no grand total (`CartTotalsDto`'s own remarks), so a
  free-delivery code there would show nothing and a percentage code would sit above a total labelled
  "items only".
- **The per-customer limit is not checked on a quote.** Doc 11 P3 step 10 puts it at placement "when the
  email is known". It also means the GET cannot be used to test whether a given address has used a given
  code. **Cost: a shopper can be refused at Place order for a limit they were not warned about** — the
  refusal re-quotes without the code and says why, which is doc 11 P3's "can place the order without it".
- **Four refusals collapse into one sentence.** No such code, inactive, removed, not started and over all
  answer `NotRecognised`: "we do not recognise that code". The other three — fully used, minimum spend
  (with the figure), already used by you — are each actionable. The box is therefore not an oracle for
  which strings the shop has ever issued, which the guest order link's one-sentence convention is about.
- **`Orders.PromoCodeId` became a real foreign key.** The column has existed and been null since the
  orders migration, which built `IX_Orders_Promo_Email` "as if the constraint existed, so adding it later
  is one `ALTER TABLE` and no index build". `NO ACTION`: a promo code is soft-deleted and never removed,
  so the rule can never refuse an admin a delete. The generated migration adds no index, as that comment
  predicted — checked, not assumed.
- **Two check constraints doc 08 §3.6 does not name.** `MaxDiscountAmount > 0` and `MinSpendAmount > 0`
  when set. A cap of 0.00 would silently make every percentage discount worth nothing while the list still
  said "10%", and a minimum spend of 0.00 is "no threshold" spelled a second way.
- **`ExcludeSaleItems` is a column and an evaluator rule, and is not on the admin form.** It can only
  exclude a line a sale campaign priced, and ADM-14 does not exist — `CheckoutReader.ToLine` computes the
  sale price as `CatalogPricing.SalePrice(list, campaignPrice: null)`, which returns the list price
  unchanged, so no line can satisfy `UnitPrice < UnitListPrice` today. A checkbox that cannot change a
  total is a promise. It is unit-tested against a synthesised campaign-priced line.
- **`Promotions.Create` and `Promotions.Delete` did not exist.** Doc 11 P3's permission table names them.
  Added through the three-step ritual: the constant, the Store Manager grant, and a **new versioned seeder
  increment (`Seed.Version` 3)** so they reach a database whose Store Manager role already exists
  (issue #122, doc 08 §9 N13).
- **Nothing is seeded.** Doc 02 line 167 replaces the demo's `TUASL10` and `FREESHIP` with admin-managed
  codes. No seeded code, no default, no form placeholder — and a unit test and an e2e test both assert the
  absence, because W3-03 shipped a real bank's name as placeholder text.
- **A refused code refuses the placement.** It is not placed at the undiscounted total: the shopper agreed
  to a figure that included the code, and charging more would be G-10 with extra steps.
- **The promo CSS is in `styles.css`, not the component.** Measured: with those four rules in
  `checkout-page.ts` the build warns at 4.33 kB against a 4.00 kB `anyComponentStyle` budget, and with
  them removed it does not warn at all. The page has no room; a warning the next task inherits is worse
  than a rule in the one stylesheet this project already uses for cross-cutting control styling.

## Surprises worth somebody else's time

- **`ApplySoftDelete` adds a *global query filter*.** `CatalogModelTests.Only_the_soft_deletable_entities_have_the_soft_delete_filter`
  went red on `PromoCode` the moment the configuration called it, and three comments I had written said
  the table had no such filter. The test was right and the comments were corrected. Expect this on the
  next `[SD]` table too: the count in that test has to go up with it.
- **A promo refusal at placement had to be told apart from the other two 409s.** The storefront
  classifies a checkout 409 by *which extension the body carries*, never by the title. The new one is
  `promoRefusal`, and `checkoutFailure` gained `'promoRejected'`.
- **The checkout promo panel changed the tab order**, and `checkout.e2e.ts`'s focus-ring test caught it:
  Tab from the note used to land on Place order and now lands on the promo box. The panel is in the
  summary, which follows the form in the DOM, so the tab order is the visual order and doc 11 P6's own
  step order (step 5 applies a code, step 7 places the order). The test now tabs from the panel's last
  control, and the promo box joined its focus-ring loop.
- **The e2e checkout stub was missing `buyableItemCount`.** `CheckoutTotalsDto` has required it since
  W3-02 and the bag's half of the stub builds it, so under the stub the checkout printed
  "Subtotal ( items)" and no browser test could see it. Fixed while mirroring the DTO for the promo
  fields — issue #126 in miniature.
- **`string.Create(CultureInfo, $"…" + $"…")` does not compile.** Concatenated interpolated strings are a
  `string`, not a `DefaultInterpolatedStringHandler`, so the overload resolution fails with CS1620. One
  long interpolated string per call.
- **CA1859 is an error in this solution**, so a private helper returning an interface where a concrete
  type would do fails the build. Four of mine did.

## Mutations, and which test each one killed

Every new test was proved by mutation. One survived and was a real hole.

| # | Mutation | Killed |
|---|---|---|
| 1 | `sp_getapplock` deleted from `OrderPromoUse.TakeAsync` | `Four_simultaneous_checkouts_by_one_email_take_one_use_of_a_per_customer_code` — 4 orders against a limit of 1 |
| 2 | `AND (TotalUsageLimit IS NULL OR UsageCount < TotalUsageLimit)` deleted | `Four_simultaneous_checkouts_take_only_the_last_use_a_code_has` — `UsageCount` 4 against a limit of 1 |
| 3 | `OrderPromoUse.ReturnAsync`'s `UPDATE` deleted | `A_cancelled_order_gives_its_use_back_and_the_code_works_again` **and** `An_expired_order_gives_its_use_back` |
| 4 | `MidpointRounding.AwayFromZero` → `ToEven` | `A_percentage_rounds_half_away_from_zero` |
| 5 | minimum spend compared with the eligible base | `A_minimum_spend_is_measured_against_the_items_subtotal_and_not_the_eligible_base` |
| 6 | window end `>` → `>=` | `A_code_stops_working_at_its_end_instant_exactly` |
| 7 | `ExcludeSaleItems` compares `UnitOriginalPrice` | `Exclude_sale_items_drops_a_campaign_priced_line_and_keeps_a_marked_down_one` |
| 8 | the percentage cap removed | `A_percentage_above_its_cap_is_the_cap_exactly` |
| 9 | the Colombo conversion removed from `ToUtc` | 7 tests in `PromoCodeScheduleTests` |
| 10 | `Inactive` no longer wins over the dates | 3 cases of `The_status_is_derived_from_the_dates_and_the_flag` |
| 11 | a fixed code not capped at the eligible base | `A_fixed_code_never_exceeds_the_eligible_items` **and** `A_fixed_code_larger_than_the_order_is_clamped_to_leave_one_rupee` |
| 12 | the storefront re-announce dance removed | `re-announces the same refusal, so a second press is not met with silence` |
| 13 | the promo live region moved inside `@if (promoSaid())` | 2 storefront tests, including `keeps the same live-region node across the re-quote that fills it` |
| 14 | `promoCode` not sent on the GET | `sends the code as a query parameter and shows the discount the server priced` |
| 15 | admin: the figures kept across a type change | `clears the amount when the type changes` |
| **16** | **admin: `totalUsageLimit` sent as a hard-coded `null`** | **nothing, at first** |

**#16 is the one that matters.** The "sends every field" test filled in only the three required fields, so
every optional one was `null` in the expected body — and replacing *any* of them with a hard-coded `null`
in the component passed. A test whose expected values are all the same value cannot tell a field that
travels from one that does not. The test now types a distinct value into every box, and there is a second
test for the all-blank case; #16 then goes red.

Two more mutations are worth recording as **compiler kills rather than test kills**: removing
`totalUsageLimit` from the request object entirely, and removing it from `AdminPromoCodeRequest`, are both
TypeScript errors. That is a stronger guard than a test, and it is why #16 had to be written as a *value*
substitution to be a fair mutation at all.

## Still owed, and known gaps

- **The promo report** (uses, discount given and revenue per code) is doc 11 P3's `Reports.View` row and
  is not built. It is a reporting feature, not ADM-13's screen.
- **`promoDiscountAllocated` reaches the storefront success page and the admin order-detail contract, and
  issue #129's own complaint — that it reaches no *screen*** — is only half closed. The order confirmation
  carries it and an integration test asserts it; the **admin order detail does not render it**, because
  that screen was not in this task's diff and adding a row to it is W3-04's file. The figure is readable
  and tested; a refund that used `lineSubtotal` would still be wrong, and nothing on the admin screen
  shows the difference. **Worth one line in W3-04.**
- **The clamp has no integration test**, by decision. It can only bite when the delivery fee is not
  holding the total up, and the only seeded zone rate with a zero fee belongs to `PICKUP` — which ships
  *disabled*, because doc 08 §9 seeds no pickup location. Enabling it would mutate reference data the
  whole integration suite reads, which `CheckoutTestBase`'s own remarks blame for four intermittent
  failures. It is covered by `PromoPricingPipelineTests` instead, and `CheckoutPromoBehaviourTests` says
  so where the test would have been.
- **`PromoCodePlanTests` rebuilds the reader's query rather than observing it**, the same limitation
  `BankQueuePlanTests` has: `FindPromoCodeAsync` is `async` and its `IQueryable` is not reachable. An
  `IgnoreQueryFilters()` added to the reader would turn a seek into a scan and leave the plan test green.
- **`OrderPromoUse`'s per-customer SQL is not reachable for a plan test either**, because `SqlQuery`'s
  text cannot be had without executing it in a transaction. The plan test runs a copy; what closes the
  gap is `CheckoutPromoRaceTests` counting executions by a fragment of the real statement's text.
- **A code applied in one tab does not appear in another**, and does not survive closing the tab. See the
  decision above.

## The whole-assembly integration run, and the two guards that caught me

The first full run was **1,396 / 1,399 with 3 failures, all from two tests in `SalesSchemaTests`**, and
both were right:

- `The_deferred_foreign_keys_are_indexed_columns_with_no_constraint(table: "Orders", column: "PromoCodeId")`
  asserted that the column has **no** constraint. True until this branch. It is out of the list now, with
  a positive `The_promo_code_foreign_key_W3_03_deferred_now_exists` in its place — exactly what W3-02 did
  for the two district keys. `OrderLines.SaleCampaignId` stays in the list; ADM-14 does not exist.
- `Every_sales_foreign_key_column_leads_an_index` found an FK column whose only leading index is filtered,
  and **its own failure message names the two correct responses**. `IX_Orders_Promo_Email`'s filter is
  `([PromoCodeId] IS NOT NULL)`, which `PromoCodeId = @x` provably implies, so it joins
  `FilteredLeadingIndexIsEnough` rather than getting a duplicate plain index.
  `Every_exempted_foreign_key_is_covered_by_an_implied_filter` then checks that shape in the database
  rather than taking my sentence for it, and `PromoCodePlanTests` measures that the seek happens.

**Second run, after the fix: 1,399 / 1,399, 0 failures, 18 m 40 s.**

**One failure in an earlier run was mine and not the code's.** `CartConcurrencyTests.Eight_simultaneous_adds_of_a_new_variant_end_at_one_row_holding_all_eight`
answered 500 once, and it was because I had **two** integration runs against LocalDB at the same time —
