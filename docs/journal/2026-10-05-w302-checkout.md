# 2026-10-05 — W3-02 (CHK-01..04): checkout, guest checkout, delivery methods, order success

Branch `feature/W3-02-checkout`, worktree `worktrees/sd-hero`, cut from `origin/main` at `1c64001`.
Scope: CHK-01 (customer details, delivery address, order summary, validation), CHK-02 (delivery methods
and fees), CHK-03 (guest checkout), CHK-04 (order success page with order number). **Not pushed, not a
PR — the tester goes first.**

## What it does, end to end

A guest adds to the bag, presses **Proceed to checkout**, fills in contact details, picks a district and
a delivery method, sees a priced summary, presses **Place order**, and lands on a success page with an
order number. Server-side: stock is reserved for every line in one transaction, the order and its lines
are written as a snapshot, an open bank payment row is created, and the bag is emptied. Nothing happens
to the money — that is the next task.

## The decisions, and why

### Order numbering — implemented, exactly as doc 08 §3.5 writes it

`INumberSeriesAllocator` / `NumberSeriesAllocator`. One statement:

```sql
UPDATE sales.NumberSeries
   SET NextValue = NextValue + 1, UpdatedAtUtc = @now
OUTPUT deleted.NextValue
 WHERE SeriesKey = @k;
```

The row is inserted lazily with a retry on the PK violation; the insert does **not** claim a value, so
both the winner and the losers allocate through the same UPDATE and the two paths cannot differ. Order
numbers are allocated in a **transaction of their own**, committed before the placement transaction
opens — `AllocateOrderNumberAsync` throws if a transaction is already active, because enlisting would
hold the series row for the length of every stock reservation in the order and every other checkout in
the shop would queue behind it. Gaps are allowed and expected.

**It is not #53's step 3's.** Invoice numbers are, and they are the opposite trade: doc 08 allocates
them *inside* the Paid transaction so the series is gapless. `AllocateAsync` is the shared primitive and
enlists in an ambient transaction, so step 3 calls it and gets the gapless behaviour for free. Nothing
here allocates from `INVOICE-2026`.

Raw ADO rather than EF, because the value is in the statement's `OUTPUT`: `ExecuteSqlInterpolated`
returns a row count and discards it, and `SqlQuery` composes the SQL into a subquery, which an `UPDATE`
cannot be.

### Price freezing — one read, named in the code

The bag reprices on every read, deliberately. An order line must never be repriced. The hand-off is
`ICheckoutReader.ReadCartAsync`: **one** read, inside the placement use case, whose three prices go
verbatim into `sales.OrderLines`. `CartItems.UnitPriceAtAdd` is not read at all, here or downstream.
`CheckoutReader`'s class docblock says this; `CheckoutCartLine`'s says it again from the contract side.

Doc 08 §5.4 puts the pricing *before* the transaction, which is what we do — so the commercial guarantee
is not "the catalogue cannot move", it is **G-10**: the request carries the total the shopper was shown,
and the order is refused if the freshly priced total differs. An order is never placed at a figure the
customer has not seen. `A_price_change_after_placement_does_not_move_the_order` proves the other half:
raising the product's price afterwards moves nothing on the order or the confirmation.

### Stock — refuse, never silently drop

Doc 08 §5.2's conditional UPDATE, in `VariantId` order (§5.3), row count checked per line; any 0-row
result rolls the **whole** transaction back and reports the available quantity per line. Two answers are
both correct and the suite asserts either: if the winner's commit lands before the loser's bag re-read,
the loser gets G-08's `LineNotPurchasable` ("adjust your bag"); if it lands in the window between that
read and the reserving UPDATE, it gets §5.4 step 3's `OUT_OF_STOCK` with the shortfall. Demanding only
the second made the race test fail on round 2 of 20 — correctly, and the comment in the test now explains
why.

**What is owed:** `inventory.InventoryMovements` does not exist. Doc 08 §5.1 wants a movement row for
every stock change; §3.4 attributes the table to ADM-12/ADM-19 (**W1-05, TODO**), so this task does not
create another task's ledger. Reconciliation is unaffected — §5.9 compares `StockLevels.Reserved` with
`Σ OrderLines.Quantity` over orders in `StockState = 0`, which reads the order lines, not the ledger, and
there is a test for exactly that aggregate. What is lost is the per-movement audit trail.

### Idempotency — server-issued, unique index, double-submit tested

`GET /api/checkout` issues a fresh `checkoutKey`; the POST must present it;
`UX_Orders_CheckoutIdempotencyKey` is the mechanism. The use case checks for a replay **first**, before
anything else, because a successful placement empties the bag and a later replay would otherwise be told
its bag was empty. A genuinely simultaneous double submit is caught by the index: the loser's insert
fails, its reservation is rolled back, and the first order is returned with **200** rather than 201.

Four simultaneous submissions of one cart, fifteen rounds: one order, one reservation, three replays —
every time.

The storefront pins the key at the **first** read and ignores the ones later re-quotes bring back.
Without that, changing the district rotated the token and a shopper who changed district and then
double-clicked would have placed two orders. There is a unit test named after it.

### Guest checkout — it is the only checkout there is

There is **no customer authentication anywhere in this repository** (ACC-01 is W3-01, unbuilt), so
`CartLookup` can only ever arrive carrying a guest token and *every* checkout is a guest checkout. I did
not build a signed-in path I cannot exercise: no sign-in step, no saved addresses, no "create an
account" box. `PlaceOrderCommand.CustomerUserId` is an `init` property W3-01 sets in the endpoint, and
it is the only difference between the two — the order's `CustomerUserId`, and therefore whether it
appears in an order history. The guest's order link is `Orders.PublicId`, as doc 08 specifies.

### Delivery fees — built from doc 08 §9, and nothing invented

This is the part the brief was most careful about, so here is exactly what happened.

**`ref.Provinces` and `ref.Districts` did not exist and I created them.** Doc 08 §3.1 heads both tables
"GLB-06, **CHK-01**", `sales.Orders.DeliveryDistrictId` is `NOT NULL`, and `Orders.DeliveryZone` is
derived from the district — so no order row can be written at all until those 25 rows exist. W3-03's
journal (decision 1) left the column indexed and unconstrained *so that whichever task created the table
would add the constraint*, and its `SalesSchemaTests` asserted the absence to force the issue. That test
failed on this branch, which is the guard working; it is now narrowed to the two columns still waiting on
`marketing`, and a new test asserts both district FKs exist, point at `ref.Districts.Id`, and are
`NO ACTION`.

**No figure on any screen is this task's invention.** Every value in `SalesReferenceData` is quoted from
doc 08 §9: the nine provinces, the 25 districts with §9's initial zones, the three delivery methods, the
nine zone rates (Colombo Standard Rs. 400 free above Rs. 10,000 in 1–2 days; Express Rs. 950; Western
Rs. 450/Rs. 1,200; island-wide Standard Rs. 600 free above Rs. 15,000, **Express unavailable**), and the
two payment providers. `SalesReferenceDataTests` asserts all of it, read from the document first and only
then checked against the database.

**They are placeholders and they are flagged as such (D8).** The client has not confirmed the zone map or
the fees. The seeder is the idempotent insert-what-is-missing kind (N13), so the first thing the client
changes is never overwritten, and there is a test that edits a zone, a fee and an on/off switch, runs the
seeder again, and asserts all three survive.

**Store pickup ships switched off**, because §9 also seeds **zero** pickup locations (client input, D8)
and doc 11 P6 requires at least one. An enabled method with nowhere to collect from is an option that
fails after the shopper has chosen it. The pickup branch is written and reachable the moment a location
exists and the method is enabled — R7's "a pickup order's district is the location's" is implemented and
`CK_Orders_Pickup` is satisfied — but nothing in this task puts a shop address on a live page.

**The bag still says "calculated at checkout", and that sentence is now true rather than merely
unfalsifiable.** What the bag lacks is a *district to price for*: `Carts.DistrictId` is not in the schema
(W2-09 left it out), GLB-06's header district selector is unbuilt (#33), and doc 08 §3.5 R7's two
fallbacks are both unreachable — no customer sign-in and no `ops.Settings`. So the bag prints the three
item figures and checkout works the delivery out, with the same labels.

### The totals add up, and the test reads them off the screen

`OrderPricing` in the Domain is doc 08 §6 steps 5–12 as one pure function, called from exactly two
places: the quote and the placement. The ladder is the bag's, settled after the bag shipped a summary
whose subtraction was false — **Subtotal** is the original ("was") total, the deduction row is
**Savings**, **Total** is the net figure, and delivery is added between them:

```
Subtotal − Savings − Discount + Delivery − Free delivery = Total
```

Three tests put that identity through figures **read back out of the rendered DOM** — in jsdom on the
checkout page, in jsdom on the order page, and in a real browser at a real viewport — rather than
asserting that three strings appear somewhere. `data-sum` attributes key the helper, not the label text,
so improving the wording cannot break the arithmetic test.

`ItemsSubtotal = Σ LineSubtotal` is the cross-row invariant W3-03's review flagged as resting entirely on
the code that writes the lines. `The_order_s_totals_add_up_in_the_database` places a three-line order and
reads every figure back out of `sales.Orders` and `sales.OrderLines`, asserting that sum plus all four
`CK_Orders_Totals` equalities and all three per-line ones.

**`DeliveryFeeAmount` and `GrandTotal` are `null`, not zero, until a district and a method are chosen.**
Doc 08 §6 step 10 has no fee without a zone, and a Delivery row reading `Rs. 0` would be a promise of free
delivery. `OrderPricing.Price` *throws* if asked to price without a rate rather than defaulting to zero.

The promo code is not built (ADM-13), so steps 7 and 8 are deliberately absent — but step 9's pro-rata
allocation and step 11's **Rs. 1.00 minimum-total clamp (G-11)** are implemented and unit-tested,
including doc 08 §6's worked example to the cent and the clamp re-running the allocation. W3-05 changes
one argument.

### Issue #47 — every string on the request is nullable

A well-formed JSON object omitting a required `string` binds `null` into a non-nullable reference
property, and the first dereference used to return 500. A checkout body is almost all strings, so the
request record and `CheckoutAddressInput` are nullable throughout, the record itself is `[FromBody]
PlaceOrderRequest?`, and `PlaceOrderValidator` reports every missing field at once. Seven body shapes are
integration-tested against the live endpoint including `{}` and `{"email":"a@b.c"}`, sent as **raw
bytes** because a typed helper cannot omit a property.

### Where this stops

The order is `PendingPayment` with one open `Pending` bank payment — doc 08 §4.1 lists that payment row
as a side effect of placement, and doc 11 P7's preconditions require it, so an order without it is one
the bank-transfer flow could not pick up and `UX_Payments_OneOpen` would stop it creating later. That is
the whole of the money. **Not here:** bank details, the reference to quote, the slip upload, the approval
queue, rejection, expiry, invoice numbers, PayPal, emails. `BuildPayment` is the one provider-specific
place and names PAY-03 as what replaces it.

### The concurrency proofs

Every one is replayed many times, and every one was proved **red** by removing the mechanism it guards.

| Race | Rounds | Invariant | Mutation that makes it red |
|---|---|---|---|
| Four shoppers, one unit, over HTTP | 20 × 4 | exactly 1 order, `Reserved = 1`, every loser told the stock went | drop `AND OnHand - Reserved >= @q` from the reserve UPDATE → `Assert.Equal() Failure: Values differ` |
| Four simultaneous submissions of one cart | 15 × 4 | 1 order, 1 reservation, 3 × 200 naming it | regenerate the key per attempt and disable the pre-check → red on both this and the sequential test |
| 32 simultaneous allocations from one series | 10 × 32 | 32 distinct values, exactly 1..32, `NextValue = 33` | split the allocator into `SELECT` then `UPDATE` → red in 27 ms |
| 32 callers racing the lazy series insert | 10 × 32 | one row, every loser recovers, values 1..32 | same mutation → red |
| Six concurrent checkouts of six variants | 8 × 6 | all succeed, six distinct order numbers | — (guards against deadlocks and number collisions) |
| §5.9 reconciliation after the rounds | — | `Reserved` = Σ lines of orders in `StockState = 0` | — |

Each mutation was applied, the test observed red, the file restored and `diff`-ed byte-identical against
the pre-mutation copy.

### Red-before / green-after on a real production bug

**The SSR cookie interceptor did not know about checkout.** `cartCookieInterceptor` forwards `sd_cart`
only for `/api/cart`, so a server-rendered `/checkout` saw an empty bag: the HTML said *"your bag is
empty"* and the page filled itself in after hydration — precisely the failure the interceptor's own
docblock says SSR exists to avoid.

Found by `checkout.e2e.ts` reading the server's HTML. Then written as a unit test first:

- **Red:** 4 failed, 1 passed — `expected null to be 'sd_cart=8e29b4c6-…'` for `/api/checkout`,
  `/api/checkout?districtId=1&deliveryMethodId=2`, `/api/checkout/orders` and the absolute form; the
  `/api/orders/{token}` case passed, because that call must **not** carry the cookie.
- **Green:** 5 passed after extending the predicate to `/api/checkout`.

`/api/orders/{token}` is deliberately excluded: an order is found by the unguessable token in its own
URL, so a guest opening their link in another browser must get the same answer.

### Six defects in my own tests, all found by running the full suite

Worth recording, because every one of them is the shape the project keeps finding.

1. **Three assertions were absolute where they had to be relative.** "No order placed in the last
   minute", "`Reserved == 0`", "`Assert.Single(PaymentMethods)`" — the assembly shares one database,
   orders are never deleted, and `SalesSchemaTestBase` inserts reference rows of its own. 28, then 13,
   then 2 tests went red in a full run and green alone. All now take a before-figure or filter to the
   seeded codes.
2. **My suite took stock and never gave it back**, on the same low-id variants
   `InStockVariantIdsAsync` hands everybody — so `CartStaleItemTests.WithStockAsync`, which sets `OnHand`
   alone to figures as low as 0, either violated `CK_StockLevels_ReservedLeOnHand` or silently changed the
   `Available` it was measuring. Two attempts at a cleverer restore did not fix it; the fix is
   `CheckoutVariantIdsAsync`, which takes variants from the **high** end of the catalogue so the fixture
   is not shared at all.
3. **A test polluted the seeded catalogue.** `A_price_change_after_placement` raised a product's
   `BasePrice` and walked away, so the next test priced differently. Restored in a `finally`.
4. **One case could not be sent at all.** `%00` as an order token throws in `TestServer`'s own path
   decoder before anything reaches the server — the W2-10 `//robots.txt` lesson exactly. Removed, with the
   reason and what is owed (a client that puts the bytes on the wire).
5. **A focus-ring assertion measured the wrong element**, and a button cannot be tested with `.focus()`.
   The radio's ring is painted on its row by `:has(:focus-visible)`, so `edgesWithoutRing` gained a
   `ringAround` parameter rather than a second copy; and Chrome does not grant `:focus-visible` to a
   button on a programmatic focus, so Place order is reached with Tab.
6. **Three Playwright waiters were armed after the event they waited for.** A response that lands before
   `waitForResponse` is registered is one the waiter never sees — a timeout that says nothing.

### And one in my own design

The order page had a "this order was already placed" notice driven by `isDuplicateSubmission`. That flag
describes a *submission*, not an order, so `GET /api/orders/{token}` answers `false` for every order
including a replayed one — correctly. The page reads the order back by its token, which is what lets it
survive a reload, so the notice **could never render**. `checkout.e2e.ts` found it unreachable. Removed,
with a test pinning the decision so it is not added back; the signal that matters is the API's 200 rather
than 201, and that is asserted.

## Things in the brief, or in the documents, that are wrong

1. **The brief says to read "`docs/11-*` P7 (place an order)".** P7 is *Payment by bank transfer* —
   explicitly #53's work and out of my scope. **P6 is Checkout**, and that is what this task is built
   against. I read P7 anyway, for the boundary.
2. **The brief says the bag "excludes [short-stock items] from its subtotal".** It does not, and should
   not: `CartReader.Totals` and the storefront's `isBuyable` both count a `NotEnoughStock` line **in** the
   subtotal at the quantity the shopper chose — the price is real and the stock may return. Only
   `OutOfStock` and `Unavailable` are excluded. Checkout follows the same rule for the summary (so the two
   pages cannot print different subtotals) and a **stricter** one for placement: every line must be
   `Buyable`. That distinction is why the bag has two different counts and two different messages.
3. **The brief says to "build what can honestly be built from seeded data".** There was **no seeded
   data** — doc 08 §9 specifies provinces, districts, delivery methods, zone rates and payment providers,
   and W3-03's journal records that it deliberately seeded none of it ("the admin milestones own the
   seeders"). Checkout cannot exist without any of them, so this task seeds all five from §9. That is the
   single largest thing in this branch that the brief did not anticipate.
4. **Doc 08 §1.3 and §3.5 still contradict each other** about `PaymentProviders.Code` being a PK (W3-03's
   tester found it; unresolved). Not touched.
5. **Doc 08 and doc 11 are silent on whether placement empties the bag.** I empty the items and keep the
   `Carts` row, so the cookie stays valid and the badge reads 0. Leaving them would mean a shopper
   returning to a bag full of things they had just bought, with the obvious next action placing a second
   order. Recorded as a decision rather than an inference.
6. **Doc 11 §7 G-31** (the Terms sentence at checkout, no stored flag) is implemented as the sentence
   only. It does **not** link to `/terms`, because GLB-10's content pages are unpublished and a link to an
   empty page is worse than none.
