### Where the live database gets it

The VPS path is: `deploy/scripts/install.sh <env>` copies `tools/db/provision-database.sql` to
`/opt/server/database/<env>/scripts/`, then `deploy/scripts/db-provision.sh <env>` pipes that copy (with a
`:setvar DbName` line taken from `SD_APP_DB_CONNECTION`) to `sqlcmd` as `sa` inside the SQL Server container
(docs/15 §5 step 3). So: **run `install.sh` from this commit before `db-provision.sh`**, or the old copy runs.
`deploy/database/compose.yml` only sets the server collation (`MSSQL_COLLATION`); it creates no database.

### Existing databases (SpencerDenim_Dev, anything provisioned before #163)

Not touched by me. Check: `SELECT name, is_read_committed_snapshot_on FROM sys.databases WHERE name = N'SpencerDenim_Dev';`.
To switch on: stop the API and close every other connection, then
`sqlcmd -S "(localdb)\MSSQLLocalDB" -E -v DbName="SpencerDenim_Dev" -i tools\db\provision-database.sql`,
or at a quiet moment `ALTER DATABASE [SpencerDenim_Dev] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;`.

Measured on a throwaway LocalDB database: with **one idle** other connection, `… WITH NO_WAIT` fails
(5070, "Database state cannot be changed while other users are using the database"); a plain `ALTER` with
no termination clause waits indefinitely and ignores `SET LOCK_TIMEOUT`.

### What RCSI does not close

With RCSI on, an **active customer** still answers slower at p90 under this load: forgot-password 2.0–3.8x
the fastest other path, wrong password 1.2–2.1x (six runs). Those paths write (a token and an outbox row in
one transaction; a failure count). The likely cause is that work outlasting the 250 ms floor at 24-way
load, i.e. W3-01's oracle with its sign flipped — **inferred, not traced**. No read is waiting on a writer
(`ReadCommittedSnapshotTests` shows the lookups do not wait). **Needs its own issue**; the test asserts the
#163 direction only and says why.

## Read → decide → write sweep

Measured first, because the sweep turned on it: on an RCSI database, an `UPDATE` that **waits** on its
target row and then evaluates `EXISTS`/`NOT EXISTS` over **another** table saw that table's committed state
(three shapes: subquery in `SET`, in `WHERE`, writer touching the other table before or after the target).
So the order-claim shape (`UPDATE sales.Orders … WHERE Status = … AND NOT EXISTS (SELECT … FROM
sales.Payments …)`) behaves as before **when the writer holds the order row**. I did not establish why
(statement restart or a lazily taken read point); the result is the evidence.

| Site | Guard | Verdict |
|---|---|---|
| Stock reserve/deduct/release (`OrderPlacementStore`, `OrderSettlementEffects`, `OrderStockRelease`) | conditional `UPDATE` + row count, CHECK constraints | Unaffected |
| Promo per-customer limit (`OrderPromoUse`) | `sp_getapplock` Exclusive/Transaction, then the count in a later statement | Unaffected: each statement gets its own snapshot, taken after the lock is granted |
| Payment settlement claim (`OrderSettlementEffects.ClaimPendingOrderPaidAsync`, bank approve/reject/accept-late) | conditional `UPDATE` on the order row + `NOT EXISTS` settlement; `UX_Payments_OneSettlement` | Unaffected (probe above) |
| Guest-order linking D5 (`LinkGuestOrdersAsync`) | conditional `ExecuteUpdate … CustomerUserId IS NULL` + count check | Safe. An order whose placement is still in flight is not linked (it was waited for before) |
| Customer lockout (`CustomerAccountLockout`) | two conditional `UPDATE`s on `AccessFailedCount` | Unaffected |
| Staff lockout / 2FA (Identity's read-modify-write) | none | Already lossy (documented in `CustomerAccountLockout`); RCSI removes the remaining S-lock waits — not made worse in kind |
| Email outbox claim | `ROWLOCK, READPAST, UPDLOCK` | Locking read; unaffected. Full suite + `PooledIsolationLeakTests` |
| Payment-event claim / record | `UPDLOCK, READPAST`; `UPDLOCK, HOLDLOCK` | Unaffected |
| Campaign recompute | `READCOMMITTEDLOCK` | **Now load-bearing**, proven by test. One unhinted reference added (the mixed-snapshot outcome it could allow was **not reproduced**) |
| `CartStore` merge | `SERIALIZABLE` | Unaffected; pool reset still proven |
| Customer registration | `UX_Users_NormalizedEmail` + duplicate handling → `LostTheRaceAsync` | Safe; classify says "Nobody" more often during a twin registration, the race path handles it |
| Address cap, RBAC last-Super-Admin | `sp_getapplock` before the reads | Unaffected |
| Number series | atomic `UPDATE … OUTPUT` | Unaffected |
| Rowversioned admin edits | `WHERE RowVersion = @orig` | Unaffected |
| `BankTransferProofStore.OpenPaymentAsync` | plain read of order status, then insert | **Changed by RCSI → fixed** with `READCOMMITTEDLOCK`; test. The pre-existing race (expiry starting after the read) remains — needs an order-row claim, outside #163 |
| `PayPalPaymentStore.OpenAttemptInTransactionAsync` `AnyAsync(CapturedRequiresRefund)` | relies on settlement routing taking the order row first | **Not fixed, latent** (PayPal disabled). `RecordExceptionAsync` does not always touch the order row, so under RCSI this read no longer waits for an in-flight routing. For the PayPal owner |
| `PayPalPaymentStore.RecordDeclinedAsync` `EXISTS` in the order `UPDATE` | waits on the order row | Probe says the `EXISTS` sees committed state after the wait. Not changed |
| Media delete vs attach, category removal link counts, dead-email alert dedupe, bank proof replacement, promo count vs late acceptance | none / unique index | Pre-existing races, window widened from "read to write" to "the other transaction's length". None RCSI-specific |

## A test that could not fail, caught by the RCSI-off comparison run

The first `ConcurrentAccountTimingTests` used the shared fixture database. It failed every time it ran
alone with RCSI off — and **passed** in the full-suite RCSI-off run, because by then the suite has
registered hundreds of users, the lookups seek, and nothing blocks (#163's own "at 500 users it seeks").
It now runs on a `FreshDeployment` database (`e6e3940`), and with RCSI off it fails even when run after
every other `Api.Accounts` test. The figures in the table above were taken on the shared database but
alone (the users table small); the fresh-database runs (one each) agree (on: sign-in p90 350–442 ms across paths, 0
errors; off: unknown/staff/deactivated p90 2,201–4,882 ms, 23 requests answering 500).

`CampaignPricingRefreshLockTests` and the new `OpenPaymentIndexTests` case **pass with RCSI off** — with
locking reads everything waits anyway. They guard the hints, which only matter with RCSI on;
`ReadCommittedSnapshotTests` is what fails if the option goes.
