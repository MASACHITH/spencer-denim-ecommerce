## 1. Recording

### Where it happens, and why exactly one side records each view

The storefront renders the first request on the server and navigates in the browser after that, so neither
side can record alone: the server never sees a click, and the browser alone misses visitors without
JavaScript and every crawler (doc 08 counts bots: `TrafficDaily.BotPageViews`) and would double-count against
the server. So:

1. `server.ts` decides **before** the render whether the request is recordable (a GET that is not a prefetch or
   prerender) and passes a `TrafficRenderContext` to `angularApp.handle(req, context)`.
2. A server-only app initializer (`markServerPageView`) marks the context *rendered* and, when recordable,
   leaves `SERVER_PAGE_VIEW` in the **transfer state** — a flag that travels inside the HTML.
3. After the render, `server.ts` records **only** a recordable request the render actually ran for and answered
   **200 `text/html`** — so a 404, a 503 or a redirect is not a page view — sets the `sd_vs` cookie on the page,
   and posts the view to the API **after** handing the page over, never awaited, 2 s timeout, every error
   swallowed. The visitor's user agent goes in the body (the process's own header is Node's). No address is sent.
4. In the browser, `PageViewTracker` skips the first navigation **iff the flag is in the page**, and records each
   later `NavigationEnd` **whose path changed** — a filter, sort, "Load more" or fragment on the same listing is
   one page being used, not a new view. Routes marked `NOT_A_PAGE_VIEW` (the catch-all and every 404/503 route)
   are never recorded. A page the browser is prerendering is recorded when shown.

"The server recorded it" and "the browser skips it" are therefore one fact carried in the page, not two guesses.
If the engine falls back to the client-side shell, the render never ran, so the server does not record and the
page carries no flag — the browser records it instead.

**One visit = exactly one row**, proved in three layers:
- `e2e/traffic.e2e.ts` (real SSR server, real browser, stub API): one server-rendered page is one recording
  request (from the server); a click is exactly one more (from the browser); a sort change is none; a reload is
  one; a 404 is none; the cookie the server sets is the one the browser's beacon carries. Each test owns its own
  `sd_vs` session, because the stub is shared.
- `PageViewRecordingTests` (real API, SQL Server): one beacon is exactly one row.
- A manual run against the **real** API and the real SSR server (see "End to end, for real" below).

### The API side

`POST /api/traffic/page-views` (anonymous, always `204`) classifies in memory (`PageViewClassifier`) and calls
`IPageViewRecorder.TryRecord`, which is `ChannelWriter.TryWrite` on a **bounded** channel
(`Traffic:QueueCapacity`, 10,000) — it never waits: full means the view is dropped and counted, and the queue
cannot grow. `PageViewWriterService` writes every 5 s or as soon as 200 rows are queued (doc 08 §3.8), resolving
product, category, department and content-page slugs in at most four small reads per batch. A failed write
drops its batch, logs once at Error and then at Warning, and recording carries on. On stop it drains for up to
5 s. Tests drain it deterministically with `PageViewWriterService.FlushAsync`, which is serialised with the
background cycle by one lock.

`IX_PageViews_Occurred INCLUDE (SessionId, IsBot, Channel, DeviceType)` and `DATA_COMPRESSION = PAGE` on the
table and the index are exactly doc 08 §3.8's (compression is raw SQL in the migration; read back from
`sys.partitions` in `AnalyticsSchemaTests`).

### No IP, no visitor ID, no secret URL

- **No IP anywhere.** No type on the path has a field for one (`TrafficClassifierTests` reflects over
  `PageView`, `PageViewSubmission`, `TrafficDaily`, `PageDaily`; `AnalyticsSchemaTests` checks the columns).
  The endpoint never reads `RemoteIpAddress` or `X-Forwarded-For`; the SSR server never forwards them. The
  beacon's request log line is `Debug` (one Information line per page view would be a second, unretained copy
  of the table) and carries the route, never the page address, which is in the body.
- **No persistent visitor ID.** `sd_vs` is a random GUID, HttpOnly, Secure, SameSite=Lax, **`Max-Age=1800`,
  re-issued on every view** — thirty idle minutes end a visit. A literal "session cookie" (no expiry) would be
  *more* persistent: browsers that restore tabs keep those for weeks.
- **No secret from a URL.** `PagePath` keeps a path segment only if it is a catalogue slug that is not a GUID and
  has no run of seven digits; anything else is `*`. `/order/…` is always `/order/*`. The query string keeps only
  the listing's filter and sort keys (`ageGroups colours fits inStock materials maxPrice minDiscountPercent
  minPrice minRating newArrivals occasions onSale sizes sort`) on listing and search pages, each value checked for
  its shape — so `?q=`, `?token=`, `?email=`, `?returnTo=`, `?paypal=`, `?PayerID=`, `?pages=`, click ids and
  fragments are all dropped. UTM values that look like an email or a phone number are dropped (a personalising
  mail tool puts one there). Only the referrer's **host** is kept, never its path or query.
- **The test:** `No_secret_from_an_address_and_no_ip_address_is_stored_or_logged` posts twelve secret-bearing
  addresses (order token, PayPal return token and payer id, reset and confirmation tokens, email and phone in the
  path, the query, the filters and the UTM tags, a fragment) with an IP in `X-Forwarded-For`, `X-Real-IP` and
  `Forwarded` and a referrer full of PII, then searches **every string column of every analytics table** and
  **every log event the host wrote at every level** for each secret. m04 (store the forwarded IP as the
  referrer) and m05 (log it) were both killed by it.

### Bots

`UserAgentClassifier.IsBot`: no user agent, one under 20 characters, a bare `Mozilla/5.0`, a crawler / preview /
monitor / HTTP-library pattern (`bot`, `crawl`, `spider`, `facebookexternalhit`, `WhatsApp`, `preview`,
`HeadlessChrome`, `Lighthouse`, `curl`, `python`, `GPTBot`, …), or a browser reporting `navigator.webdriver`
(which the beacon passes on — that is how Playwright, Selenium and Puppeteer are caught). In-app browsers
(Facebook, Instagram, TikTok), DuckDuckGo and Yandex browsers are people. Bot rows are recorded with
`IsBot = 1` (doc 08 counts and keeps them) and are in no visitor figure. A bot that fakes a browser user agent
and no automation flag counts as a person: without the IP there is no telling, which is doc 08's trade.

## 2. Aggregation

`TrafficRollup.RebuildAsync(from, to)`: one transaction, `sp_getapplock` exclusive first, `DELETE` the days from
both tables, `INSERT … SELECT` from `TrafficSql`. **Colombo days** throughout (`DATEADD(minute, 330, …)`; range
on the raw UTC column). **Each session's human views are credited to its first view of the day** (channel,
device, source) — the raw row of a click inside the shop is Direct, so without this "arrived from Google, then
six clicks" would be one Organic and six Direct. Bots go to `BotPageViews` only. Sources: UTM source, else
referrer host, else `(direct)` / `(not set)`; beyond the day's top 50 by sessions, `(other)`.

`TrafficRollupService`: 00:30 Colombo nightly and once a minute after start-up; rebuilds the last three
completed days and **builds any older day within raw retention that has views and no rows** (the host was down).
Today is never stored. `ops.JobLeases` does not exist, so there is no "last completion" to read; the rebuild is
idempotent and locked instead.

**Retention:** `TrafficRetentionService` at 01:30 purges raw rows older than 90 Colombo days and bot rows older
than 7, in `DELETE TOP (4000)` loops time-boxed to 10 minutes (doc 08 §8.4). The daily tables are kept. Both
periods are configuration (`Traffic__RawRetentionDays`, `Traffic__BotRetentionDays`, validated ≥ 4 because the
rollup rebuilds three days) — **not `ops.Settings`**: the settings screen has a form per group and no Traffic
form, so a seeded row would be a value staff can see and not change. The keys stay in `DeferredSettingKeys`
with the reason updated, and `SettingKeySpecificationTests` now pins both code defaults against doc 08's cells.
**Owed:** the Traffic settings form, and doc 08's whole `Retention` job for every other table (audit logs,
outbox bodies, carts, IP columns, media, alerts) — only traffic is purged.

Both jobs stand down when `Traffic:JobsEnabled=false`, which `ApiFactory` sets for every test host; the tests run
one pass directly as of a chosen day.

## End to end, for real

Not a test in the suite — a one-off run of the whole chain with nothing stubbed, to answer "one real visit,
how many rows" against the real thing. A throwaway database (`SpencerDenim_W403Visit`, created, migrated with
`dotnet ef database update`, seeded with the demo catalogue by the API, dropped afterwards); the real API
(`Traffic__FlushSeconds=1`) on port 6320; the built SSR server on 6321 with `API_INTERNAL_URL` pointing at it;
headless Chromium with the browser's `/api` calls routed to the API as the gateway would. Five steps, one visit:

| Step | Who should record | Row |
|---|---|---|
| open `/` | the server | `1  /                    Home        Direct  Desktop  IsBot=1` |
| click *Women* in the header | the browser | `2  /women               Department  Direct  Desktop  IsBot=1` |
| change the sort | nobody (same page) | — |
| reload `/women?sort=newest` | the server | `3  /women?sort=newest   Department  Direct  Desktop  IsBot=1` |
| open `/no-such-page-w403` (404) | nobody | — |

**Three rows, all with the one session the server's cookie gave the browser, and three rows in the whole
database.** `IsBot = 1` because the browser was automated (`navigator.webdriver`, HeadlessChrome) — the bot rule
working, not a fault. The API's log mentioned the beacon route twelve times and the session id and page
addresses never.

## Corrections and open questions

**Corrections to the brief**

1. **"`origin/main` is `fdb480a`."** It was `6ecee99` when the worktree was cut (#170 and #176 had landed), and
   main moved again during the day (#142, #144, #146, #165), which is merged in. None carried a migration.
2. **"Batched insert … every 5 s or 200 rows" — "a full channel must drop".** Agreed and built; one nuance worth
   knowing: under EF's retry-on-failure a *slow* database holds a batch for the retry window, during which the
   queue keeps filling up to its bound and then drops. Pages are never affected; views can be.
3. **"`SessionId` (session cookie)".** Built as a 30-minute sliding `Max-Age` cookie, deliberately not a
   browser-session cookie: with "continue where you left off" a session cookie lives for weeks, which is the
   persistent identifier doc 08 rules out. Owner to confirm the reading.
4. **"Seed `Traffic.RawRetentionDays` and `BotRetentionDays` now?"** Not seeded, and I think the brief's premise
   needs one more fact: the settings screen is a set of hand-built forms, one per group, with no generic editor,
   so a seeded key is visible to nobody who can change it. The purge runs on doc 08's defaults from
   configuration instead; seeding belongs with a Traffic settings form (owed).
5. **"The nightly `Retention` job does not exist."** Still true for every table but `analytics.PageViews`; only the
   traffic purge is built. Doc 08 §3.8's `NightlyStats` is also only half built: the traffic rollup is here,
   `ProductStats` (30-day units, drift) is not.
6. **"A filtered or covering index needs a plan test that forces the index … and asserts it compiles."** For a
   *covering* index forcing always compiles — a forced non-covering index is still usable, with a Key Lookup. The
   plan test therefore forces the index and asserts **no lookup**, with a control that shows one.
7. **"Write backend endpoint tests for every route"** — done for all three routes; the brief's "#174 deliberately
   left the widget out" is right, and two W4-02 tests asserted its absence (Vitest and Playwright); both are
   replaced, not deleted.
8. **Running alongside the RCSI agent.** `sd-rcsi` was running its integration suite while my mutation runs (one
   filtered class at a time) were going; every kill above is a named assertion on the mutated behaviour, but if
   the tester sees a different count on a mutation, a collision is the first suspect.

**Open questions for the owner**

1. **The dashboard widget needs `Traffic.View`** (P16: Order Staff "see the dashboard but not … Traffic"). If
   the widget was meant for everyone with `Dashboard.View`, it is one permission on one route.
2. **Cookie consent.** `sd_vs` is an analytics cookie with no personal data; there is no consent banner in scope
   (doc 02). Worth a line with the client's PDPA review of the privacy page.
3. **The gateway's access log** (`deploy/gateway/nginx.conf`, `sd_json`) records `remote_addr` and the full
   `request_uri` — `/order/{token}` and `?token=` included — for every request. That is ops logging, not traffic
   recording, and was not changed here; but "no IP, no secret URL" holds for `analytics.*` and the API's logs,
   not for the gateway's stdout. Retention of those container logs is a deployment decision.
4. **A future CDN or HTML cache** in front of the SSR server would serve pages that never reach it: server-side
   recording would undercount and the cached page's flag would stop the browser recording too. Today nothing
   caches HTML (no `proxy_cache`). If one is added, recording should move to "browser always, server only when
   no JavaScript" — and a cached page must not carry someone's `Set-Cookie`.
5. **Today's dashboard KPIs** do not include visits; conversion sits in the traffic widget beside the visits it
   divides by, not on a KPI card. Say if a card was wanted.
6. **Beacon abuse.** The endpoint is public and unthrottled (the SSR server's calls all come from one address, so
   an address-based throttle would throttle every first page). A flood can inflate figures but not memory (the
   queue drops). Rate-limiting per visitor would need a decision.
