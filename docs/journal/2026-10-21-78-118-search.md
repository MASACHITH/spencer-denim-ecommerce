## 1. #118: root cause

**It was never about 768 px, and it was a real defect.** `SiteHeader` closed every panel (search, menu, bag) on
each `NavigationEnd`. On a server-rendered load the header is hydrated and clickable **before** the router's first
navigation has ended (that navigation waits for the lazy route chunks). A shopper who opened the search panel in
that window had it shut by the *first* navigation's end: the panel took `hidden`, the field lost focus, the popup
closed on `focusout`, and the rest of the typing went nowhere — "the element is never found", exactly as reported.
768 px was simply the only width the suite drove the **panel** at (every other suggestion test uses the results
page's box or the inline box from 1280 px, which no navigation closes).

**Measured on `a3490d3`** (the tree #118 was reported on), with a MutationObserver/replaceState log in a scratch
spec, on a cold server:

| t | event |
|---|---|
| 815 ms | click on the search toggle (hydrated), panel `hidden=false` |
| 915–945 ms | first keystrokes |
| 936 ms | `history.replaceState` — the first navigation ends |
| 994 ms | panel `hidden=true` |
| 1019 ms | `focusout` on the input; one suggestion request, for "je" |

Serially (`--workers=1`) it reproduced 1 run in 3 cold, 0 in 12 warm — a window, not contention (#115). Holding the
lazy route chunks back until the shopper has typed made it deterministic: **5 of 5 failing on `a3490d3`**, **5 of 5
passing on `a3490d3` + W3-01's `event.id > 1`**. So W3-01 (`f5af9c1`) fixed it for `/` — which is why it "stopped
reproducing" on main — but not for a first page whose guard redirects: on current main **`/account` (signed out)
still failed 3 of 3**, because navigation 1 is cancelled by `signedInGuard` and navigation 2 is the first to succeed.

**Fix** (`site-header.ts`): close panels only on a navigation **away** — one whose router `Navigation` has a
`previousNavigation` (`isNavigationAway(router.lastSuccessfulNavigation())`; `lastSuccessfulNavigation` is set just
before `NavigationEnd` is emitted, verified in the router source). No retries, no longer timeouts.

**Tests:** unit — the redirected-first-navigation case (fails on `event.id > 1`, verified) and the predicate; e2e —
`a search box opened during start-up keeps its suggestions (#118)`: `/` and `/account` × all 8 widths, route chunks
held back by a gate released only after suggestions are on screen, then asserts the panel/inline box is still
visible, focused, expanded and listing. **85 of 85** under `--repeat-each=5` at default workers (the 16 tests + "one
Escape" × 5), while a mutation run was building in the background.

## 2. #78: what was built

**Recording (doc 08 DB25).** The results page sends `POST /api/search/submissions {term, automated}` once per term
it shows (the term effect; filters, sort and Load More do not change the term; the server render sends nothing, so
SSR + hydration is one count). Keystrokes never count. The API: no IP, no user, no session, no cookie issued;
`204` whatever happened; request log at Debug like the page-view beacon.

- **Privacy rule** (`SearchQueryText`, Application): the storefront's corrected `isPrivate` inherited as #78 requires
  — any at-sign (`@`, `＠`, `﹫`), **≥ 7 decimal digits anywhere** (by code point, any script) — plus order/invoice
  number shapes (`SD-2026-…`, `INV-2026-…`, partials). Normalised as `normaliseTerm` + lower-case, 100 chars, never
  through a surrogate pair. The browser applies the same rule before sending, so the server's is the second line.
- **Bot filter:** `UserAgentClassifier.IsBot(userAgent, navigator.webdriver)` — #180's rule. Bots are not counted at
  all (no bot column in DB25).
- **Buffer + flush** (`SearchQueryBuffer`, `SearchQueryWriterService`): a count per (Colombo day, term), bounded
  (`SearchStats:MaxBufferedTerms`, 5000; full = existing terms still count, new dropped, warned once a minute),
  flushed every 60 s; failed flush drops and logs once; deterministic `FlushAsync`; 5 s drain on stop.
- **Upsert** (`SearchQueryStore.UpsertSql`): DB25 exactly — `UPDATE … += @n`; if 0 rows `INSERT`; on 2627/2601 retry
  the `UPDATE`, inside `TRY…CATCH` with `XACT_ABORT OFF`. Autocommit statements at the connection's default (RCSI):
  the increment is one statement, so no lost update; the insert race is settled by the key. Fixed lock order (day,
  term).
- **Zero results decided by the server**: each distinct term in a flush is run once through the real search
  (`IProductCatalogReader.SearchAsync`, one row). A caller cannot claim results.
- **No nightly rollup** — by design: DB25 keeps no raw search rows, the buffer is the aggregation. **Retention:**
  13 months, `DELETE TOP (4000)` loops, run by `TrafficRetentionService` at 01:30 Colombo beside the traffic purge,
  each in its own try/catch. Fixed in doc 08, so not a setting (the #193 traffic settings are about raw page views).

**Public list** — `GET /api/search/popular` → `{terms}` (no counts), cached 5 min (generation-guarded, evicted by
hide/show on this instance), `Cache-Control: public, max-age=300`. Doc 08 §7.6's TOP 8 / 30 days / with results,
plus the abuse controls below.

**Storefront:** the overlay's empty state shows **Recent searches** and **Popular searches** (deduped against
recent), falling back to **Browse the shop** only when both are empty — so a new shop still shows real entrances and
never a made-up "popular". The empty search page lists popular searches as links. The list is fetched once per page
load in the browser, only when an empty overlay opens or the empty page shows; vetted on the way in.

**Admin:** Content → **Popular searches** (`/content/popular-searches`, linked from the dashboard): what shoppers
see now with counts, hide (from the list or typed in advance), show again. `Content.View` reads, `Content.Edit`
writes, antiforgery, audited (`EntityType = HiddenSearchTerm`, Create/Delete, the term as id), idempotent under
races (2627 → "already hidden", no audit row).

**Migration `20261021112032_SearchQueriesDaily`:** `analytics.SearchQueriesDaily` (Date `date`, QueryNormalized
`nvarchar(100)`, Searches, ZeroResultSearches; `PK_SearchQueriesDaily (Date, QueryNormalized)`;
`CK_SearchQueriesDaily_Counts`) and `analytics.HiddenSearchTerms` (QueryNormalized PK `PK_HiddenSearchTerms`,
HiddenAtUtc `datetime2(3)`). Both QueryNormalized columns carry an **explicit column collation
`Latin1_General_100_CI_AS_SC`** (as the brief asked; identical to the database default, and the key's equality *is*
the collation — doc 08 N12 forbids `UseCollation` at the *database* level, which this is not). No secondary indexes:
both reads and the purge seek the clustered key. `has-pending-model-changes`: none. No column names a person
(`AnalyticsSchemaTests` still passes).

Doc 08 §3.8 / §8.4 updated with the as-built detail (beacon, rule, controls, hide-list table, retention row).

## 3. Owner decisions (safe choice taken — please confirm)

1. **Abuse controls on showing other shoppers' terms:** (a) only searches **with results** count, decided by the
   server — a term must match something the shop sells; (b) **≥ 5** such searches in 30 days
   (`SearchStats:PopularMinimumSearches`); (c) **≤ 40 characters** shown (100 counted); (d) **staff hide list**,
   exact normalised term. Not done: substring/word blocklists (would need a curated word list), per-visitor dedupe
   (needs an identifier DB25 deliberately does not keep).
2. **Privacy rule is the storefront's (stricter than DB25's "run of 7 digits"):** "levis 501 32x34" is not counted.
3. **Bots are not counted at all.**
4. **Hide/show permission is `Content.Edit`** (it changes what the storefront shows); reading needs `Content.View`.
5. **Hidden terms are kept indefinitely** (a handful of staff decisions).
6. **No curated "popular" list.** Fallback is the existing honest "Browse the shop".

## 8. Independent tester's round, and the fixes (commit `2c69dbe`)

Started from the tester's `cb92848`/`1dbb17c`. Three findings graded HIGH/MEDIUM, three LOW, one left alone.

**HIGH — the "must have results" abuse control was bypassable.** `SearchTerms.Tokenise` only ever checks the
first five tokens; a term with five matching substrings plus an unrelated sixth word (`"li in ne en lin idiot"`)
found results under the five-token search and carried the sixth word onto the public list, unverified, with five
requests. Added `SearchTerms.HasUncheckedTokens` (counts every distinct token the search would never look at, no
cap) and a check at the top of `SearchQueryStore.HasResultsAsync`: a term with more tokens than the search would
check is never credited with "having results", with no query run at all. Unskipped
`A_phrase_whose_extra_words_match_nothing_never_reaches_the_public_list`.

**HIGH — no rate limit on `POST /api/search/submissions`.** 2,000 POSTs from one client in under a second all
counted. Added `SearchSubmissionThrottle` — the same address-partitioned fixed-window shape as
`NewsletterSignupThrottle`/`ContactEnquiryThrottle`, reusing `ClientAddressPartition.IsInfrastructure` rather than
a third private copy of its warning — at **30 submissions per address per minute**, checked first in the endpoint.
A refused submission is silently dropped (still 204), the same as a bot or a privacy-refused term: nothing about
the answer is worth a caller learning from. New tests: `Submissions_past_the_rate_limit_are_silently_dropped_and_do_not_count`,
`Two_addresses_are_throttled_independently`.

**MEDIUM — #118 regression: a search run from the panel during start-up left the panel open.** `isNavigationAway`
answers false for the shopper's own search in that window, because that navigation *replaces* the router's
pending one and so becomes the first to succeed — it carries no `previousNavigation` either, indistinguishable
from the outside from a navigation the router started on its own. Fixed the way the coordinator asked: added
`HeaderSearch.closed` (an `output<void>()`, the same pattern `sd-drawer`/`sd-mini-bag` already use), emitted from
`run()` and from choosing a path-based suggestion — never from Escape or Tab, which dismiss the popup and go
nowhere. `SiteHeader` wires the panel instance's `(closed)` to a new `closeSearchPanel()`, which closes with **no**
focus management, unlike `closeSearch()` (Escape's own handler): the shopper is on their way to a results page,
not staying on this one. The original `isNavigationAway` fix is untouched and still covers every other navigation
away. Removed `test.fail()` from `header-panels-navigation.e2e.ts`; **30/30 passed under `--repeat-each=6`**.

**MEDIUM — the 5,000-entry buffer could be flooded by one visitor.** 6,000 unique junk terms from one client filled
it; a legitimate term from another visitor was lost; the resulting flush took 12.3 s. The rate limit above closes
this too: its window (one minute) matches the buffer's flush interval
(`SearchStatsOptions.DefaultFlushSeconds`), so one address can now put at most 30 of the buffer's 5,000 entries in
before the next flush empties it again — re-measured, not merely assumed, by
`A_client_that_respects_the_rate_limit_cannot_fill_the_buffer_within_one_flush_window`, which also checks a second
visitor's genuine search still lands. No separate per-IP buffer cap was needed.

**LOW — the privacy rule ran on the truncated term.** 88 characters of padding pushed
`john.perera@example.com` past the 100th character, and the address was stored as its local part alone
(`"…aaaa john.perera"`). `SearchQueryText.Normalise` now checks `IsPersonal` on the **whole** normalised term
before `Truncate` runs. Unskipped `An_email_address_cut_off_by_the_hundred_character_limit_is_not_stored`.

**LOW — invisible characters were never stripped from a search term at all.** Neither a bidi override (U+202E)
nor a zero-width character (U+200B, U+FEFF) was removed; both travelled into storage byte for byte. Extended
`PlainText` (the #189 helper review text, review display names and customer names already share) with
`IsInvisibleFormatting` for the two zero-width characters, and wired both it and the existing `IsBidiControl` into
`SearchQueryText.Normalise`'s own character scan — dropped outright, never turned into a space, since they carry
no word boundary of their own. **Deliberately excluded: ZWJ and ZWNJ (U+200C/U+200D)**, which Sinhala and Tamil
conjuncts need and which #189 D1 already pins must survive; a dedicated test
(`Zwj_and_zwnj_still_survive_stripping`, and the `SearchQueryText` equivalent) proves the two families are kept
apart. The extension to `PlainText` also benefits review text and names, which had the same gap; the full unit
suite (4,018 tests, including every `ReviewRules`/`CustomerAccountValidator` test) still passes.

**LOW — doc 08 said `HiddenAtUtc` was `datetime2(0)`; the code was already `datetime2(3)`.** Checked every other
audit timestamp column (`ops.AuditLogs.OccurredAtUtc`, `AppRole.CreatedAtUtc`/`UpdatedAtUtc`,
`AppUser.LastLoginAtUtc`/`AnonymisedAtUtc`): all `datetime2(3)`. Only `analytics.PageViews.OccurredAtUtc` is
`datetime2(0)`, and doc 08 §3.8 gives a specific, high-volume reason for that one column. `HiddenAtUtc` is a
staff decision, a handful of rows — the code's `datetime2(3)` was right, so the doc was corrected rather than
the migration touched.

**Left alone, as instructed:** the en/em-dash order-number defect (still `Skip`-pinned, not asked for); the
barrier-based insert-race test and the letters-only zero-result term (both already fixed by the tester in
`cb92848`, untouched here); `product-page.e2e.ts:999`'s known load flake.
