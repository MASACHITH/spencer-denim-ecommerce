# 2026-11-06 — Tharanga: #262, newsletter unsubscribe

Second of the in-scope features (after #253 → PR #277). No migration: `UX_NewsletterSubscribers_UnsubscribeToken`

## Done (branch `feature/262-newsletter-unsubscribe`)

- **Public:** `POST /api/content/newsletter/unsubscribe` `{ token }` → 204 for every token (live, used, wrong, not a
  GUID), one conditional UPDATE on the token's unique index, held to the signup's 250 ms floor. No throttle (it cannot
  write a stranger's address or mail anyone).
- **Storefront page `/unsubscribe?token=...`:** one press, nothing on arrival (mail scanners open links, some run
  script), the same "done" for every token, the token removed from the address afterwards, `noindex` + `no-store`.
  **Query string, not a path segment**: every log and traffic record drops query strings by construction
  (`RequestPathRedaction`, `PagePath`, `server/log-path.ts`); a path token would need a new credential route in three
  implementations. `unsubscribe` added to `ContentPageSlugRules.Reserved` (caught by `ContentPageSlugRulesTests`).
- **Staff:** `POST /api/admin/newsletter/subscribers/{id}/unsubscribe`, **`Newsletter.Export`** (doc 08 §9 has no
  newsletter write permission; Store Manager and Super Admin hold both today), antiforgery, conditional UPDATE + audit
  row (`StatusChange`, EntityId = id, no address, no token) in one retried transaction. Two-step control on the
  admin list; the outcome survives the reload; the question is the Yes button's description.
- **Export:** new last column "Unsubscribe link" (`{Email:StorefrontBaseUrl}/unsubscribe?token=...`, empty when the
  base URL is unset) for the owner's mail merge. Guide says to merge it into every newsletter and to **replace** the
  email tool's list with a fresh export before each mailing.
- **Copy:** sign-up and footer promise the link again (Contact page kept as the other way); the seeded Privacy draft
  gains one sentence; `StorePagesLint` permits exactly that fragment and `store-pages.json` was refreshed.
