## 2. Defect B (Major) — fixed: the read endpoints handed out Super Admin status to anyone

The tester's finding was that rounds 1–2 spent themselves making the write-side 403 byte-identical so a
non-GrantsAll actor could not tell "protected" from "doesn't exist", while `GET /api/admin/users` returned
`grantsAllPermissions` and full role detail to every `Users.View` holder — and any real `Users.Manage` actor
needs `Users.View` to pick a target. The write-side work was therefore moot in practice.

**The decision, which doc 08 §3.1 does not spell out for the read side and which the architect should confirm:**
a viewer without GrantsAll is shown **no GrantsAll holder at all**, rather than a redacted one.

- `GET /users` — GrantsAll holders are removed from the rows *before* the count and the page, so the total and
  the paging behave as if those accounts did not exist. A `roleId` filter on the Super Admin role returns empty.
- `GET /users/{id}` — a GrantsAll holder is the same `404` as an unknown id, compared on the wire in the test
  (status, content type and body with the per-request `traceId` removed), not just on the status code.
- `GET /roles` / `/roles/{id}` — the GrantsAll role is not listed, its detail is the same `404` as an unknown
  role, and **every role's `userCount` excludes GrantsAll holders**, because otherwise a shared role's headcount
  reveals one. This last one is the part I would most like a second opinion on; it is the subtlest leak in the set.

**Why hiding rather than nulling the flag.** Returning the user with `grantsAllPermissions: false` would be a
lie the UI then acts on — it would offer an Edit button that always 403s. Returning them with the roles stripped
still says "there is an account here you may not touch", which is the same oracle in a thinner disguise. Making
them absent is the only answer consistent with what the write side already does.

**Filtered in SQL, not after the read** (a `Where` over an `IQueryable<int>` of holder ids, composed into the
same statement as a subquery). That matters for more than efficiency: a by-id lookup of a Super Admin runs the
same single query and gets the same empty result as a missing id, so this route has no timing asymmetry of its
own — which is exactly the mistake defect A is.

Proven by **mutation**: with the viewer argument forced to `true` (the pre-fix behaviour) the three new HTTP
tests fail — the list shows the Super Admin and the total goes 1 → 2, and the by-id route answers `OK` where it
must answer `404`. Restored from a hashed backup afterwards and the hashes re-checked.

## 3. Defect A (Major) — **not** fixed, filed as #101, on the owner's instruction after I reported the analysis

The timing side-channel is real and the tester measured it (~4.1 ms against 6–7 ms, 40 samples). Two findings
changed what to do about it:

- **The round-2 plan would not have worked.** It was "add the missing `GetRolesAsync` call to the not-found
  path". But the asymmetry mostly lives *inside* `GetStaffUserSnapshotAsync`: **1** query for a missing user,
  **3–4** for an existing one, because the extra queries exist precisely when there is data to load. Work added
  to the not-found path cannot reproduce the cost of loading data that is not there. A constant-time floor is
  the only shape that closes it, and that is an artificial delay in an API — the architect's call.
- **It cannot be reached through the product today.** The write routes need `Users.Manage`, and the leak needs a
  holder of it who is *not* a Super Admin. No seeded role grants `Users.*` (doc 08 §9 excludes it from Store
  Manager; the other two are narrower), and **role CRUD is not built in this slice**, so there is no path to mint
  such a role. The only `Users.Manage` holders are Super Admins, for whom knowing an id exists is not a leak.

So it is a latent defect with a written trigger condition: **#101 must be fixed by whichever slice ships role
CRUD**, and the three handlers now carry a comment at the not-found branch naming it.

## 4. Converted the audit writes to `Enlist` (issue #59), which found a real hole in user creation

`main`'s W1-12 handlers enlist their audit row in the caller's unit of work so the change and its trail commit
together. These four handlers still called `WriteAsync` *after* the store's transaction had committed — the
exact failure `Enlist` exists to prevent. Converted: the handler builds the row (it holds the before/after
state), the store enlists it inside its own transaction on the success path only.

**The find: `CreateStaffUserAsync` had no transaction at all.** It called `CreateAsync` and then
`AddToRolesAsync` as two independent saves, so a failure in the second left **a staff user who existed and held
no roles**, with nothing in the audit log. It is one transaction now. Its audit row needs the new user's id,
which does not exist until the insert, so the handler passes a `Func<int, AuditLog>` the store invokes inside
the transaction — the same shape `CategoryWriteHandlers` uses on `main`. The retry path clears the change
tracker first, or a transient-failure retry would re-insert the user the previous attempt had tracked as Added.

Four new integration tests, and the second pair is the ones that matter: a refused write leaves no row and an
accepted one leaves exactly one; a **failure writing the row rolls the change back with it** (an over-long
`UserAgent`, which SQL Server rejects only at the final save, after the role change and the stamp rotation have
already been saved inside the transaction — so a pass proves those are rolled back too); the same for a
deactivation and a profile edit; and creating a user leaves no user at all if its audit row cannot be written.

Proven by mutation: moving `CommitAsync` before the enlist (the pre-#59 ordering) leaves the role change
applied with no trail — `Expected: Orders.View… Actual: Content.Edit…`.

## 5. `DefaultRoleDefinitions` was stale against the permission catalogue

`Store_Manager_has_every_permission_except_UsersStar_and_the_GrantsAll_only_settings` walks
`PermissionCatalog.All`, and it went red after the rebase: `main` added `Categories.Create`, `Categories.Delete`,
`Media.Create` and `Media.Edit` (W1-12, W1-04) and no default role had been given them. Added to Store Manager
and Content Editor per doc 08 §9's wildcards, with the Content Editor test's expected set updated to match.

The lists are written out rather than computed by exclusion on purpose — a new permission must be granted
deliberately, never by default — so this will recur every time the catalogue grows. There is now a comment at
the top of the class saying so, and the Store Manager test is the thing that catches it.
