**Found and fixed before it went out (own review pass, not a tester finding):** the date-range filter had
a boundary bug that would have shown up immediately in real use. An HTML `<input type="date">` — what the
"To" filter uses — sends a bare date like `2026-09-30`, and the naive normalisation treated that as
midnight *start* of the day. As the upper bound that meant `toUtc=2026-09-30` only matched rows at
exactly `2026-09-30T00:00:00.000`, silently dropping the rest of the day a user plainly meant to include.
Fixed in `GetAuditLogsQuery.ParseUtcDate`: a bare date used as the upper bound is now rolled to the last
tick of that day; a bare lower bound stays at midnight; a timestamp that already carries a time-of-day is
trusted exactly as given either way. Covered by three new unit tests and one integration test
(`A_bare_to_date_includes_rows_from_later_the_same_day`) that seeds a row late in the day and asserts a
bare `toUtc` for that same day still returns it.

**Later — round 2 closed out, PR opened:** the replay-test failure was a test bug, not a provider bug.
`AdminTwoFactorEndpointTests.An_authenticator_code_is_accepted_once_only` called
`TotpTestCodes.Next(key, 1)` twice — once to sign in, again later assuming it would reproduce the same
code to test reuse-rejection. `Next` derives its code from `DateTimeOffset.UtcNow` at call time, so a
30-second TOTP step boundary falling between the two calls made the second call compute a genuinely new,
unused code, which the server correctly accepted (not a replay at all). Fixed by capturing the code once
into `laterCode` and reusing that exact string both places. Full integration suite: **246/246**.
