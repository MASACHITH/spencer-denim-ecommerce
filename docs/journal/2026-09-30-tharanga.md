## 1. Angular route guard — returnUrl (item 2)

The route guards themselves (`adminSessionGuard`, `signedInGuard` in
`src/frontend/projects/admin/src/app/core/auth/auth-guards.ts`) already existed from W1-01/#17's work and
already redirect an unauthenticated or password-change-pending visitor away from an admin route — so that part
of the TASKS.md row was already done, just not documented as such. What was actually missing, matching the
issue text: the redirect never preserved *where the visitor was headed*, so everyone landed back on `/`
regardless of what they'd tried to open. No existing `returnUrl` convention anywhere in the app (checked the
storefront's route guards too — `catalog-route.guards.ts` is a `canMatch` for department routing, unrelated).

Built one from scratch, all in `auth-guards.ts` plus the two pages that consume it:

- `redirectWithReturnUrl()` attaches `?returnUrl=<attempted path>` to the login/change-password redirect, unless
  the attempted path is the redirect target itself or just the dashboard root (`/`) — both would be default
  behaviour anyway and would just be noise in the address bar.
- `sanitizeReturnUrl()` (exported, unit-tested directly) only accepts a same-origin in-app path — rejects
  anything starting with `//` or `/\`, or with no leading `/` at all. Angular's router can't actually be made to
  navigate off-site with `navigateByUrl`, so this isn't closing a live open-redirect hole today, but it's the
  kind of gap this project's testers have caught before ("a client-side gate that doesn't match what's actually
  needed") and it costs nothing to close now rather than assume it stays harmless as the app grows.
- `LoginPage` reads `returnUrl` off `ActivatedRoute` and navigates there on success instead of always `/`; if a
  password change is forced first, `returnUrl` is carried forward as a query param onto `/change-password`.
- `ChangePasswordPage` reads the same param and honours it once the change succeeds, instead of hardcoding `/`.

All built as plain strings passed to `navigateByUrl` (via `router.serializeUrl(createUrlTree(...))` where a
query param has to be attached), specifically so the no-`returnUrl` case still calls `navigateByUrl('/')` /
`navigateByUrl('/change-password')` exactly as before — kept the existing tests' assertions meaningful instead
of loosening them to fit a `UrlTree` object.

**Test gotcha worth flagging:** the natural way to test this — `TestBed.overrideProvider(ActivatedRoute, ...)`
inside an `it()` — fails at runtime ("Cannot override provider when the test module has already been
instantiated") because the shared `beforeEach` in both `login-page.spec.ts` and `change-password-page.spec.ts`
already calls `TestBed.inject(...)` to grab `controller`/`router`, which instantiates the module before the
test body runs. Worked around it with a small `configureWithReturnUrl()` helper in each spec that calls
`TestBed.resetTestingModule()` and reconfigures fresh, reassigning the outer `controller`/`router`/`navigateSpy`
bindings for that one test. Not elegant, but every other test in both files is untouched and still exercises the
original (no-`returnUrl`) module setup exactly as before.

### The six RBAC safety rules — how each was implemented and tested

1. **Only GrantsAll may create/edit/delete roles, change permissions, or assign/unassign GrantsAll itself.**
   Role CRUD wasn't built (see "Decisions" #2), so the only live surface is assigning the GrantsAll role to
   a user, or creating a user with it. `RoleAssignmentPolicy.CanManageStaffUser`'s
   `targetHasGrantsAllBefore/After` parameters block this outright for a non-GrantsAll actor.
   Tested: unit (`Non_grants_all_actor_can_never_assign_the_grants_all_role`,
   `A_non_grants_all_actor_can_never_manage_a_target_who_already_holds_GrantsAll`) and integration
   (`Non_grants_all_actor_can_never_assign_the_grants_all_role_even_with_users_manage`,
   `UsersManage_actor_cannot_manage_a_target_who_already_holds_GrantsAll`).

2. **Subset rule (N3).** Every command handler (`CreateStaffUserCommandHandler`, `AssignUserRolesCommand
   Handler`, `SetStaffUserActiveCommandHandler`, `UpdateStaffUserProfileCommandHandler`) loads the actor's
   real effective permissions (`IEffectivePermissionsProvider`, never trusts the principal) and the target's
   current roles/permissions from `IStaffUserRoleManagementStore`, then calls
   `RoleAssignmentPolicy.CanManageStaffUser` with the **aggregate union** of the *whole new role set* as
   "after" — not a per-role check — so combining two individually-subset roles into a set that together
   exceeds the actor's own permissions is still caught. Email changes are gated separately by
   `RoleAssignmentPolicy.CanChangeStaffEmail` (GrantsAll-only), independent of the subset result, per rule 2's
   own wording. Tested at both layers extensively — see `AssignUserRolesCommandHandlerTests`,
   `CreateStaffUserCommandHandlerTests`, `UpdateStaffUserProfileCommandHandlerTests` (unit) and
   `UserEndpointTests` (integration, real actors with real, narrower roles).

3. **Self-edit block.** `RoleAssignmentPolicy.IsSelfRoleEditBlocked` is checked **first**, before any
   database read, in `AssignUserRolesCommandHandler`. I also extended the same rationale to
   self-deactivation (`SetStaffUserActiveCommandHandler`) — see "Decisions" #3, this is a deliberate
   extension beyond the rule's literal text, please confirm it's wanted.

4. **Last Super Admin guard — this is the one the task said to take real care with.**
   `StaffUserRoleManagementStore.ReplaceRolesAsync`/`SetActiveAsync` only run the guard at all when the
   operation could actually reduce the active-GrantsAll count (current holder losing the role, or being
   deactivated) — cheap to check, avoids locking on every unrelated write. When it applies:
   `dbContext.Database.CreateExecutionStrategy().ExecuteAsync(...)` wraps `BeginTransactionAsync` →
   `EXEC sp_getapplock @Resource='rbac:grants-all', @LockMode='Exclusive', @LockOwner='Transaction'`
   (default infinite `@LockTimeout`, so a second caller **blocks** rather than fails fast — that's what
   makes the race resolve to exactly one winner instead of both failing or both succeeding) → re-count
   active holders excluding the target → `RoleAssignmentPolicy.CanReduceActiveGrantsAllHolders` → commit or
   rollback.
   - **Real bug caught by the tests, not by review:** my first version called `Database
     .BeginTransactionAsync()` directly, which threw at runtime ("the configured execution strategy does
     not support user-initiated transactions") because `Database:MaxRetryCount` enables
     `EnableRetryOnFailure`. Fixed by wrapping the whole begin/work/commit block in
     `CreateExecutionStrategy().ExecuteAsync(...)`, the documented EF Core pattern for combining the two.
     Every test in `UserEndpointTests` involving a write was failing with 500s until this was fixed —
     good reminder that "it compiles" and "the SQL is right" are not the same as "it runs".
   - **Sequential case:** proved directly against the store (`StaffUserRoleManagementStoreTests
     .Deactivating_the_sole_active_GrantsAll_holder_is_rejected` /
     `Unassigning_the_GrantsAll_role_from_the_sole_holder_is_rejected`), deliberately bypassing the
     handler's actor/self-edit authorization layer. Worth spelling out **why** it's tested this way, not
     through the API: rules 2+3 mean the only actor ever authorized to touch a GrantsAll target *is* another
     active GrantsAll holder — so reaching "attempt to deactivate the literal sole remaining Super Admin"
     through a legitimate, non-racing HTTP request is actually impossible by construction (if such an actor
     exists and is distinct from the target, there are ≥2 active holders, so the guard correctly allows it).
     The store-level test proves the guard's own arithmetic is right regardless; the HTTP-level test
     `A_lone_active_super_admin_cannot_be_deactivated_by_anyone_reachable_through_this_api` proves the
     *reachable* paths are all refused (by rule 2, before rule 4 even runs).
   - **Concurrent case (the one the task specifically asked for):**
     `UserEndpointTests.Two_concurrent_deactivations_of_the_last_two_super_admins_never_both_succeed` — two
     real GrantsAll admins, each deactivating the *other* at the same time via `Task.WhenAll` over two real
     HTTP clients. Asserts exactly one 200 and one 409, then independently re-queries the database and
     asserts exactly one of the two is active (not "one 409 was returned", the actual row state). Ran the
     full integration suite three times in a row to check for flakiness — passed all three (246/246 each
     time).
   - Both `IStaffUserRoleManagementStoreTests` and `UserEndpointTests` had to be made aware that
     `UX_Roles_GrantsAll` allows **at most one** GrantsAll role in the whole database, and this suite shares
     one database for the whole assembly (`AssemblyFixture`) — see "Decisions" #4 for the trouble this
     caused and how it was resolved; it broke a pre-existing, previously-green test twice before I got the
     cleanup right, which is exactly the kind of cross-test interference a second reviewer should double
     check I actually caught all of.

5. **SecurityStamp rotation.** `ReplaceRolesAsync` calls `userManager.UpdateSecurityStampAsync(user)` after
   the role change commits (inside the same transaction). Verified two ways: unit
   (`Successful_assignment_rotates_the_targets_security_stamp_via_the_store`, against the fake store) and
   integration (`Assigning_roles_rotates_the_targets_security_stamp`, comparing the real DB column
   before/after over HTTP) — I did not just assume the existing #16 mechanism picks this up; I read
   `IdentityRegistration.ValidateAdminPrincipalAsync` and confirmed it compares the cookie's stamp claim
   against the live DB value on each revalidation, and separately confirmed it checks `IsActive` directly
   too (so deactivation takes effect even without a stamp bump, which is why I did *not* add one there —
   rule 5 is scoped to role/permission changes specifically).

6. **Audit.** Role/permission changes are logged as `AuditActions.PermissionChange` with `before`/`after`
   JSON holding both role names and the full permission list (doc 08's literal ask). Create/deactivate/
   reactivate/profile-edit use the more specific, already-declared vocabulary (`Create`, `StaffDeactivated`,
   `StaffReactivated`, `Update`/`EmailChanged`) with their own before/after diff — see "Decisions" #5 on why
   I read this as the better match for doc 08's audit vocabulary than flattening every write to one action
   name. Redaction: `Audit_rows_for_this_feature_never_contain_redacted_columns` (integration) scans every
   `AuditLogs` row this feature writes for `PasswordHash`/`SecurityStamp`/`ConcurrencyStamp`/
   `AccessFailedCount` literally appearing in the JSON — none do, and the initial password is never logged
   (`CreateStaffUserCommandHandlerTests` checks this explicitly too).

### Adversarial self-review (per the working method) — what I checked and the outcome

- *Could a Store Manager (non-GrantsAll, `Users.Manage`) escalate their own effective permissions by
  assigning themselves a role with one extra permission?* No — blocked before any permission check even
  runs, by the self-edit rule (rule 3), which doesn't care what the role would grant.
- *Could two concurrent requests both pass the last-Super-Admin check before either commits?* No — proven
  by the concurrency test above; the second caller blocks on the app lock rather than racing the read.
- *Does deactivating a user actually end their session promptly?* Yes, verified by reading (not assuming)
  the existing `ValidateAdminPrincipalAsync` — it checks `IsActive` directly every revalidation interval,
  independent of the stamp.
- *Could combining two roles, each individually a subset, together exceed the actor's own permissions?* No
  — the subset check always runs against the union of the whole new role set, never role-by-role.

### Decisions the architect/owner should sanity-check

1. **Default-role seeding shares the `Seed:Admin:Enabled` gate with the bootstrap Super Admin**, rather than
   running unconditionally. This mirrors the existing pattern exactly (idempotent by name, don't invent a
   new mechanism) but means that in an environment where `Seed:Admin:Enabled` has already been turned back
   off after go-live (the documented steady-state), these three roles won't get created until someone
   flips it on again once. Since role *creation* is idempotent and harmless to re-run, and doesn't touch a
   bootstrap-admin-user, I don't think this is risky, but flagging the operational implication rather than
   silently deciding it.
2. **Role management is read-only in this slice** (list/view only, no create/edit/delete/change-permissions
   UI or endpoint). The task's own wording asked for "list/view roles and their permission sets"
   specifically, and full role CRUD is GrantsAll-only per rule 1 anyway, so this reads as intentionally out
   of scope for W1-08 rather than a gap — but confirming, since it's the kind of thing that's easy to read
   either way.
3. **Self-deactivation is blocked**, extending rule 3's literal text ("nobody can edit their own role
   assignments") to deactivation too. Rationale: without this, a non-GrantsAll `Users.Manage` actor's own
   permissions are trivially a subset of themselves, so the subset check alone would let them deactivate
   their own account — a self-lockout footgun, not a privilege-escalation one, but still worth blocking.
   Flagged explicitly in `SetStaffUserActiveResult.SelfEditNotAllowed`'s own doc comment too.
4. **Added `Reviews.Edit`, `Reviews.Delete`, `Settings.View` to `Permissions.cs`.** Doc 08 §9's default-role
   table names these for Content Editor and Store Manager respectively, but the permission catalogue hadn't
   declared them yet (only `Reviews.View/Approve` and `Settings.Edit` existed). Checked every other active
   worktree's branch first — none had touched `Permissions.cs` — so this should be conflict-free, but it's
   the one change in this PR that touches a file other slices could plausibly also extend.
5. **Audit action naming**: the task text said "every change here is audited as `AuditLogs` `PermissionChange`
   with before/after permission lists" fairly literally; I read that as describing the *role/permission*
   changes specifically (doc 08 §3.1 already reserves `PermissionChange` for exactly that, and separately
   lists `StaffDeactivated`/`StaffReactivated`/`EmailChanged`/`Create` as the vocabulary for the other event
   types under its Users audit note). I used the richer, already-declared vocabulary for
   create/deactivate/reactivate/profile-edit instead of flattening everything to `PermissionChange`, since
   the audit log viewer being built in parallel (W1-09) is more useful with distinguishable actions. Every
   one of this feature's audit rows still carries a real before/after diff either way. Flagging the reading
   in case a stricter interpretation was intended.

## W1-08 tester-round-1 fixes (issue #8) — same branch, new commit(s)

An independent tester agent reviewed this branch and FAILed it on two Major defects and one Minor. All
three are now fixed, with fresh tests proving each fix, and every suite re-run clean. This section documents
what changed and why; the numbers at the end are from the fixed code, not the original build above.

### Defect 1 (Major) — Super Admin identity oracle via distinguishable denial reason

**The bug:** `RbacDenialClassifier.Classify` returned a distinct `RbacDenialReason.TargetIsOrWouldBecomeGrantsAll`
(with its own message) whenever a non-GrantsAll actor's target held or would gain Super Admin, versus the
generic `NotSubsetOfActorPermissions` for a target that merely had one extra ordinary permission. A
non-GrantsAll `Users.Manage` actor could therefore fish arbitrary staff IDs and learn, from the 403 body
alone, exactly which ones are Super Admin — the same enumeration-bug class as the W1-01 login-timing fix.
The tester also flagged that a genuine 404 (`TargetNotFound`) for a non-existent target, sitting alongside
that distinguishable 403, made the oracle worse (three distinguishable outcomes instead of two).

**The fix:**
- `RbacDenialReason.TargetIsOrWouldBecomeGrantsAll` is **deleted from the enum entirely** (not just hidden) —
  doc 08 §3.1 already says "GrantsAll holders are never a subset, so they are protected", so this was never
  really a separate case, just a separately-reported one. `RbacDenialClassifier.Classify` now folds it into
  `NotSubsetOfActorPermissions` unconditionally.
- All three write handlers (`AssignUserRolesCommandHandler`, `SetStaffUserActiveCommandHandler`,
  `UpdateStaffUserProfileCommandHandler`) now load the actor's effective permissions **before** the target
  lookup, so the target-not-found branch can decide correctly: a GrantsAll actor still gets a real
  `TargetNotFound` (404) — they're allowed to know — but a non-GrantsAll actor gets the exact same
  `Forbidden(NotSubsetOfActorPermissions, ...)` result the subset rule already produces, which the existing
  `UserEndpoints.ToProblem` renders identically. This was done in the **Application layer** (the command
  handler returns `Forbidden` instead of `TargetNotFound`), not by special-casing the endpoint, specifically
  so the two 403 bodies are byte-identical by construction rather than by two independently-written mapping
  branches that could drift apart.
- No internal/logging distinction was added for the collapsed case — there was no pre-existing
  denial-logging path to preserve it in, and the tester's guidance was to keep it out of the response only,
  not necessarily to invent new logging.

**Proof this is closed, not just "collapsed the enum":**
- New integration test `UserEndpointTests.GrantsAll_target_and_merely_over_permissioned_target_produce_byte_identical_denial_bodies`
  creates one target holding Super Admin and one holding an unrelated extra permission, hits both through the
  same actor and endpoint, and asserts `error`, `title`, `detail`, `status` are identical **and** that neither
  body has an extra property the other lacks (guards against a new, subtler oracle like an extra field).
- New integration tests `Non_grants_all_actor_gets_the_generic_denial_not_a_404_for_a_target_that_does_not_exist`
  (asserts 403 + `NotSubsetOfActorPermissions`, not 404, for a non-existent target) and
  `GrantsAll_actor_still_gets_a_real_404_for_a_target_that_does_not_exist` (contrast case, unaffected by the
  fix).
- New unit tests in all three handler test files:
  `Non_grants_all_actor_gets_the_same_generic_denial_for_a_target_that_does_not_exist` and existing
  `TargetIsOrWouldBecomeGrantsAll` assertions updated to `NotSubsetOfActorPermissions`.
- Frontend `users-api.ts`'s `FORBIDDEN_MESSAGES` no longer has a `TargetIsOrWouldBecomeGrantsAll` key (dead
  now that the API never sends it); a comment explains why, so nobody re-adds it "to be thorough".

### Defect 2 (Major, then-unreachable but real) — subset rule authorized against a stale read

**The bug:** `AssignUserRolesCommandHandler`/`SetStaffUserActiveCommandHandler`/`UpdateStaffUserProfileCommandHandler`
authorized against a snapshot read outside any transaction, then `StaffUserRoleManagementStore` re-read the
target's role state independently and wrote with no check tying the write back to what was authorized. Only
rule 4 (last-Super-Admin) had real transactional protection (`sp_getapplock` + fresh recount); rules 1/2 (the
subset rule) had none, so a concurrent change to the same target between the handler's read and the store's
write could be silently clobbered, or the write could proceed even though the target's true state at write
time no longer satisfied the subset rule.

**The fix — re-check inside the same transaction as the write, using rule 4's own pattern:**
- New `RbacActorContext(HasGrantsAll, HasUsersManage, EffectivePermissions)`
  (`Application/Admin/Users/Abstractions/RbacActorContext.cs`) carries the handler's authorization decision
  into the store.
- `IStaffUserRoleManagementStore.ReplaceRolesAsync`/`SetActiveAsync`/`UpdateProfileAsync` all now take this
  context. Inside the existing `CreateExecutionStrategy().ExecuteAsync` transaction, each method first
  acquires a **new, per-target** `sp_getapplock` resource (`rbac:manage-user:{targetUserId}`) — deliberately
  scoped per-target rather than reusing the global `rbac:grants-all` resource, so unrelated users' writes
  don't serialise against each other for no reason — then re-reads the target's CURRENT roles/permissions
  fresh (`LoadCurrentPermissionStateAsync`) and re-runs `RoleAssignmentPolicy.CanManageStaffUser` against that
  fresh state. If it no longer holds, the whole operation rolls back and returns a new
  `AuthorizationStale` result on all three store result types.
- `UpdateProfileAsync` previously had **no transaction at all** (each `UserManager` call saved independently);
  it's now wrapped in the same transaction pattern as the other two, consistent with the class's existing
  doc comment about `UserManager` calls sharing the ambient transaction.
- Handlers map `AuthorizationStale` to the exact same `Forbidden(NotSubsetOfActorPermissions, ...)` shape as
  defect 1's generic denial — deliberately not a new, separately-observable reason, so this fix doesn't
  reintroduce a new oracle of its own.
- Rule 4 (last-Super-Admin) still works exactly as before; where a write could reduce the active-GrantsAll
  count, `AcquireGrantsAllLockAsync` still runs (now using the freshly re-read `currentHasGrantsAll`, which is
  more correct than the old pre-transaction read, not less).

**Proof the race is actually closed** (`StaffUserRoleManagementStoreTests.cs`, real SQL Server):
- `Deactivation_authorized_against_a_stale_snapshot_is_rejected_after_a_concurrent_role_change_widens_the_target` —
  deterministic, sequential reproduction of the tester's exact scenario: a low-privilege actor's authorization
  is computed against the target's original narrow role; a *different*, GrantsAll admin then fully commits a
  role change widening the target past the first actor's permissions; the first actor's (now-stale) write is
  attempted last. Asserts `SetActiveStoreResult.AuthorizationStale`, and that the target is still active
  (i.e., the stale write did not silently deactivate them) — this is the "first must now fail cleanly, not
  silently succeed against stale authorization" proof the tester asked for.
- `Two_concurrent_writers_to_the_same_target_never_leave_a_lost_update_from_the_stale_actor` — true
  concurrency: two separate DI scopes (mirroring two separate HTTP requests) call `ReplaceRolesAsync` on the
  *same* target at the same time via `Task.WhenAll`, one from a low-privilege actor authorized against the
  original narrow role, one from a GrantsAll actor widening it. Asserts the GrantsAll write always succeeds
  (never subject to the subset rule), the low-privilege write is always either `Success` or
  `AuthorizationStale` (never anything else), and — regardless of which writer's applock acquisition won the
  race — the target's **final** role is always the GrantsAll admin's, proving the low-privilege actor can
  never silently re-apply its stale role on top of a legitimate concurrent change.
- Ran the RBAC-relevant subset (`UserEndpointTests` + `StaffUserRoleManagementStoreTests`, 20 tests) three
  extra times beyond the two full suite runs below, specifically hunting for flakiness in the new concurrency
  test — 5/5 passed identically every time (no `Task.WhenAll` ordering ever produced an unexpected result).

### Defect 3 (Minor) — dead code, `RoleAssignmentPolicy.CanAssignRole`

Deleted `CanAssignRole` from `Domain/Identity/RoleAssignmentPolicy.cs` and its 6 dedicated unit tests from
`RoleAssignmentPolicyTests.cs`. Chose deletion over a doc-comment-only fix: the tester confirmed it's strictly
redundant with `CanManageStaffUser`'s aggregate-union check (which is at least as strict) and there's no
imminent single-role-add feature planned that would need it — keeping unused, security-adjacent API surface
around is more likely to be reached for by mistake later than to be useful.

### Adversarial re-review of these three fixes specifically

- *Did collapsing the enum leave any other field that could become a new oracle?* Checked byte-for-byte via
  the new `GrantsAll_target_and_merely_over_permissioned_target_produce_byte_identical_denial_bodies` test,
  including an explicit property-name-set comparison, not just spot-checking `error`.
- *Does the `AuthorizationStale` store result leak anything defect 1 just closed?* No — every call site maps
  it to the identical generic `Forbidden(NotSubsetOfActorPermissions, ...)`, never its own reason string.
- *Could the new per-target `sp_getapplock` deadlock against the existing global `rbac:grants-all` lock?* No —
  lock acquisition order is always per-target first, then (only when needed) the global lock, in every one of
  the three write paths; never the reverse order anywhere in the codebase, so no cycle is possible.
- *Did wrapping `UpdateProfileAsync` in a transaction change its email-uniqueness error mapping?* No —
  `MapProfileError` is unchanged; the only difference is that a partial failure (e.g. `SetUserNameAsync`
  succeeding after `SetEmailAsync`, then `UpdateAsync` failing) now rolls back cleanly instead of leaving a
  partially-applied profile update, which is strictly safer than before.
- *Tried to race the fix the way the tester raced the original code:* the `Task.WhenAll` test above is exactly
  that attempt, run 3 extra times looking for a window where it doesn't hold — none found.
