## 1. Angular route guard — returnUrl (item 2)

The route guards themselves (`adminSessionGuard`, `signedInGuard` in
`src/frontend/projects/admin/src/app/core/auth/auth-guards.ts`) already existed from W1-01/#17's work and
already redirect an unauthenticated or password-change-pending visitor away from an admin route — so that part
of the TASKS.md row was already done, just not documented as such. What was actually missing, matching the
issue text: the redirect never preserved *where the visitor was headed*, so everyone landed back on `/`
regardless of what they'd tried to open. No existing `returnUrl` convention anywhere in the app (checked the
storefront's route guards too — `catalog-route.guards.ts` is a `canMatch` for department routing, unrelated).

Built one from scratch, all in `auth-guards.ts` plus the two pages that consume it:

- `redirectWithReturnUrl()` attaches `?returnUrl=<attempted path>` to the login/change-password redirect, unless
  the attempted path is the redirect target itself or just the dashboard root (`/`) — both would be default
  behaviour anyway and would just be noise in the address bar.
- `sanitizeReturnUrl()` (exported, unit-tested directly) only accepts a same-origin in-app path — rejects
  anything starting with `//` or `/\`, or with no leading `/` at all. Angular's router can't actually be made to
  navigate off-site with `navigateByUrl`, so this isn't closing a live open-redirect hole today, but it's the
  kind of gap this project's testers have caught before ("a client-side gate that doesn't match what's actually
  needed") and it costs nothing to close now rather than assume it stays harmless as the app grows.
- `LoginPage` reads `returnUrl` off `ActivatedRoute` and navigates there on success instead of always `/`; if a
  password change is forced first, `returnUrl` is carried forward as a query param onto `/change-password`.
- `ChangePasswordPage` reads the same param and honours it once the change succeeds, instead of hardcoding `/`.

All built as plain strings passed to `navigateByUrl` (via `router.serializeUrl(createUrlTree(...))` where a
query param has to be attached), specifically so the no-`returnUrl` case still calls `navigateByUrl('/')` /
`navigateByUrl('/change-password')` exactly as before — kept the existing tests' assertions meaningful instead
of loosening them to fit a `UrlTree` object.

**Test gotcha worth flagging:** the natural way to test this — `TestBed.overrideProvider(ActivatedRoute, ...)`
inside an `it()` — fails at runtime ("Cannot override provider when the test module has already been
instantiated") because the shared `beforeEach` in both `login-page.spec.ts` and `change-password-page.spec.ts`
already calls `TestBed.inject(...)` to grab `controller`/`router`, which instantiates the module before the
test body runs. Worked around it with a small `configureWithReturnUrl()` helper in each spec that calls
`TestBed.resetTestingModule()` and reconfigures fresh, reassigning the outer `controller`/`router`/`navigateSpy`
bindings for that one test. Not elegant, but every other test in both files is untouched and still exercises the
original (no-`returnUrl`) module setup exactly as before.

## 2. Forwarded-headers regression test (item 3)

**Investigated the blocker first, as instructed.** The W1-01 note said `Microsoft.AspNetCore.HttpOverrides`
types didn't resolve in "the plain-SDK unit test project" and guessed it might be machine-specific. Reproduced
it directly: added a throwaway file to `SpencerDenim.UnitTests` referencing
`Microsoft.AspNetCore.HttpOverrides.ForwardedHeadersOptions` and built just that project —

```
error CS0246: The type or namespace name 'ForwardedHeadersOptions' could not be found
```

— on this machine too. **It isn't machine-specific.** `SpencerDenim.UnitTests` is a plain `Microsoft.NET.Sdk`
project; it only reaches `SpencerDenim.Api` (a `Microsoft.NET.Sdk.Web` project) via `ProjectReference`, and a
`ProjectReference` alone does not carry the ASP.NET Core shared framework's ref assemblies down to a plain-SDK
consumer — that needs the Web SDK itself, an explicit `<FrameworkReference Include="Microsoft.AspNetCore.App" />`,
or a package (like `Microsoft.AspNetCore.Mvc.Testing`) that brings one along. Deleted the throwaway file; no
project file changes needed or made.

**Decision: the test lives in `SpencerDenim.IntegrationTests`**, in `AdminAuthEndpointTests.cs` (new fact
`A_forged_X_Forwarded_For_header_from_a_direct_caller_does_not_reach_the_audit_log`), not a new unit test. Two
reasons: (1) that project already resolves `Microsoft.AspNetCore.*` types fine via its own
`Microsoft.AspNetCore.Mvc.Testing` reference — no toolchain fix needed; (2) this genuinely needs the real HTTP
pipeline end to end (`WebApplicationFactory`/`TestServer`, header in → audit row out), which is what this
project is for, not something a unit test could exercise in isolation anyway.

**One real wrinkle:** `TestServer` has no real socket, so `HttpContext.Connection.RemoteIpAddress` is `null` by
default — there's no "real peer" for the assertion to fall back on the way a live Kestrel connection has one.
Added a small `IStartupFilter` (`SimulatedRemoteIpStartupFilter`) that stamps a fixed, known, non-loopback
address onto the connection before the rest of the pipeline runs (via `factory.WithWebHostBuilder(...)`, layered
on top of the existing `ApiFactory` rather than changing it). The forged `X-Forwarded-For` header then claims a
*third*, different address, so the only way the test can pass is if the audit row ends up with the simulated
connection's address and neither of the header's.

**Verified the test actually catches the regression, not just that it's green for the wrong reason** (the class
of bug this project's testers keep finding) — temporarily reintroduced the exact round-3 vulnerability in
`ForwardedHeadersSetup.cs` (`ForwardedHeaders = XForwardedProto | XForwardedFor`, cleared `KnownIPNetworks`) and
re-ran just this test:

```
Assert.Equal() Failure: Strings differ
Expected: "198.51.100.7"
Actual:   "203.0.113.99"
```

Failed exactly as it should, with the forged IP visible in the failure message. Reverted immediately
(`git diff` on `ForwardedHeadersSetup.cs` is clean — confirmed with `git status`/`git diff` before committing).
Did **not** touch `ForwardedHeadersSetup.cs` in the actual commit; W0-15 still owns re-enabling
`X-Forwarded-For` once real Caddy/Docker proxying exists.
