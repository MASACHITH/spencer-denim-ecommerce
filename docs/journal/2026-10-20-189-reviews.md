## Design choices, and the docs behind them

- **Verified buyer** means a **Delivered** order whose `Orders.CustomerUserId` is the reviewer's account and that contains the product (doc 08 D4, doc 11 P12 step 2, P9 step 9).
  - The match is never by email. A guest order with the same address counts only once it is linked, and linking needs the address confirmed (D5, #162's takeover fix).
  - Paid, Processing and Shipped don't count: the goods haven't arrived. Refunded, Cancelled and Expired don't count either.
  - The badge is set at submission and can be gained by a later edit. It is never removed, including after a refund (G-27).
- **Who may write:** any signed-in, active customer, buyer or not. Doc 11 P12 says "Customer reviews before delivery → allowed but without the Verified buyer badge". The client chose sign-in, not purchase, as the abuse control (01 G5, Q13).
- **One review per customer per product.** A second POST answers 409 with the saved review, and the form switches to editing it.
- **Edits (G-32):** an edit returns to Pending while approval is required; the display name keeps its first snapshot.
  - **A review staff hid stays hidden when its author edits it**, even with approval off, so an author can't undo a moderator.
- **Plain text, rendered as text.** Doc 08 gives `Body nvarchar(4000)` and no HTML, so `HtmlSanitiser` is not used.
  - Text is stored as typed after normalising: `\r\n` becomes `\n`, it is trimmed, and runs of three or more line breaks become two.
  - Refused: C0/C1 control characters (except the body's line breaks and tab), bidi overrides, isolates and marks, unpaired surrogates, and a title on two lines.
  - Every renderer uses interpolation. Unit, Vitest and e2e tests show `<img onerror>` arriving as visible text with no element and no script run.
- **Limits:** rating 1–5, required, as a JSON whole number (`4.5`, `"4"` and `true` are refused); title 120; body 4,000; note 500.
- **Display name:** first name and last initial ("Nimal P."), taken from the profile at submission. It is not editable, and never the email or the full surname.
- **ProductStats recompute:** `RatingAverage`/`RatingCount` only, recomputed from approved rows.
  - Average to two places, halves away from zero; NULL with no approved reviews.
  - `StatsRefreshedAtUtc` stays `NightlyStats`' timestamp.
  - Concurrency protocol (`ProductRatingSql`): every review write takes the product's **`ProductStats` row with `UPDLOCK` first**, then changes the review, then runs one `UPDATE … FROM … CROSS APPLY (COUNT, SUM … WITH (READCOMMITTEDLOCK))`.
    - Under RCSI the second writer's statements all start after the first commits, so it counts the first's approval. No read-then-write, so no lost update.
    - Every writer takes the stats row before any review row, so review writers can't deadlock each other.
    - The same lock serialises two tabs creating a first review, and the unique index is the backstop.
- **Moderation:** one conditional `UPDATE … OUTPUT deleted.Status WHERE Id AND RowVersion = @seen AND Status IN (allowed) AND product not deleted`.
  - Allowed moves follow doc 11 P12: Pending → Approved ↔ Hidden, or Pending → Hidden.
  - A miss is diagnosed after the lock: NotFound, Stale (the version moved because another moderator decided or the author edited) or Unchanged (already in the target status).
  - An applied action writes **one audit row** (`Approve`, or `StatusChange` for hide) with the status before and after, the product and `noteGiven`. **The note text is not copied**: it is personal data the PDPA erasure deletes with the review, and doc 08 §3.1 step 2 doesn't list `AuditLogs`.
- **Rate limit:** 10 creates or edits per hour **per customer account** (`ReviewWriteThrottle`), taken before the use case runs, with no queue and 429 plus `Retry-After`.
  - It is keyed by account rather than address because the route already needs a session, and an address partition behind an untrusted proxy is everyone's partition.
- **SSR:** the summary and list are server-rendered and are the same for every visitor.
  - `AccountStore` never asks during SSR, so the form and the sign-in prompt render only in the browser.
  - The e2e test fetches the HTML with a customer cookie and finds neither, and no per-user text.
- **Cards and listing:** they already show `ProductStats` ratings (CARD-01, PDP-02), so nothing new was added. The Highest Rated sort and the min-rating filter now run on real figures.
- **No JSON-LD:** the project emits no product structured data, so no `AggregateRating` was added.
- **PDPA:** `IProductReviewErasure.EraseForCustomerAsync(userId)` locks the affected stats rows, deletes the account's reviews and recomputes every affected product in one transaction. It joins the caller's transaction if there is one.
  - **No anonymisation routine exists yet** (doc 11 P17, `Customers.Delete`), so nothing calls it. P17 owes the call.

## Decisions for the owner (safe choice taken)

1. **Reviews.Delete isn't used.** ADM-16 says "approve / hide", and hiding already takes a review off the site, reversibly. Hard delete happens only through the PDPA hook.
2. **Display name isn't editable** by the customer ("defaults from the profile" in P12 allows either). A free display name invites impersonation ("Colombo Wardrobe team"). Easy to add later.
3. **A hidden review stays hidden after its author edits it**, even with approval off. G-32 covers approved reviews only; this closes the case where an author could undo a moderator.
4. **Moderation notes stay out of the audit log** (`noteGiven` only), for PDPA.
5. **Demo seed ratings:** the dev/staging demo catalogue seeds fake `RatingAverage`/`RatingCount` with no reviews behind them.
   - The product header shows the seeded figure until the first review write or moderation recomputes the truth. The reviews section always shows the truth, computed from rows.
   - Production has no demo catalogue. A one-off recompute of every product could be added if staging should look consistent; it would change listing fixtures, so it wasn't done here.
6. **The rate limit is a code constant** (10 an hour), not a setting.

**What M4 and M5 mean, honestly.** With the stats row held by the test connection, every approval waits at
the recompute `UPDATE`. When the lock is released, each resumed `UPDATE … FROM … CROSS APPLY` still counted
every approval committed before it, so the single conditional statement alone was enough in this staging. M11
shows what the protocol and the test do guard against: a recompute that reads the count first and writes it
afterwards loses updates, and the concurrency test catches it. The stats-row lock stays for three reasons:

- it is doc 08 §7.4's pattern;
- it orders every review writer the same way, so a future multi-statement path cannot deadlock or lose an update;
- it makes two tabs' first reviews a decision rather than a unique-index violation.

But no test proves the lock is needed for the single-statement recompute as written. A tester may want to try
a staging where the second recompute's snapshot is taken before the first commits and it does not block.

## Round 2: tester findings D1 and D2, and the notes (fixed on the same branch)

The tester's commit 82574c8 added `ReviewTesterAttackTests` (25 cases, 3 failing on purpose).

- **D1 (Medium): the display name carried control and bidi characters from the profile.** A first name with U+202E reversed the "Verified buyer" badge and the date beside it.
  - `PlainText` (Domain) now defines the unsafe set once: control characters, bidi embeddings, overrides, isolates and marks, U+2028/2029/0085, and unpaired surrogates.
  - `ReviewRules.DisplayNameFor` strips them, turning tab or line breaks into a space and falling back to "Customer".
  - `CustomerAccountValidator` refuses them in the first and last name on register and profile, with the same sentence review text uses.
  - The storefront and admin render the name in `<bdi>` with `unicode-bidi: isolate`.
  - The tester's test now plants the names straight into the account. Registration refuses them, so planting is how a name saved before this rule would look. It also asserts the result is "Nimal P.".
  - **Names already stored are not rewritten.** They are cleaned wherever they become a review's display name. A data fix for existing profiles is the owner's call.
- **D2 (Low): U+2028 and U+2029 let a title span two lines.** U+0085, U+2028 and U+2029 are now line breaks: refused in a title, stored as `\n` in a body, so both rules treat every line break the same way. The stub mirrors this.
- **Rate limit:** the permit is taken after the body passes `ReviewRules`, so a 400 is free. A 409 or 404 still counts, because on the server each one is a transaction. The stub mirrors this.
- **Erasure race:** `EraseForCustomerAsync` now locks the stats rows of every product the account has reviewed, in one statement, before touching a review. It deletes with `OUTPUT deleted.ProductId`, locks any product that arrived in the gap, and recomputes exactly the products whose rows it deleted.
- **Missing `ProductStats` row:** logged as a warning (EventId 7301), not created. Every column except the rating is pricing, so an upsert would have to invent prices, and `CatalogVisibility` would then list the product at Rs. 0. A customer can't reach this path for such a product, because submission requires a visible product, which requires the row.
- **The stats-row lock is kept.** The tester showed it is what prevents deadlock 1205 when combined with `READCOMMITTEDLOCK`. `Simultaneous_approvals_of_one_product_never_deadlock_even_without_retries` passes.
- **Housekeeping:** literal invisible characters in test inputs (the tool writing my `\u` escapes as the characters themselves) were replaced with escapes or `(char)0x…`, and a scan of every changed file finds none left.
