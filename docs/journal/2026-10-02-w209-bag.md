## 2. The migration, exactly

`sales.Carts`: `Id int IDENTITY PK` · `Token uniqueidentifier NOT NULL` (UX, default `newid()`) ·
`CustomerUserId int NULL` → FK `identity.Users` NO ACTION · `CreatedAtUtc` · `LastActivityAtUtc`.
Indexes `UX_Carts_Token`, `UX_Carts_Customer` (`WHERE CustomerUserId IS NOT NULL`),
`IX_Carts_LastActivity` INCLUDE `CustomerUserId`.

`sales.CartItems`: `Id int IDENTITY PK` · `CartId` → FK `Carts` **CASCADE** · `VariantId` → FK
`catalog.ProductVariants` NO ACTION · `Quantity smallint` with `CK_CartItems_Quantity BETWEEN 1 AND 10`
· `UnitPriceAtAdd decimal(18,2)` · `AddedAtUtc` · `UpdatedAtUtc`. Indexes
`UX_CartItems_Cart_Variant`, `IX_CartItems_Variant`.

**No rowversion on either** (doc 08 §1.5 excludes hot rows). **No audit columns** (§3.8 lists both
tables as never audited). Nothing else in `sales` is created — not `Orders`, `OrderLines`,
`OrderStatusHistory`, `Payments`, `PaymentEvents`, `Refunds`, `NumberSeries`, `DeliveryMethods`,
`DeliveryMethodZoneRates`, `PickupLocations`, `Couriers`, `PaymentProviders` (all #53's), and not
`WishlistItems` (W2-08's). `CartModelTests` asserts the schema holds exactly two tables, so adding one
is a decision rather than an accident.

### The three doc 08 `Carts` columns that are deliberately absent

This **corrects the brief**, which asked only about `DeliveryMethodId`.

| Column | Why not |
|---|---|
| `DeliveryMethodId` | `sales.DeliveryMethods` is #53's, so the FK cannot exist. Nothing in CART-01/02 reads or writes it. |
| `DistrictId` | **`ref.Districts` has never been created by any migration.** `AppUser.DefaultDistrictId` is already in the model with its FK deliberately left off for the same reason. |
| `PromoCodeText` | ADM-13 is week 3 and `marketing.PromoCodes` does not exist, so doc 08 §3.5's "revalidated on every read" is impossible — the column could only ever hold a code nothing had checked. |

The principle: **this migration creates exactly the columns CART-01/CART-02 reads or writes.** Two of
the three could not carry their foreign key today, and the migration that delivers each feature adds
its column with its constraint in one piece. Flagged for Tharanga on #53.

## 3. Decisions

### The guest cookie

`sd_cart`, holding `Carts.Token` and nothing else. `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`,
30-day sliding — reissued on every answer that resolved the bag, which is what makes it slide.

- **`Secure` is unconditional**, not `CookieSecurePolicy.SameAsRequest` and not behind a
  `RequireSecureCookies`-style flag like the admin cookie. There is no deployment where sending a bag
  capability in clear is wanted. Browsers treat `http://localhost` as trustworthy and accept `Secure`
  there, so development and the browser tests are unaffected; **the integration tests address the host
  as `https://localhost`**, because .NET's `CookieContainer` correctly refuses to send a `Secure`
  cookie over `http` — a suite on the default `http://localhost` would have "proved" the cookie worked
  by never exercising it.
- **`Lax`, not `Strict`.** A shopper arriving from an email, an ad or a search result makes a
  cross-site *top-level navigation*, and `Strict` withholds the cookie on exactly that request — so
  the server-rendered header would show an empty bag to someone whose bag is not empty. `Lax` still
  withholds it from cross-site POSTs, which is the case that matters.
- **A cookie value that is not the canonical GUID reads as "no bag", not as a 400.** A shopper cannot
  edit their own cookie, so a 400 would lock that browser out of the shop until they cleared site
  data. A well-formed token naming a bag that no longer exists is **cleared** rather than reissued.
- **The token is never in a response body, the HTML or the transfer state.** It is `HttpOnly` so that
  a script cannot read it; a copy anywhere a script can reach would make the flag decorative. Asserted
  in both the integration suite and `bag.e2e.ts`.
- **CSRF**: a cross-site HTML form can only send `urlencoded`, `multipart` or `text/plain`, and the
  writes require `application/json` → **415**. A cross-origin JSON `fetch` needs a CORS preflight and
  the API configures no CORS policy at all. With `SameSite=Lax` on top there is no shape of cross-site
  request left that reaches a bag.
- **Somebody else's token**: a token can only ever resolve a cart whose `CustomerUserId IS NULL`
  (`CartStore.FindAsync`), so an account cart is unreachable by token even with the exact value stored
  on its row. A guest token is a bearer capability by design — that is what the cookie *is* — and the
  three flags are what protect it.

### The sign-in merge: **merge**, not replace and not refuse

- *Replace* throws away what the shopper was doing in the last five minutes for something they added
  weeks ago on another device — the shape of bug this project has already shipped twice.
- *Refuse* (keep both, make them choose) needs a screen and a decision nothing in `docs/02` asks for.
- *Merge* keeps everything; the only case to get right is the same variant in both bags, where the
  quantities sum and clamp at 10 exactly as a second Add to Bag would. Doc 08 §3.5 already specifies
  it, so this is less a new decision than the one already taken.

Implemented in `MergeGuestCartCommandHandler`, in one transaction, with the guest cart deleted and the
guest cookie cleared afterwards. **Nothing calls it yet, and that is reported rather than hidden:**
there is no customer authentication in the repository at all (ACC-01 — the only cookie scheme is the
admin one), so `Carts.CustomerUserId` is never written over HTTP today. It is built and tested anyway
because the merge is where a bag is silently lost if it is written in a hurry at the end of ACC-01, and
because `UX_Carts_Customer` is in this migration to stop exactly the double cart a wrong merge
produces. ACC-01 needs two lines: call the handler after `SignInAsync`, and read the customer id in
`CartEndpoints.ReadLookup`.

### Stale and unbuyable items

Every line is **repriced from the catalogue on every read** (doc 08 §6). `UnitPriceAtAdd` travels only
so the storefront can say "the price has changed", and **nothing totals from it** — a line's subtotal,
the bag's subtotal and the saving are all built from today's price.

| State | What the bag does |
|---|---|
| Price moved | Today's price, today's line total, plus a notice. The stored figure is reported as history. |
| Unpublished / soft-deleted product, deactivated department or primary category (ADM-11), deactivated variant | **`Unavailable`.** The line stays, named, with its colour and size, **with no price at all**, no quantity control, out of the subtotal, and still removable. |
| Sold out | `OutOfStock`. Still priced (the shop still sells it), out of the subtotal, still removable. |
| Fewer left than the bag holds | `NotEnoughStock`. Keeps the quantity the shopper chose — it is theirs — says how many are left, and stays in the subtotal at the price really being offered. The selector's ceiling drops to the stock but **never below the quantity already shown**, or the control could not re-select its own value. |

A line that cannot be sold is never priced into a figure the shopper is being asked to pay. An
unavailable line shows no price because there is no offer left to quote — quoting the old one is the
same mistake as pricing from `UnitPriceAtAdd`.

`CartReader` uses `IgnoreQueryFilters()` and reads `IsDeleted` as data, because `Product` carries the
soft-delete filter and the product is a *required* navigation: with the filter on, a deleted product's
line is dropped from the join and **the item vanishes out of the bag with no message**. Measured — see
§5.

### Move to wishlist

It saves to **this browser** and then removes the line, in that order so a storage failure cannot lose
the item from both. It writes to the same `LocalWishlist` the product card's heart has used since
W2-04, and doc 08 §1.7 already specifies a guest wishlist as `localStorage` merged into
`sales.WishlistItems` on login — so this is the shape that was already decided, not an invention. A
`save()` method was added to `LocalWishlist` beside `toggle()`: toggling something already saved would
have removed it, so the bag line would have been deleted and the wishlist entry with it.

**What it cannot keep: the colour and the size.** `LocalWishlist` holds product slugs, as the heart
does, while `sales.WishlistItems` has a `ProductColourId`. Moving "Indigo / S" saves the product, not
the colourway. **Owed to W2-08.**

### The promo code: not built

CART-01 asks for one; there is nothing behind it. ADM-13 is week 3 and `marketing.PromoCodes` does not
exist, so every code a shopper typed would be refused and the field would teach them the shop is
broken. Doc 08 §3.5 also wants the code revalidated on every cart read, which is impossible with no
table to read. **No promo field on the bag page**, asserted by both a unit test and a browser test so
it cannot reappear by accident. **Owed: ADM-13, plus `Carts.PromoCodeText` and a `POST /api/cart/promo`.**

### Delivery and the total: not invented

Doc 08 §6 step 10 takes the fee from a `sales.DeliveryMethodZoneRates` row that "must exist and be
available". That table is #53's and `ref.Districts` has never been created; issue #33 is open because
delivery estimates have no source at all. So:

```
Subtotal (N items)     Rs. X
Discount              −Rs. Y      (only when there is one)
Delivery              Calculated at checkout
───
Total (items only)     Rs. X
```

plus one line of fine print. The total row is labelled for what it covers; a row called "Total" that
silently excluded delivery would be the misleading version. **The `CartTotalsDto` has no promo,
delivery or grand-total field at all** — a field nothing can fill is a field somebody will fill with a
guess.

## 4. The concurrency proof (doc 08 §3.5, DB22)

`CartStore.AddItemAsync` is doc 08's statement verbatim: one
`UPDATE … SET Quantity = IIF(Quantity + @q > 10, 10, Quantity + @q) WHERE CartId = @c AND VariantId = @v`,
and when it matches nothing an `INSERT` whose unique violation (2627/2601) is retried as the `UPDATE`.
Set quantity and remove are single statements; `LastActivityAtUtc` is a one-column last-writer-wins
update. There is no shape in this file in which a lost update is possible to write.

`CartConcurrencyTests` replays five races, **each many times, each round on a fresh cart**:

| Test | Shape | Rounds |
|---|---|---|
| `Eight_simultaneous_adds_of_a_new_variant_end_at_one_row_holding_all_eight` | the insert race, over HTTP | 25 × 8 writers |
| `Eight_simultaneous_adds_to_an_existing_line_lose_none_of_them` | the update race, over HTTP | 25 × 8 writers |
| `Two_simultaneous_adds_that_would_exceed_ten_land_exactly_on_ten` | the clamp under a race | 25 × 2 writers |
| `The_store_itself_never_loses_an_add_and_never_makes_a_second_row` | the same races at the store, no HTTP in the way | 60 × 10 writers |
| `Ten_simultaneous_creates_for_one_customer_make_exactly_one_cart` | `UX_Carts_Customer` | 15 × 10 writers |

**Proof that the tests are not vacuous.** `AddItemAsync` was temporarily replaced with the obvious
read-then-write (read the quantity, clamp in C#, write it back) and the suite re-run:

```
× Two_simultaneous_adds_that_would_exceed_ten_land_exactly_on_ten    Expected: 10  Actual: 6
× Eight_simultaneous_adds_to_an_existing_line_lose_none_of_them      Expected: 8   Actual: 6

                                                                     Expected: 8   Actual: 3
Failed!  - Failed: 3, Passed: 2, Total: 5
```

With the DB22 statement restored: `Passed! - Failed: 0, Passed: 5, Total: 5`, and the same five green
on every subsequent run of the suite.

## 5. Red before, green after

### 5.1 The vanishing bag line (fixed before it shipped)

`IgnoreQueryFilters()` removed from `CartReader.ReadAsync`, which is what the obvious implementation
looks like:

```
× CartStaleItemTests.A_soft_deleted_product_is_still_shown_in_the_bag_rather_than_vanishing
  Assert.Single() Failure: The collection was empty
Failed!  - Failed: 1, Passed: 9, Total: 10
```

Restored: `Passed! - Failed: 0, Passed: 10, Total: 10`. The empty collection *is* the bug — the item
is simply gone from the shopper's bag with no message.

### 5.2 A sold-out add told the shopper and then un-told them (a real product bug, found by `bag.e2e.ts`)

`CartStore.add` sets the message on a 409 **and** re-reads the bag, because the stock has moved. The
successful read then cleared the message:

```
× the bag › adding › a size that sells out between the page load and the click says so
  Error: expect(locator).toContainText(expected) failed
  Expected substring: "sold out"
  Error: element(s) not found
```

Fixed by threading `keepMessage` through the read: a read's own success says nothing about whether the
add succeeded, so it must not answer for it. The unit regression test
(`says a sold-out add is sold out, and re-reads the bag because the stock has moved`) with the fix
reverted:

```
× CartStore › adding (PDP-03) › says a sold-out add is sold out, and re-reads the bag…
  AssertionError: the given combination of arguments (null and string) is invalid…
  (store.error() was null)
Tests  1 failed | 809 passed
```

Fix restored: `Tests  810 passed`. And the browser test green.

### 5.3 The header bag control navigated and closed its own drawer

The first version used `routerLink="/bag"` with `preventDefault()`. `RouterLink`'s own click handler
navigates **whether or not the event was default-prevented**, so the drawer opened and the router then
went to `/bag`, whose `NavigationEnd` closed it again:

```
× SiteHeader › the bag control › opens the mini bag on a plain click instead of navigating
  expected 'false' to be 'true'   (aria-expanded)
```

Fixed with a plain `href="/bag"` and no `RouterLink`: the anchor is inert until the handler runs, and
before hydration it is an ordinary link to an ordinary page. Modified and middle clicks are left to
the browser, each with its own test.

### 5.4 Four test defects of my own, each kept as a comment at the site

- **Two "different" variants were the same variant.** Two separate "first in-stock variant" queries
  returned the same id, so a round added 1 + 8 to one row and the insert-race assertion read 9 instead
  of 8. A race test whose two variants are one variant measures nothing.
- **A helper disposed its scope before its query ran** (`return` inside `using var scope`), failing two
  merge tests with `Invalid operation. The connection is closed.`
- **`%00` in a path tests the harness, not the server.** `TestHost` refuses to build the request
  (`PathString.FromUriComponent`: "The path contains null characters"), so nothing reaches the server.
  Replaced with `%20` and the reason written down.
- **Counting a product name is a bound somebody has to guess.** "ships the bag once, not twice" guessed
  ≤ 8 and the real figure was 9 (the link plus two aria-labels). Now counts `"itemsSubtotal"` and
  `"unitPriceAtAdd"`, which exist nowhere but in a serialised `CartDto`, and asserts exactly one of
  each.
- **A class name is in every document's `<head>`.** "a page that is not the bag carries no bag
  contents" asserted on `mini-bag__line`, which Angular inlines into every page's stylesheet. Now
  asserts on the payload keys.
- **`parseInt('1e9')` is 1.** The bag's typed-quantity handler would have set the quantity to one for
  a shopper who typed `1e9`. Now a digits-only pattern; anything else, and anything below 1, puts the
  box back to the quantity the bag already holds and sends nothing. Doc 04 §4's "clamp to the maximum"
  still applies above the ceiling, because "99" against a ceiling of 4 is an unambiguous instruction.
- **Chromium's focus modality.** The focus-ring test pressed Tab *before* a mouse click, which undoes
  it, and reported all four ring edges missing on a button that paints one perfectly. Tab now comes
  after the click, and each control is asserted `:focus-visible` before being measured — without that
  guard "no edges missing" is meaningless.
- **The quantity stepper always has one disabled button** at the ends of its range (minus at 1, plus at
  the stock ceiling), and a disabled control cannot take focus. The ring test now uses a variant with
  four in stock and sits at two.

### 5.5 Issue #47 does **not** reproduce on these endpoints

The bag's writes were written first in the plain `[FromBody]` shape, and every body shape #47 names was
measured:

```
{bad} · {"variantId":"abc"} · {"quantity":"abc"} · (empty) · null · [] · "just a string" · {"quantity":1}
→ 400 on all eight.  Passed: 30, Failed: 1, Total: 31   (the one failure was the %00 harness case above)
```

So **#47 is not a global property of this host's body binding** on .NET 10 minimal APIs, and no
hand-rolled body reader was added. One difference I can see, offered as a lead rather than a
diagnosis: the cart request records use **value types** (`int`), so an absent or null field binds to 0
and is then validated, whereas `AdminLoginRequest(string Email, string Password)` uses non-nullable
reference types, where an absent or null field binds `null` and reaches code annotated as non-null.
Whoever picks up #47 should reproduce it against those endpoints. The eight shapes are now a
regression guard on the bag, in `CartRequestValidationTests`.

## 6. SSR: what is and is not in the document

- **`/bag` renders server-side.** `BagPage` reads the cart from its constructor, so the request is in
  flight before the first change detection and the HTML carries the lines rather than a spinner.
- **`cartCookieInterceptor`** copies `sd_cart` — **and only `sd_cart`** — onto the SSR process's call
  to the API. The same browser may be carrying `sd_admin_auth`; relaying a staff session from the SSR
  process would hand the storefront an authenticated identity it has no business holding. It applies
  only to `/api/cart`, and matches an absolute URL too, because `apiBaseUrlInterceptor` rewrites the
  URL in the same chain.
- **A read never creates a cart** (doc 08 §3.5), so SSR never needs to deliver a `Set-Cookie` it has no
  way of relaying. Every mutation happens in the browser, where the round trip is the browser's own.
- **`/bag` answers `Cache-Control: no-store, no-cache, private` and `Vary: Cookie`**, and `noindex`
  (cleared on the way out, as the not-found page does). A shared cache holding this document would hand
  one shopper another shopper's bag.
- **No other page carries bag data.** The header count is taken up after the first render, exactly as
  the wishlist count is, so an ordinary page's markup stays visitor-independent and cacheable. The mini
  bag's list renders only once the drawer has been open — `sd-drawer` keeps its panel in the DOM when
  closed, so anything in its body would otherwise be in the HTML of every page.
- **The bag travels once.** `withNoHttpTransferCache()` is already on; the store takes the single
  explicit handover in its **constructor**, which is load-bearing: the header is created before the
  routed page, so a later take would mean the browser's first render showed a count of 0 against a
  server-rendered badge of N — a hydration mismatch.
- Asserted on the wire: no cart token in the HTML, no `sd_cart`, no internal API host, no
  `API_INTERNAL_URL`, exactly one copy of the payload, and `href="/bag"` present in the server HTML
  before any script has run.

### The screen reader, and the two live regions

There are two `role="status" aria-live="polite"` regions and **exactly one ever holds text**. A dialog
with `aria-modal="true"` can hide everything outside it from a screen reader, so a change made inside
the open drawer is announced from inside it (doc 04 §4 says exactly this), while a change made on the
bag page with the drawer shut is announced from outside, because the drawer's contents are not in the
accessibility tree at all. Both holding the sentence would announce it twice. An identical sentence
gets a trailing space, because a live region only speaks when its text changes — without it, two
removals in a row would be announced once.

## A2. Two W2-10 behaviours my branch had to meet

### A2.1 `robots.txt` — the `Disallow` had to come out, not go in

My §9 item 5 said there was no `robots.txt` at all. True at `5b5d3f8`. W2-10 added one — and it already
carries **`Disallow: /bag`**, added while `/bag` was still a redirect to the home page with no `noindex`
of its own to protect.

That line and the bag page's `noindex` do not reinforce each other, which is W2-10's own argument for
`/search`: a crawler that may not fetch a page never reads its `noindex`, and a URL it keeps finding
links to can still be listed bare. **Decision: remove `Disallow: /bag`, keep the `noindex`.** Three
reasons, in order of weight:

1. **`/bag` is linked harder than `/search` is.** The header renders a real `<a href="/bag">` on *every
   page of the site* — deliberately, so the link works before hydration — which is exactly the condition
   that makes a `Disallow` counterproductive rather than merely redundant.
2. **Allowing the fetch is what makes the tag work**, and the tag is the only mechanism that actually
   removes a URL from an index.
3. **Letting a crawler fetch the bag is free and safe.** Doc 08 §3.5 creates the cart row on the first
   Add to Bag and never on a page view, so a crawl inserts nothing and gets no cookie — asserted in
   `seo.e2e.ts`. With no cookie it renders the empty bag.

`/account` and `/checkout` stay disallowed, and the file now says why they are different: neither page
exists, and both will sit behind authentication, where a crawler gets a redirect or a 401 rather than a
page that could carry a `noindex` at all.

**`Cache-Control: no-store` and `Vary: Cookie` on `/bag` are untouched.** They are about shared caches,
not crawlers, and nothing here weakens them.

Tests updated to match, with the reasoning at each: `robots-txt.spec.ts` (the session list, and the
"does not disallow" case is now a two-case `it.each`), and `seo.e2e.ts` (the session list, the
"does not disallow" case, `/bag` removed from "still reaches the home page while its page is unbuilt",
and **a new test** that `/bag` answers 200, carries the `noindex`, and sets no cookie — the half of

### A7-ish: one of mine was flaky, and the cause was a bad hydration signal

The first full run after the rebase was **603 passed, 1 failed**, and the failure was this branch's own:
`bag.e2e.ts` — "clamps a typed quantity that is over the stock" — `toHaveValue` on the quantity box. It
then passed **six times out of six** on its own.

Not written off as contention. The cause is a defect in the test, and in a shape worth naming: **the bag
page is server-rendered, so `.bag__line` is in the document before a line of JavaScript has run.**
Waiting for it proves the server answered, not that the page is alive. Under a full-suite load that gap
is wide enough to lose an event — `fill('99')` dispatched `change` before the listener existed, the
handler never ran, and the box kept `99`.

Fixed for the whole class rather than the one test. `openBagPage(page, items)` waits for the header's
**bag badge**, which is the one thing on that page that *cannot* be server-rendered: `StorefrontCounts`
takes the count up inside `afterNextRender`, which never runs on the server (deliberately — a count in
the markup would make every page per-visitor). A badge with a number in it *is* hydration, observed.
All nine `/bag` navigations in the suite go through it.

`addFromProductPage` had the same latent hole and got the same treatment, using the signal the product
page's own suite already uses and documents: the PDP-07 `localStorage` entry, written as the last thing
the page does. `toBeEnabled()` on Add to Bag was never a hydration check — the button is
*server-rendered enabled* when the URL settles a variant, so the actionability check passes on a control
whose click handler does not exist yet.

## A5. One thing fixed on principle, and one issue filed

**`CartReader` was a fourth definition of "visible".** W2-10 added `CatalogVisibility` — "whether a
shopper can reach this address, written once" — with a convention test over `SpencerDenim.Infrastructure`.
That test **does not reach `CartReader`**, because the sweep keys on
`dbContext.(Departments|Categories|Products)` and the cart reader queries `CartItems` and
`ProductVariants`. So 921 unit tests passed with the rule spelled out a fourth time, which is the exact
situation that test's own docblock was written about ("the tester reverted all three to inline predicates
and 887 unit plus 511 integration tests passed").

Fixed rather than left for the tester: `FindSellableVariantAsync` now composes
`CatalogVisibility.VisibleProduct`. That meant starting the query at `Products` and `SelectMany`-ing into
its variants, because an `Expression<Func<Product, bool>>` cannot be invoked against `variant.Product`
inside an EF predicate without an expression rewriter; it produces the same single join. The variant's
own `IsActive` stays local, which is what `CatalogVisibility` says it should (a variant is not an
address). All 66 cart integration tests still pass.

`CartReader.ReadAsync` **cannot** compose it, for the opposite of the usual reason: it must not *filter*.
A withdrawn line has to stay on the page, named, unpriced and removable, so the rule is needed as data
about a row rather than as a `WHERE`. That is recorded in `CatalogVisibility`'s own docblock beside the
`HomeContentReader` case, which is the precedent that file already set.

**And then the fix tripped the test**, which is worth recording because it is the opposite of the usual
order. Moving the query to `dbContext.Products` is what brought the file into the sweep at all, and the
statement that composes `VisibleProduct` also carries `.Where(variant => … variant.IsActive)` — the
*variant's* switch, which `CatalogVisibility` deliberately leaves local:

```
Only_CatalogVisibility_decides_whether_an_address_is_reachable [FAIL]
  src/backend/.../Sales/CartReader.cs:143 queries Products and decides visibility itself
Failed!  - Failed: 1, Passed: 920, Total: 921
```

The failure message offers two outs — compose it, or add the file to `MayDecideForThemselves` with the
reason — and the second is the right one here, for `ReadAsync`'s sake rather than the regex's. The
alternative was splitting the query across two statements so the `IsActive` no longer shares a statement
with `dbContext.Products`, and that would have passed while shaping code around a pattern and leaving
`ReadAsync` undocumented by any test (the sweep never reaches it: it queries `CartItems`). The list entry
names **both** halves — what composes, what cannot and why, and that the switch the sweep sees is the
variant's — which is what that list is for: "adding a fourth is a deliberate edit to this list with a
sentence attached". 921 unit tests green after it.

**Filed as #92** — the axe **incomplete** results across the storefront (the hero/banner and
sold-out-swatch `color-contrast` at serious, the `aria-haspopup`/`aria-controls` pattern at critical,
the `no-autoplay-audio` moderate). The harness reads `violations` only, so nothing looks at
`incomplete`, at any impact — and axe will never decide those on its own; a person has to. The issue
