## Decisions

**A product's slug stays editable; a department's name and slug do not.** Doc 11 P1's business rules state
the answer outright — "Slug change after first publish shows a 'this breaks existing links' confirmation;
redirects are not in v1" — and the reasoning holds: a department slug is the first segment of every listing
URL beneath it, a product slug is one page's URL, and products are corrected constantly in the first weeks
of a season. Freely editable before first publish; afterwards only with `confirmSlugChange`, otherwise a
409 `slug_change_needs_confirmation` naming both slugs so the screen can put the warning in front of the
admin. `CK_Products_Slug` makes the grammar direct-SQL-proof, which is the other half of the W1-02
follow-up. **A rename never touches the slug**: a product that has been published has links to its slug,
and fixing a typo in the name is not a request to break them.

**Media is addressed by `MediaAsset.PublicId`, not by the internal id.** That is ADM-22's convention and its
reason: an internal id is a sequential integer, and taking one on a write makes enumeration the key to
attaching somebody else's asset. **This is inconsistent with ADM-11**, which takes `imageAssetId` as an
`int` on the category routes — see *For the owner* below.

**`media: null` leaves the photographs alone; `media: []` clears them.** Conflating those is the W1-12
defect (every save silently cleared a block's images, missed by 1,571 tests because every fixture had those
columns null). It is guarded at both ends: the API treats an absent field as "say nothing", and the form
only sends the field once the gallery has actually been touched — and the API client *deletes* the key
rather than leaving it `undefined`, so the contract does not depend on the serialiser.

**Move up / Move down, never drag and drop**, for colourways, the variant matrix and the gallery. The
owner's decision of 2026-10-02 for ADM-11 (`docs/11` P1 step 4) carried over unchanged.

**The variant matrix is cards, not a table.** A 6 × 8 table scrolls sideways on a phone, and doc 02's
audience is largely on Sri Lankan mobile data. Measured at all eight breakpoints: no horizontal overflow.

**An ordered variant is never dropped by the form.** Doc 08 §3.2 keeps it for ever and the API refuses the
delete with 409 `variant_has_orders`; the form makes that unreachable by keeping the row, switched off and
visible, when its size is unticked. A row that simply vanished would produce a 409 about a row that was no
longer there to explain it.

**Video limits** are the library's, not new ones: MP4 only, checked by **file signature** rather than by
filename, at most **50 MB** (`MediaLimits.MaxVideoBytes`, the ceiling of `CK_MediaAssets_SizeBytes`), poster
image required, no H.264 track refused. There is deliberately **no second upload path**: the form posts to
`POST /api/admin/media/videos` (W1-04) and sends the `publicId` back. The form also refuses an over-size
file before it uploads anything, which on a mobile connection is the difference between an instant answer
and a wasted 50 MB. One video per product (doc 11 P1 step 11), never the card image.

## Surprises worth the next person's time

**The stale-build trap, twice in one session.** `dotnet ef migrations has-pending-model-changes --no-build`
reported "changes have been made to the model" right after the migration that answered them — because the
assembly on disk predated the migration. One rebuild and it was clean. And later: `ng build admin` failed
on a syntax error and I ran Playwright anyway, which reported **38 failures** that were all one broken
build. Build, read the build output, *then* verify.

**Backticks in an Angular `styles:` template.** A CSS comment containing `` `disabled` `` terminates the
template literal. Two separate build failures, both from a comment.

**`[name]` on an input with `ngModel` does not set the DOM attribute.** `name` is an `@Input` of `NgModel`,
so `[name]="'colour-name-' + i"` binds the directive and renders nothing. A Playwright selector of
`input[name^="colour-name-"]` matched nothing and the test failed for a reason that was not the screen.

**Playwright's `toBeDisabled()` counts `aria-disabled="true"` as disabled.** So
`expect(button).not.toBeDisabled()` is the wrong assertion for the ADM-22 fix. What has to be true is the
DOM property, plus "still focusable".

**Playwright caps an in-memory `setInputFiles` buffer at 50 MB**, which is exactly the boundary the video
limit test is about. The file has to go to disk.

**A second worktree's Playwright server was holding a port.** `4515` was `sd-quickview`'s admin stub, and
the **fixed** storefront stub ports (4420–4433) collide between worktrees — only `E2E_ADMIN_PORT` is
derived from the worktree path. I overrode every `E2E_*_PORT` into the 4620s rather than killing anything;
`playwright.config.ts` should derive all of them the way it derives the admin one. `charon-svc.exe` still
holds 4502; untouched.

**A live test database can read zero sessions, so session count is not proof of ownership.** `MEMORY` and
the brief both say to read a database's creation time and owning process before dropping it, and that is
right — but I nearly refined it into "0 sessions means dead", which is false. Another agent's
`SpencerDenim_Test_*` showed **32** sessions on one reading and **0** thirty seconds later: the connection
pool drains between tests. Two checks thirty seconds apart is what saved it. I left four
`SpencerDenim_Test_*` databases in place rather than guess; three are probably mine, from runs I had to
kill, and whoever cleans up should check the same way.

**The integration suite hung once, and the hang cost two runs.** `dotnet test` sat with a live `testhost`,
no SQL request in flight and no CPU movement for twenty minutes, after a previous run of the same suite had
been killed mid-flight. Killing the test host to unblock a rebuild also silently loses the run's result
line — the parent `dotnet test` exits 0 with nothing but its header in the log, which looks like a clean
run to anything that greps for failures. Two lessons: a killed suite leaves an orphan
`SpencerDenim_Test_<guid>` database (drop your own; read the creation time first), and the
`SpencerDenim.IntegrationTests.exe` self-host keeps the DLLs locked after the test host is gone, so a
rebuild needs both stopped.

## The defect only a real database could find

**Removing a variant from a product answered 500.** Two foreign keys stood in the way, and the unit suite
could not see either of them because the fake store just drops a row from a list:

1. `FK_StockLevels_ProductVariants_VariantId` is `NO ACTION`, so a variant cannot leave the table while its
   1:1 stock row points at it. `EnsureStockRowsAsync` had just created that row.
2. `ProductVariants (ProductColourId, ProductId)` onto `ProductColours` is a *required* composite key with
   `NO ACTION`, and EF's default `CascadeTiming.Immediate` tries to null it the instant a colourway leaves
   `Product.Colours` — before the variants have been marked for deletion at all. The exception is
   *"the association between entity types 'ProductColour' and 'ProductVariant' has been severed"*, and it
   is thrown from a `DetectChanges` several statements later, which is why the 500 pointed nowhere useful.

The fix is three parts. The store deletes variants **explicitly**
(`IProductWriteStore.RemoveVariantsAsync`) and takes their stock rows with them; the store sets
`CascadeDeleteTiming` and `DeleteOrphansTiming` to `OnSaveChanges`, so the whole intended end state is
assembled before EF works out the cascades once; and **a variant that holds stock is no longer deletable at
all** — it is kept and switched off, like an ordered one, because deleting it would take a count of real
garments with it and stock belongs to ADM-12's ledger. The 409 is now `variant_not_deletable` with
`orderedSkus` and `stockedSkus` listed separately, and the form keeps both kinds of row visible.

This is worth the next person's time twice over: **the cascade timing is a property of this unit of work**,
and any future aggregate that removes a parent and its `NO ACTION` children in one save will hit the same
wall; and **the whole thing was found by writing an integration test for a case no unit test could cover**,
after 1,312 unit tests and 42 browser tests were green.

**And a second one in the same place: a size added to an existing product got no stock row.** Doc 11 P1
step 10 creates one "for every new variant", and the create path did — the *edit* path did not, so a size
added later was invisible to the availability join `ProductCatalogReader` uses, read as out of stock for
ever, and gave ADM-12 nothing to update. The row is now carried on `ProductVariant.StockLevel`, so it is
part of whichever save created the variant rather than of one of them.

## For the owner

- **`ProductsAttributes` / reference data has no screen.** Doc 11 §7 G-02's default puts attribute options,
  colour families, sizes and age groups under `Products.Edit`, and ADM-10 does not list a screen for them.
  The product form can only choose from what the seeder put there. A new colour family or a new size scale
  still needs a migration or a SQL statement. Worth a decision before the client starts loading stock.
- **Media is addressed two different ways in the admin API**: `publicId` (Guid) on products and settings,
  `imageAssetId` (int) on categories. The product routes follow the newer and better-argued convention; the
  category routes are the ones that should change, which is W1-12's to fix rather than mine to alter under
  it.
- **A variant that holds stock can no longer be deleted from the product form**, only switched off. That
  is a decision this task had to make because the database forced it, and it is defensible — but if the
  client wants a mistyped size with stock against it genuinely removed, that needs an ADM-12 action that
  writes an `Adjustment` movement to zero first. Worth confirming.
- **There is no media library screen (ADM-18), so every product photograph is uploaded from the product
  form.** Re-using one photograph on a second product means uploading the same file again — which is not
  as bad as it sounds, because `MediaService` de-duplicates by SHA-256 and hands back the existing asset,
  so nothing is stored twice. But there is no way to *browse* what has already been uploaded.
- **`Category.SizeGuideId` is still read by nothing.** The product form offers the product's own size guide,
  as doc 08 §3.2 specifies; the "inherit from the nearest ancestor category" rule remains a design note.

# Round 2 — the tester's FAIL, and what it was really about

The independent tester returned **FAIL with five Majors**. Three of the five were one mistake, made once
and believed everywhere, so they are worth recording together rather than as a list of fixes.

## The one mistake: a vocabulary nobody agreed on

`Program.cs` registers a global `JsonStringEnumConverter`, with a comment saying why: "enums travel as
their names, so a client never has to keep a copy of our numeric values in sync." Every **response** in
this API therefore carries `"Sale"`, `"Gallery"`, `"Image"`. My **write** contracts declared `int?`.

So the admin product API could not read back what it had just written. Three of the tester's findings fall
straight out of that:

- **M1** — `POST` with `badgeOverride: 1` answered **500**. `Enum.IsDefined(typeof(ProductBadge), 1)`
  throws `ArgumentException` when the boxed argument's type is not the enum's underlying type, and
  `ProductBadge` is a `byte` enum. A validation guard that crashes instead of validating.
- **M2** — `mediaRole: "Gallery"`, which is exactly what `GET` had just returned, was a **400**.
- **m1** — the read and write halves of one resource disagreed, with nothing anywhere asserting they
  agreed.

The fix is the representation, once: the write contracts now take the **names** too, and refuse a numeric
string outright even though `Enum.TryParse` would happily accept `"1"` as `New`. That last part came from
my own new test going red — the first version of the fix accepted `"1"`, because `1` is a real member and
`TryParse` reads digits.

Two things now hold it in place:

- `ProductRequestMapperTests` — **52 cases** over the mapper that did not have a single test before, which
  is the whole reason M1 shipped.
- `AdminProductEnumContractTests` — reads `admin-product.model.ts` and `admin-product-stub.mjs` and asserts
  their string unions **equal** `Enum.GetNames<…>()`, that the badge union excludes `LowStock` (computed at
  read time, never stored), and that neither file assigns a *number* to an enum field. The TypeScript cannot
  drift from the C# again without a backend test failing.

**The tester was right to forbid re-running Playwright and Vitest before the stub was fixed.** The browser
stub spoke the numeric dialect, so the browser suite was green against a contract the server does not have.
Green there was evidence of nothing, and that is precisely how this shipped.

## M3 — a size in a shopper's bag

Removing a colourway deleted its variants, and `sales.CartItems` has an `ON DELETE NO ACTION` foreign key
onto them, so the delete answered **500** whenever any shopper had that size in their bag.

Rather than add a second hand-written delete, `VariantReferences` in the domain now names every table that
references a variant and what should happen to it — `StockLevels` and `CartItems` go with the variant,
`OrderLines` block the delete — and a model convention test walks the EF model and fails when a new
reference appears that the list has not been told about. `inventory.InventoryMovements` (**#108**) does not
exist yet; the docblock records that it must be `BlocksTheDelete` when ADM-12 adds it. Issue #108 is
therefore pre-registered rather than a future 500.

## M4 — a live product edited into a state it could not be published in

Doc 11 §7 G-01's checklist ran only on the publish **transition**. So `PUT /products/45` with `media: []`
answered **204** on a published product and left it on the shop with no photographs and a null card image —
and the storefront then served that product **200 with zero images**. A shopper saw a live product with
nothing to look at; the admin saw a 204 saying it had worked.

Refused with **409 `published_product_would_break`** and the blockers, not auto-unpublished. Taking a
product off the shop is its own deliberate act with its own `StatusChange` audit row, and a 204 that had
quietly removed a product from the shop would be discovered days later.

## m3 — four more ways to lose work silently

`AdminProductRequests` documented the rule for every collection — a null list means "this request says
nothing about it", an empty list means "make it empty" — and the mapper then manufactured an empty list for
four of the five. Omitting `extraCategoryIds` unlinked every extra category; omitting `variants` deleted
every size the guards allowed; `colours` and `relatedProducts` the same. All with a 204.

This is **W1-12's defect again, in four new places**, and the comment claiming otherwise is why nobody
looked. The distinction now holds end to end, and `[]` still clears.

Fixing it also caught a regression I introduced doing it: an early return skipped the Kids age-group rule
below it. `ProductWriteHandlerTests.A_kids_product_without_an_age_group_is_refused_by_name` went red, the
block moved above the guard, and the comment there now says why the order matters.

## m6 — an accessibility rule that could never fire

The form uploaded every photograph with `altText = product name || file name`, and the publish checklist
accepts the library asset's own alt text. So G-01's third rule **could never block anything**: every
picture arrived already "described". A shopper using a screen reader would have heard the product's name
read out once for each of its six photographs, which is worse than silence because it sounds like a
description.

Product uploads now send no alt text at all. The browser stub was inventing one of its own on every image
upload, which disabled the rule there too; it now echoes the field it was sent.

## n1 — the nit that was not a nit

The tester reported one serious axe `target-size` on the colour name input at 1280 px, and noted my "axe
clean" claim held at 320 px and on the list but not at desktop width. Measuring it properly made it much
worse than a nit.

`.form__actions` was `position: sticky; bottom: 0` over an **opaque** panel. While stuck it covered
whatever was behind it: scrolling the form at 320 px put the save bar over `field-care`, every media row's
alt text box and the related-product buttons — **44 px of each, their whole height**, so they could not be
clicked at all until the admin nudged the page. axe names whichever control happens to sit at the
viewport's bottom edge, which is why the finding looked flaky and why it moved as content changed.

The bar is now in flow, like every other admin screen's. A new layout test scrolls the form in
viewport-height steps at all eight widths and asserts no control is covered; it failed with **17 covered
controls** before the change.

## Found while fixing, not reported by anyone

**`GET /products/{id}` reported `cardImageUrl` and `hoverImageUrl` as null for every product**, however
full its gallery. The detail read loads a tracked graph rather than a projection — deliberately, so the
publish checklist is the same function the API refuses with — and a tracked graph has to be told to
`Include` a navigation. `CardImageAsset` and `HoverImageAsset` never were. The denormalised columns behind

It surfaced because the M4 test asserted a live product still had a card image after a refused save, and
failed for the wrong reason. Nothing in the admin renders either field today, so no screen was visibly
wrong — the payload was simply lying, and the next consumer would have believed it.

lists this branch's own files too, as reversed changes, so intersecting that with anything reports almost
every file as a conflict. Only `git diff <merge-base> origin/main` against `git diff <merge-base> HEAD`
answers the question.

### Migration ordering, and one artefact of it

Checkout's `20261005074430_CheckoutReferenceData` sits **before** `20261006042018_ProductSlugCheckConstraint`,

**One artefact to know about, deliberately left:** this migration's `.Designer.cs` snapshot is the model as
it stood *before* checkout, because it was generated before checkout existed and now sits after it. It has
zero references to `Provinces`. That costs nothing in practice — migrations are applied by running `Up()`
in order, and the only snapshot EF diffs against is `AppDbContextModelSnapshot.cs`, which is complete and
which `has-pending-model-changes` confirms. But it gives the standing ban on `dotnet ef migrations remove`
a second, concrete reason on this branch: `remove` restores the last migration's Designer snapshot into the
top-level one, which here would silently delete checkout's model from it.

### The one piece of new work: reachability

`measure.ts` arrives with `unreachable()`, and this screen has now been wrong about two of the three
questions those helpers answer:

1. **Big enough** — `undersized()`. The size and category ticks were 36–41 px at 320 px.
2. **Not buried** — the save-bar test. An opaque sticky bar covered 17 controls at 320 px.
3. **On the screen at all** — never asked until now.

Two tests added: every control on the form at all eight widths, and both confirmation panels at
**320 × 568**, the shortest phone doc 04 §4 implies — height is what catches this class of bug and the
rest of the layout block uses 720 or 900. A panel the admin cannot finish is a product they cannot rename
or remove, and the press that opens it has already decided to do the thing. The list's row actions get the
same question.

*Proved* by pinning `.form__actions` 200 px below the viewport with `position: fixed`, which is the shape
of W2-04's MAJOR 1: the reachability test fails with **23 unreachable controls** and Save **79 px past the
fold**, while **"every control on the form is at least 44 px at 320 px" still passes**. That one run is
the entire argument for the helper.

And `unreachable`'s refusal to measure nothing (#80) earned itself on the way in. The first version of the
panel test asked for `[data-testid="confirm-slug"] button` — but that test id is on the button itself, not
on a panel, so the selector matched nothing and the test would have passed as a check that could not fail.
It threw instead. That is a real red, not a staged one, and it is the second time this round a new
guard caught my own mistake rather than somebody else's.
