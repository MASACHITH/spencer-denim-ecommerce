## Decisions

**A product's slug stays editable; a department's name and slug do not.** Doc 11 P1's business rules state
the answer outright — "Slug change after first publish shows a 'this breaks existing links' confirmation;
redirects are not in v1" — and the reasoning holds: a department slug is the first segment of every listing
URL beneath it, a product slug is one page's URL, and products are corrected constantly in the first weeks
of a season. Freely editable before first publish; afterwards only with `confirmSlugChange`, otherwise a
409 `slug_change_needs_confirmation` naming both slugs so the screen can put the warning in front of the
admin. `CK_Products_Slug` makes the grammar direct-SQL-proof, which is the other half of the W1-02
follow-up. **A rename never touches the slug**: a product that has been published has links to its slug,
and fixing a typo in the name is not a request to break them.

**Media is addressed by `MediaAsset.PublicId`, not by the internal id.** That is ADM-22's convention and its
reason: an internal id is a sequential integer, and taking one on a write makes enumeration the key to
attaching somebody else's asset. **This is inconsistent with ADM-11**, which takes `imageAssetId` as an
`int` on the category routes — see *For the owner* below.

**`media: null` leaves the photographs alone; `media: []` clears them.** Conflating those is the W1-12
defect (every save silently cleared a block's images, missed by 1,571 tests because every fixture had those
columns null). It is guarded at both ends: the API treats an absent field as "say nothing", and the form
only sends the field once the gallery has actually been touched — and the API client *deletes* the key
rather than leaving it `undefined`, so the contract does not depend on the serialiser.

**Move up / Move down, never drag and drop**, for colourways, the variant matrix and the gallery. The
owner's decision of 2026-10-02 for ADM-11 (`docs/11` P1 step 4) carried over unchanged.

**The variant matrix is cards, not a table.** A 6 × 8 table scrolls sideways on a phone, and doc 02's
audience is largely on Sri Lankan mobile data. Measured at all eight breakpoints: no horizontal overflow.

**An ordered variant is never dropped by the form.** Doc 08 §3.2 keeps it for ever and the API refuses the
delete with 409 `variant_has_orders`; the form makes that unreachable by keeping the row, switched off and
visible, when its size is unticked. A row that simply vanished would produce a 409 about a row that was no
longer there to explain it.

**Video limits** are the library's, not new ones: MP4 only, checked by **file signature** rather than by
filename, at most **50 MB** (`MediaLimits.MaxVideoBytes`, the ceiling of `CK_MediaAssets_SizeBytes`), poster
image required, no H.264 track refused. There is deliberately **no second upload path**: the form posts to
`POST /api/admin/media/videos` (W1-04) and sends the `publicId` back. The form also refuses an over-size
file before it uploads anything, which on a mobile connection is the difference between an instant answer
and a wasted 50 MB. One video per product (doc 11 P1 step 11), never the card image.

## Surprises worth the next person's time

**The stale-build trap, twice in one session.** `dotnet ef migrations has-pending-model-changes --no-build`
reported "changes have been made to the model" right after the migration that answered them — because the
assembly on disk predated the migration. One rebuild and it was clean. And later: `ng build admin` failed
on a syntax error and I ran Playwright anyway, which reported **38 failures** that were all one broken
build. Build, read the build output, *then* verify.

**Backticks in an Angular `styles:` template.** A CSS comment containing `` `disabled` `` terminates the
template literal. Two separate build failures, both from a comment.

**`[name]` on an input with `ngModel` does not set the DOM attribute.** `name` is an `@Input` of `NgModel`,
so `[name]="'colour-name-' + i"` binds the directive and renders nothing. A Playwright selector of
`input[name^="colour-name-"]` matched nothing and the test failed for a reason that was not the screen.

**Playwright's `toBeDisabled()` counts `aria-disabled="true"` as disabled.** So
`expect(button).not.toBeDisabled()` is the wrong assertion for the ADM-22 fix. What has to be true is the
DOM property, plus "still focusable".

**Playwright caps an in-memory `setInputFiles` buffer at 50 MB**, which is exactly the boundary the video
limit test is about. The file has to go to disk.

**A second worktree's Playwright server was holding a port.** `4515` was `sd-quickview`'s admin stub, and
the **fixed** storefront stub ports (4420–4433) collide between worktrees — only `E2E_ADMIN_PORT` is
derived from the worktree path. I overrode every `E2E_*_PORT` into the 4620s rather than killing anything;
`playwright.config.ts` should derive all of them the way it derives the admin one. `charon-svc.exe` still
holds 4502; untouched.

**The integration suite hung once, and the hang cost two runs.** `dotnet test` sat with a live `testhost`,
no SQL request in flight and no CPU movement for twenty minutes, after a previous run of the same suite had
been killed mid-flight. Killing the test host to unblock a rebuild also silently loses the run's result
line — the parent `dotnet test` exits 0 with nothing but its header in the log, which looks like a clean
run to anything that greps for failures. Two lessons: a killed suite leaves an orphan
`SpencerDenim_Test_<guid>` database (drop your own; read the creation time first), and the
`SpencerDenim.IntegrationTests.exe` self-host keeps the DLLs locked after the test host is gone, so a
rebuild needs both stopped.

## The defect only a real database could find

**Removing a variant from a product answered 500.** Two foreign keys stood in the way, and the unit suite
could not see either of them because the fake store just drops a row from a list:

1. `FK_StockLevels_ProductVariants_VariantId` is `NO ACTION`, so a variant cannot leave the table while its
   1:1 stock row points at it. `EnsureStockRowsAsync` had just created that row.
2. `ProductVariants (ProductColourId, ProductId)` onto `ProductColours` is a *required* composite key with
   `NO ACTION`, and EF's default `CascadeTiming.Immediate` tries to null it the instant a colourway leaves
   `Product.Colours` — before the variants have been marked for deletion at all. The exception is
   *"the association between entity types 'ProductColour' and 'ProductVariant' has been severed"*, and it
   is thrown from a `DetectChanges` several statements later, which is why the 500 pointed nowhere useful.

The fix is three parts. The store deletes variants **explicitly**
(`IProductWriteStore.RemoveVariantsAsync`) and takes their stock rows with them; the store sets
`CascadeDeleteTiming` and `DeleteOrphansTiming` to `OnSaveChanges`, so the whole intended end state is
assembled before EF works out the cascades once; and **a variant that holds stock is no longer deletable at
all** — it is kept and switched off, like an ordered one, because deleting it would take a count of real
garments with it and stock belongs to ADM-12's ledger. The 409 is now `variant_not_deletable` with
`orderedSkus` and `stockedSkus` listed separately, and the form keeps both kinds of row visible.

This is worth the next person's time twice over: **the cascade timing is a property of this unit of work**,
and any future aggregate that removes a parent and its `NO ACTION` children in one save will hit the same
wall; and **the whole thing was found by writing an integration test for a case no unit test could cover**,
after 1,312 unit tests and 42 browser tests were green.

**And a second one in the same place: a size added to an existing product got no stock row.** Doc 11 P1
step 10 creates one "for every new variant", and the create path did — the *edit* path did not, so a size
added later was invisible to the availability join `ProductCatalogReader` uses, read as out of stock for
ever, and gave ADM-12 nothing to update. The row is now carried on `ProductVariant.StockLevel`, so it is
part of whichever save created the variant rather than of one of them.

## For the owner

- **`ProductsAttributes` / reference data has no screen.** Doc 11 §7 G-02's default puts attribute options,
  colour families, sizes and age groups under `Products.Edit`, and ADM-10 does not list a screen for them.
  The product form can only choose from what the seeder put there. A new colour family or a new size scale
  still needs a migration or a SQL statement. Worth a decision before the client starts loading stock.
- **Media is addressed two different ways in the admin API**: `publicId` (Guid) on products and settings,
  `imageAssetId` (int) on categories. The product routes follow the newer and better-argued convention; the
  category routes are the ones that should change, which is W1-12's to fix rather than mine to alter under
  it.
- **A variant that holds stock can no longer be deleted from the product form**, only switched off. That
  is a decision this task had to make because the database forced it, and it is defensible — but if the
  client wants a mistyped size with stock against it genuinely removed, that needs an ADM-12 action that
  writes an `Adjustment` movement to zero first. Worth confirming.
- **There is no media library screen (ADM-18), so every product photograph is uploaded from the product
  form.** Re-using one photograph on a second product means uploading the same file again — which is not
  as bad as it sounds, because `MediaService` de-duplicates by SHA-256 and hands back the existing asset,
  so nothing is stored twice. But there is no way to *browse* what has already been uploaded.
- **`Category.SizeGuideId` is still read by nothing.** The product form offers the product's own size guide,
  as doc 08 §3.2 specifies; the "inherit from the nearest ancestor category" rule remains a design note.
