**Decisions:**

- **The import is a verb on the API** (`import-client-assets --from <dir> [--dry-run]`), not a seeding
  flag and not a tool project. It needs the whole composition root — the configured media volumes with
  their startup validation, the real `IMediaService`, the database — and a seeding flag would tie the
  client's own photographs to `Seed__*`, which means "the shape a development database starts in". It
  never starts Kestrel, so it binds no port.
- **Every byte goes through `IMediaService`.** Nothing in the importer composes a `MediaAssets` row or
  touches a file, so each photograph gets the same signature check, EXIF stripping, rendition set,
  checksum deduplication and usage tracking as an admin upload.
- **The naming contract is a pure function in the Application layer**
  (`ClientAssetNaming`), separate from the importer that reads the disk. The rule that decides *which
  garment a photograph is of* is the one thing here that can go silently and expensively wrong, so it
  is testable exhaustively and without a database. Every repair is bounded by the real slug list; a
  near miss with two answers is refused rather than guessed; anything unplaceable stops the whole run
  before a byte is stored.
- **A product with one photograph gets a card and no hover.** Leaving the seeded placeholder in the
  hover slot would mean a real garment flipping, on hover, to a grey frame that says no photograph was
  supplied.
- **The ten kids' products keep their placeholders.** No adult photograph is put in front of a
  children's garment to fill a gap.

**Surprises worth the other person's time:**

## Fix round 1 (same day)

**Done:** the tester's four majors and two minors on W1-13, plus the two asset decisions. Two more
commits on `feature/W1-13-client-assets`; back with the tester, still not pushed.

**Surprises worth the other person's time:**

- **"All or nothing" was only true of the failure I had thought about.** `IMediaService` saves on the
  shared scoped `AppDbContext` for every upload, so a run that failed at the hero had already committed
  every product before it — 88 assets, 358 files and four homepage sections switched live, under a
  report that said FAILED. If you are writing a multi-step import on this context, it is one transaction
  or it is nothing; and **the transaction has to go inside `CreateExecutionStrategy().ExecuteAsync`**,
  because `EnableRetryOnFailure` is on and that strategy refuses a user-initiated transaction otherwise.
  Clear the change tracker at the top of each attempt.
- **A reference row keyed on the thing it points at cannot express a replacement.** Key it on the slot.
- **A seeded placeholder has to count as "empty"** or "never overwrite a person" can never be
  implemented: on a seeded database every slot is already full.
- **The `aspect-ratio` + `max-height` trap is in exactly three rules in this codebase** — the hero, the
  feature banner and the department tile's media frame. All three have an explicit width now. If you
  write a fourth, give it one, or the e2e test that counts them will fail.
- **A test that writes to the OS temp directory has to clean up after itself.** Mine did not, for one
  run.

**Decisions:** the two bad pictures are held back by the **checksum of the delivered bytes**, not by
section type and not by an operator flag, so the hold releases itself the day a replacement arrives
rather than quietly keeping a finished block off the front page.

**Next:** the tester.

## Fix round 2 (same day)

**Done:** the blocker, two minors and the exit codes. Back with the tester; still not pushed.

**Surprises worth the other person's time:**

- **A refactor can drop an invariant the old code held by accident.** Round 1 keyed a gallery row on the
  asset, which happens to *be* `UX_ProductMedia_Product_Asset_Colour`. Round 2 re-keyed it on the slot —
  the right fix — and nothing then checked the index, so two identical files in one drop crashed the
  import. **If you key a lookup on something other than the table's unique index, check the index
  separately: the database has its own idea of identity and every write has to satisfy both.**
- **A dry run has to resolve identity or it is not a plan.** Ours handed each file a separate nothing,
  so it reported the crashing input as green. It hashes now, exactly as the pipeline does.
- **`UploadVideoAsync` creates a second asset you never see.** Anything cleaning up after a failed run
  has to diff the table, not replay its own bookkeeping.
- **A refused video has its poster rolled back by `MediaService` itself**, so it is useless as a repro
  for "the poster's files were left behind". The hero has to succeed and the run fail afterwards.
- **You cannot press Ctrl+C from this harness at all.** `kill -INT` does not reach .NET's
  `Console.CancelKeyPress` from Git Bash, and the agent's own process has no console and cannot
  `AllocConsole` (ERROR_ACCESS_DENIED), so `GenerateConsoleCtrlEvent` returns true and delivers to
  nothing — confirmed against an import slowed to 61–84 s, signalled at 2.5 s, 5 s and 8 s, finishing
  normally each time. Prove a cancellation path with a seam you control, not with a signal.

**Next:** the tester.

## Fix round 3 (same day)

**Done:** the rollback no longer deletes files belonging to another connection, and a dry run no longer
claims "0 refused". Back with the tester; still not pushed.

**Surprises worth the other person's time:**

- **"Everything new in the table" is not "everything this run made".** Another connection commits
  while you are in flight, and at READ COMMITTED its rows are new to you too. Build a clean-up list
  from what *your* calls returned, never from a diff of a shared table — and if the two disagree,
  prefer the one that cannot over-delete. **A missed file is litter; a deleted file is data loss.**
- **Ask "is this already in the library?" before an upload, not after.** The pipeline deduplicates, so
  afterwards a created asset and a deduplicated one look identical, and deleting the second takes out
  the file somebody else's row points at.
- **The admin upload path commits a `Processing` row and has no transaction**, so you cannot use
  `Status = Processing` to mean "mine". That closes off the obvious way to clean up after an interrupt,
  which is why one asset's files are deliberately left behind on Ctrl+C.
- **A dry run that cannot check a file must not print `0 refused` without saying so.** The caveat
  belongs in the output the operator reads, not only in the method's doc comment.

**Next:** the tester. Ctrl+C still wants a human at a real terminal.
