## 1. The Traffic settings form

- **API:** `PUT /api/admin/settings/traffic`, body `{ rawRetentionDays, botRetentionDays, rowVersion }`, digits as
  text like the screen's other numeric boxes. `UpdateTrafficSettingsCommandHandler` follows the invoice handler's
  order (fields → token → permission over the keys *asked* to write → diff → save) plus one step after permission:
  **bots never longer than people**, compared on the value each key will hold after the save (new where sent,
  stored where not). It runs after the permission check so a caller who may not write the keys learns nothing
  about the stored figures from a 400. A present-but-empty field is **refused**, not cleared (an unset period
  would silently hand the purge back to configuration). One audit row per changed key; an unchanged save writes
  none. Its own save unit (`SettingCatalog.SaveUnits`).
- **Screen:** a "Traffic" panel on Settings, same style as the invoice form (explicit label/id pairs, numeric
  keyboard, hint with the bounds, field errors beside the box, `aria-disabled` save, edits held across the
  re-read). Shown only when the server sends the `Traffic` group.
- **Who may edit: `Settings.Edit` — Super Admin and Store Manager.** Doc 08 §3.8's table gives the group
  `Settings.Edit`, and its N2 sensitive-change trigger list (payments, SMTP, security,
  `Privacy.RetainInvoiceBillTo`) does not include it, so **no Super Admin alert**. docs/02's "legal retention"
  (Super Admin only) is read as the invoice-retention key, which stays `Settings.Security` and deferred. What makes
  delegating it safe is the bounds (below) and the fact that the daily totals are never purged.
  *Recorded as a decision for the owner to confirm*: if "legal retention" was meant to include visit-data
  retention, the change is the catalogue row's permission (the seeder realigns it on the next start) plus raising
  the existing single-send `SensitiveSettingsChangedAlert` from the handler, as the Bank and PayPal handlers do.

### Bounds — chosen from how the purge and rollup use the values

| Key | Form | Configuration (`Traffic__*`, unchanged) | Why |
|---|---|---|---|
| `Traffic.RawRetentionDays` | **30–365** | 4–3,650 | A month of visit-level rows to explain a figure from. (*Revised in the second fix round:* the first rationale — "a short period turns an unnoticed rollup outage into a permanent gap" — no longer holds, because the purge never deletes an unbuilt day and the catch-up has no lower bound.) Above a year raw rows serve no report (daily tables are kept indefinitely) and only keep visit-level rows (random session id) longer. |
| `Traffic.BotRetentionDays` | **7–90**, and ≤ raw | 4–raw | Bot views are counted into `TrafficDaily.BotPageViews` by the same rollup, so the same outage argument; 7 is doc 08's own figure (4 days past the rebuild window). Bots are kept out of every visitor figure, so longer than people has no use. |

The form is stricter than configuration on purpose: it is what a staff user may type, and a purge is irreversible.

### Precedence — the database row wins; configuration is the fallback

`TrafficRetentionPeriods.Resolve` (Domain, pure) is the one place the rule lives:

1. A `Traffic.*` row holding whole invariant digits **inside the form's bounds** is used.
2. Otherwise — no row, empty, text, out of bounds (written by hand), or a row flipped to Secret — the configured
   `Traffic__RawRetentionDays` / `Traffic__BotRetentionDays` is used (already held to 4–3,650 at start-up). Falling
   back rather than clamping, because a clamped value is a number nobody chose.
3. Bots are cut to the raw period if the resolved pair would keep them longer (the form refuses that pair; this
   covers one it never saw).

Why the row wins: it is the value a staff user sees and can change, so it is the one they will believe; an
environment variable silently overriding the screen would make the form lie. The purge (`TrafficRetentionService`)
reads it through `TrafficRetentionSettings` (uncached, nightly). (*Second fix round:* the rollup's catch-up no
longer reads it at all — see §8.) Each purge logs the periods
and their source (event 7131: "from Settings" / "from Configuration"); an ignored non-empty row logs a warning
(event 7133).

**The deployed default is unchanged.** Seeded 90/7 = doc 08 §3.8 = `TrafficOptions` defaults, pinned against the
document's own cell by `The_traffic_retention_fallback_is_the_seeded_value_and_the_documented_default`. Compose did
not pass any `Traffic__*` before, so every existing deployment purged at 90/7 and still does, before and after the
seeder runs.

## 8. Second fix round (tester re-test `0869584`)

**Major — a day the guard kept was never recovered.** The catch-up searched only `today - rawDays`, which is exactly
the window the guard's kept days fall outside, so in production a kept day stayed for ever, event 7134 fired
nightly, and its totals never reached the Traffic page. My own test had called `RebuildAsync` by hand and hid it.

- **Fix:** `TrafficRollupService.RunOnceAsync` now builds the **oldest never-built days that still have raw rows,
  with no lower bound** (`TrafficSql.OldestUnbuiltDaysBefore`, `TrafficRollup.FindOldestUnbuiltDaysAsync`), capped at
  `MaxCatchUpDaysPerRun = 31` a night, oldest first. It reads only days that have raw rows — one range of
  `IX_PageViews_Occurred` over what the purge has kept (≈ the raw period, as before) with `TOP` — and never walks
  empty calendar days. It no longer reads the retention setting. Safe: a purged day has no raw rows and is never
  found, so it cannot store a zero over a real day; an unbuilt day always keeps all its rows (the guard).
- Log 7134 and the docblocks now say what happens: the 00:30 rollup builds such days (up to 31 a night) and the next
  purge deletes them; the same day reported night after night means the rollup is failing on it. The 30-day
  minimum's rationale was rewritten (handler message, admin hint, `SettingKeys`) — it no longer claims a short period
  loses history.
- **Tests on the real path only:** the tester's `A_day_the_purge_keeps_as_unbuilt_is_built_by_the_nightly_jobs_and_then_purged`
  passes unchanged (three nights of `TrafficRollupService.RunOnceAsync` then `TrafficRetentionService.RunOnceAsync`).
  My `After_the_rollup_builds…` and the settings purge test now run the nightly rollup instead of `RebuildAsync`. The
  two tests that pinned "the catch-up stops at the raw period" (mine and the tester's boundary test) were inverted to
  the new behaviour, and `TrafficRollupTests` now expects the old never-built day to be built (filtered to its own year,
  since the unbounded catch-up also builds other classes' leftovers in the shared database). New:
  `The_catch_up_builds_the_oldest_unbuilt_days_first_and_caps_one_pass` (40 scattered days → ≤ 31, oldest first, the
  rest the next pass).

**Minor — flaky plan test.** It pinned a Clustered Index Seek on `PK_TrafficDaily`; once the tables fill the optimiser
picks a Merge Join. It now asserts only that PageViews is read through `IX_PageViews_Occurred` (forced, as the class
does): no Key Lookup, no table scan, no `PK_PageViews` read. The join is not pinned.

**Mutations — 6/6 killed** (filtered `~Traffic` integration suite): catch-up bounded by 30 days again; catch-up
removed; newest first instead of oldest; already-built days not excluded; per-night cap ignored; cap of zero.
