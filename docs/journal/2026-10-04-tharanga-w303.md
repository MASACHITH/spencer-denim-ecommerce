## A real bug the verification caught

The first generated migration was **missing `UX_Payments_OneSettlement` and `IX_Payments_Exceptions`**.
Two `HasIndex(p => p.OrderId)` calls and two `HasIndex(p => p.CreatedAtUtc)` calls: EF treats a second
`HasIndex` over the same property set as *further configuration of the same index*, so each pair silently
collapsed into one and the last one won. It built clean, the model had no pending changes, and every test of
the open-payment rule would have passed — while the "one settling payment per order" invariant did not exist
in the database at all. Fixed with the named `HasIndex(expr, name)` overload; the migration was removed and
regenerated, and I verified the nine Payments indexes against `sys.indexes` on a real database.

**This is the thing I most want the tester to look at.** It is the exact failure mode a schema task has:
an index that is quietly absent breaks nothing until money is involved.

## Decisions doc 08 left open, and how I read them

1. **Four of doc 08's foreign keys are columns with no constraint**, because the table they point at does not
   exist in any migration: `Orders.DeliveryDistrictId` and `PickupLocations.DistrictId` (`ref.Districts`,
   GLB-06 — the `ref` schema has never been created), `Orders.PromoCodeId` (`marketing.PromoCodes`, ADM-13)
   and `OrderLines.SaleCampaignId` (`marketing.SaleCampaigns`, ADM-14). I did **not** drop the columns the
   way W2-09 dropped `Carts.DistrictId`: two of them are `NOT NULL` in doc 08 and the table is unusable
   without them. Each is indexed as if the constraint existed, and a test names all four so that creating
   `ref.Districts` and forgetting the constraint fails rather than passes.
2. **`UX_Payments_Provider_Reference` / `_Txn` — ambiguous in doc 08** ("filtered NOT NULL", no column list).
   I read the names as `(ProviderCode, ProviderReference)` and `(ProviderCode, ProviderTransactionId)`.
   Rationale: the provider is part of the identity of a reference, so two gateways can never be made to
   collide, and the index still seeks "find the payment for this PayPal order" in one go. **Architect: if you
   meant the single column, say so — it is a one-line change now and a migration later.**
3. **The `Delivery` snapshot columns carry no prefix** (`DeliveryMethodCode`, `DeliveryMethodName`,
   `PickupLocationName`, `EstimatedDaysMin`, `EstimatedDaysMax`) while `ShipAddress` uses `Ship_`. That is
   literally how doc 08 §3.5 writes them, and `CK_Orders_ShipAddress`, `CK_Orders_Pickup` and §4.1's G-18
   guard all name `DeliveryMethodCode` unprefixed, so it has to be exactly that.
4. **Complex types, not owned entities**, for `ShipAddress` and `Delivery`. Columns land on `sales.Orders`
   with no second row identity, which is what "complex, required" asks for.
5. **`DeliveryZone` lives in `SpencerDenim.Domain.Sales`** for now. Doc 08 says the zone CK is shared with
   `ref.Districts.DeliveryZone`; when GLB-06 builds that table the enum should move to a `Ref` namespace —
   a rename, not a redefinition.
6. **Exactly one cascade added**: `DeliveryMethodZoneRates → DeliveryMethods`, which is the last entry on
   §1.6's allow-list. `Orders → OrderLines` is explicitly `NO ACTION`; EF makes a required relationship
   cascade by default, and §1.6 puts both tables on the never-deleted list. There is a test for each
   direction.
7. **`[A]` and `[RV]` read strictly from §3.5's markers.** `[RV]` = Orders, Payments, PaymentProviders,
   DeliveryMethods, DeliveryMethodZoneRates. `[A]` = Orders, PaymentProviders, DeliveryMethods,
   DeliveryMethodZoneRates, PickupLocations, Couriers. `Payments` is `[RV]` but **not** `[A]`, so it has no
   `…ByUserId` audit pair; `Payments.ApprovedByUserId` and `Refunds.CreatedByUserId` are business facts and
   are modelled as plain columns with no FK (§1.5's rule for user columns). Both markers are asserted from
   the database catalogue in either direction.
8. **`NumberSeries` has no rowversion on purpose.** §3.5 allocates with
   `UPDATE … SET NextValue = NextValue + 1 OUTPUT deleted.NextValue`; a concurrency token would invite the
   read-then-write that form exists to avoid.

## Check constraints I added that doc 08 does **not** name — please sanity-check

All of them are "this value has no meaning below zero / below one" guards in the same spirit as the ones doc
08 does state. None of them narrows a rule doc 08 states, but they are mine, not doc 08's:

- `CK_NumberSeries_NextValue` — `NextValue >= 1`.
- `CK_DeliveryMethodZoneRates_FreeAboveAmount` — `NULL OR >= 0` (doc 08 constrains `Fee` only).
- `CK_OrderLines_RefundedQuantity` — doc 08 gives `<= Quantity`; I also added `>= 0`.
- `CK_Payments_RefundedAmount` — `>= 0`. I deliberately did **not** add an upper bound against `Amount`:
  doc 08 states none, and an FX-rounded PayPal refund could land a cent over the LKR figure, which must not
  fail the transaction.
- `CK_PaymentEvents_AttemptCount` — `>= 0`.
- `CK_Refunds_ProviderAmount` — `NULL OR > 0`, mirroring doc 08's `Amount > 0`.

If any of these is wrong, it is cheaper to drop it now than after step 3 is written against it.

## Things in doc 08 I think are ambiguous or wrong

1. **§3.8's redaction list includes `Payments.ProofAssetId` ("logged as `[changed]`"), but §3.5 does not mark
   `Payments` as `[A]`.** The audit interceptor stamps and (later) logs `IAuditable` entities, so as written,
   `Payments` is never audited and that redaction rule can never fire. Either `Payments` should be `[A]`, or
   the row-level changes that need auditing are written through the order (which is `[A]`), or the entry is
   left over from an earlier revision. **I followed §3.5's markers and did not make `Payments` audited.**
   Owner's call (doc 08 is yours, not ours).
2. **`UX_Payments_Provider_Reference` / `_Txn` have no column list** — see decision 2 above.
3. **Nothing in the schema ties `Refunds.PaymentId` to `Refunds.OrderId`.** A refund row can name a payment
   that belongs to a different order. Doc 08 does not ask for a constraint and SQL Server cannot express it
   without a composite key or a trigger, so it is an application invariant for step 3 — worth stating
   somewhere, because it is the kind of thing a bad join writes silently.
4. **`PickupLocations.DistrictId` vs `Orders.DeliveryDistrictId` for a PICKUP order.** R7 says a pickup order
   uses the pickup location's district, but nothing in the schema enforces that the snapshot matches the
   location. Again an application rule for the placement use case.
5. **`IX_Orders_StockReserved (Id) WHERE StockState = 0`** is an index whose only key is the clustered key. It
   works and it is small, but it is an unusual shape; I built it exactly as doc 08 writes it rather than
   substituting my own judgement. Worth a second look when the reconciliation job is written.
6. Doc 11 P7 and doc 08 §3.5 (N7) **agree** on bank-transfer resubmission (update the open Pending row;
   a new row only after a rejection). I checked specifically because that is the sort of thing that drifts.
   No contradiction found.

## Tester round 1: PASS, and the one Minor I fixed before the PR

An independent tester reviewed this step and **passed** it: no Majors, every claim in this entry verified
against a real database, and both of my own verification claims reproduced by them independently. Four Minors.

**Fixed: the index test only proved the filter.** `The_index_doc_08_names_exists_with_its_filter` compared
`filter_definition` and nothing else, so an index that existed but had lost its uniqueness, or was keyed on the
wrong column, or had dropped its `INCLUDE` list, still passed. That matters more here than it would anywhere
else, because **this task's own defect was a silently-wrong index** — two `HasIndex` calls over the same property
collapsing into one and deleting `UX_Payments_OneSettlement` while the build stayed clean. A guard that cannot
see the thing that already went wrong once is not a guard.

It is now `The_index_doc_08_names_exists_with_its_shape`, comparing `is_unique | key columns in order with
direction | included columns | filter` for all 31 indexes doc 08 §3.5 names.

**Each of the 31 expectations was read from doc 08 first and only then checked against `sys.indexes`**, which is
the order that matters: had I copied the shapes out of the database, the test would assert that the schema is
what it is rather than what the document says. Doing it that way found two of my own guesses to be wrong and the
schema to be right — `IX_Orders_Paid` is `(PaidAtUtc)` with no `DESC`, and `IX_OrderStatusHistory_Order_Occurred`
is `(OrderId, OccurredAtUtc)` with no `DESC` and no `INCLUDE`, exactly as §3.5 and the history table's `IX`
line specify. All 31 now agree with doc 08.

**Proven non-vacuous, and specifically against the failure mode the old test missed.** Setting
`unique: false` on `UX_Payments_OneSettlement` **in the migration only** (so the model and snapshot still agree
and the pending-model-changes guard stays quiet) fails the new test with
`Expected: "1|OrderId||([IsOrderSettlement]=(1))" / Actual: "0|OrderId||…"`. The filter is byte-identical in both,
so the old test passed that mutation — an order could have been settled twice. Migration restored and confirmed
byte-identical to the commit.

Worth noting for anyone doing this again: mutating the *configuration* instead proves nothing about this test,
because the project's `PendingModelChangesWarning` guard fails every integration test first. That guard is a good
thing, but it meant the only honest way to test the shape assertion was to desynchronise the database from the
model deliberately.
