### 2. How it reaches a database — the #235 mechanism, extended without changing its rules
`HomeContentSeeder.SeedPolicyPagesAsync` offers the policy copy **once per `Seed.PolicyPagesVersion`**, fills and **publishes** a page only while its body is **empty or exactly an earlier seed**, and never overwrites anything else. Three changes, all in `PolicyPageContent` and `HomeContentSeeder`:

1. **`SeedVersion` 1 → 2.** A database that recorded version 1 (UAT, anything that ran #235) is offered the new copy on its next start; a fresh database goes straight to 2. Idempotent: a second start finds the marker at 2 and does nothing.
2. **`IntroducedIn` per page** (Shipping 1, Returns 1, About 2, Privacy 2, Terms 2). The seeder offers a page only if its `IntroducedIn` is **greater than the recorded version**. *Why this exists:* a plain version bump would have re-offered Shipping and Returns as well, and an admin who had emptied or unpublished one of those after v1 would have had it refilled and re-published by a deployment they did not ask for. Tested by `Only_the_five_policy_pages_are_seeded_with_copy_and_each_has_a_version_it_was_introduced_in` and by the integration test `A_database_that_took_version_one_gets_only_the_three_new_pages`, which empties and unpublishes Returns as an admin would, winds the marker back to 1 and checks the upgrade fills only About, Privacy and Terms and leaves Returns alone.
3. **`PreviousSeeds` / `Bodies`** carry five keys. `PreviousSeeds` is what makes a later copy edit safe: a page that still holds exactly an earlier seed may be upgraded, a page the admin touched may not.

**What happens to an admin's choices** (covered by the integration tests in `DeliveryReturnsSeedTests` against real SQL Server unless marked):

| State of the page when the upgrade runs | Result |
|---|---|
| Body empty, any publish flag (the install default: unpublished) | Filled and published. An empty page has nothing to protect; the install default for these three was "unpublished until the client's copy", and this is that copy |
| Body holds the admin's own words | Untouched, published flag untouched (`On_a_database_that_took_version_one_an_admins_words_survive_and_an_empty_page_is_filled`) |
| Body empty because the admin **emptied** it before the upgrade, still unpublished | Indistinguishable from a fresh install: **filled and published**. Avoiding that would need a record of "an admin emptied this", which no column holds. Documented in the seeder |
| Body emptied or unpublished by an admin **after** the marker is at 2 | Left alone for ever: the marker is what remembers the offer was made (`After_the_first_offer_an_admin_who_unpublishes_or_empties_a_new_page_keeps_it_that_way`) |
| Page soft-deleted | Not offered (soft-delete filter) |
| `Contact` | Never receives copy (`SystemPageCopyTests`; its content is the form and the settings) |
| Shipping / Returns, any state | Never re-offered by this change (`IntroducedIn` = 1) |

## Found in review (and fixed before this note)
1. **The first Privacy draft left out things the code does.** `Order.PlacedIpAddress` is stored on every order (`CheckoutEndpoints.cs:186` → `OrderPlacementStore.cs:432`); the checkout takes an optional order note (`checkout-page.ts:861`); a bank-transfer slip is an uploaded file kept with the payment; and a customer lockout writes an audit row with the IP address and browser (`CustomerAuthUseCases.cs:153-160`). All four are now in the Privacy policy. A privacy policy that omits what is collected is the one error that page cannot afford.
2. **`docs/08` §B2 (line 2019) says the policy must state that deleted bank-slip files remain in backups for up to 35 days.** Now stated for deleted data in general and pinned by a test.
3. **PayPal receives the recipient's name as well as the address** (`PayPalHttpGateway.cs:339-351`); the first draft said address only.
4. **The product page does not show only what is in stock.** It shows every colour and size and marks the sold-out ones (`product-page.ts:225, 246`), and the size guide exists only where the admin wrote one (`product-page.ts:256`). The first About draft said "the colours and sizes that are in stock, a size guide"; now corrected, and the Terms say "where there is one".
5. **A plain version bump would have republished emptied Shipping/Returns pages** (see 2 above).
