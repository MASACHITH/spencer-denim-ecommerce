## The design decision worth reading, because it goes against the brief I was given

The brief told me to copy W2-09's answer for the bag: a server-side wishlist identified by a cookie
token, with `CustomerUserId` nullable behind a filtered unique index, so that the merge-on-login seam
is ready. **I did not do that, and here is why.**

1. **The scope baseline says the opposite, verbatim.** `docs/02` WISH-01: "Guests keep it in the
   browser; it merges into the account on login." Doc 08 §1.7 lists the guest wishlist under
   "Client-side only (**no tables**)". Doc 08 §3.5 gives `WishlistItems.CustomerUserId` as **NOT NULL**.
   Doc 11 §538/§553/§1263 say it three more times, and §1263 specifically merges "the **browser**
   wishlist into the account wishlist". Four documents, one answer.
2. **Nullable-without-a-token is meaningless, and nullable-with-a-token is new schema.** A row with a
   NULL owner and no token belongs to nobody — nothing can find it again. Doc 08 §3.5 has no `Token`
   column on this table, so the brief's shape is only reachable by inventing one, which changes what
   W3-01's merge has to be.
3. **A cookie buys a guest nothing here.** A cookie is browser state too: it dies with a private
   window and goes when site data is cleared, exactly as `localStorage` does. What server-side storage
   buys the *bag* is the four things doc 08 §3.5 enumerates — SSR of the count, one place for price and
   stock validation, a single-operation merge, cross-device — and only the last applies to a wishlist,
   and only once there are accounts.
4. **It would have put a write on an anonymous page view.** The cart row is created on the first Add to
   Bag, never on a page view (§3.5). A cookie wishlist creates a row on the first heart tap, from
   unauthenticated traffic, with no rate limit.

So: the guest wishlist stays in the browser, `sales.WishlistItems` is created exactly as doc 08 §3.5
specifies, and **W3-01 owns the merge** — it signs the customer in, reads the list the storefront posts
to it, and inserts the rows that are missing with §3.5's `WHERE NOT EXISTS`. The seam is documented on
`WishlistItem`, on the `DbSet`, on the migration and in `WishlistSchemaTests`.

**What this means for the half of WISH-01 that is not built.** "It merges into the account on login"
cannot be built or tested: there is no `CustomerUserId` for a row to carry, and no login to merge at.
Everything else in the line is built. Nothing in the application inserts into `sales.WishlistItems`
yet; the table exists because §3.5 specifies it, because two places in the repository said it was
W2-08's, and because the merge needs a target with the right shape before the task that writes it.

## Decisions

- **The browser keeps keys, the shop keeps prices.** `localStorage` holds the slug, the product's name
  and the optional colourway; everything a card draws is read live from `/api/wishlist` every time the
  page is opened. `RecentlyViewed` (PDP-07) stores whole cards and its own `TODO(W2-07)` says it should
  stop — a wishlist is a list a shopper comes back to in a week, so a stored price is a wrong price.
  The name is kept only so a withdrawn item can be *named and removed* when there is no card to send.
- **An absent field on a save says nothing about it; an explicit `null` clears it.** This is W1-12's
  defect in the shape it would take here: the bag's "move to wishlist" records a colourway, a listing
  card's heart knows the name and nothing about a colour, and `??` cannot tell "no colour" from "I was
  not asked about the colour". The fixture that proves it has real data in the field the second save is
  silent about.
- **Move to bag opens Quick View**, because a saved entry names a product and a bag line needs a
  variant (`ProductCardDto` carries colours and no sizes at all). The entry leaves the wishlist on
  `QuickView.added` and on nothing else. `CartStore.lastAdded` could not serve: it is a root signal
  that moves for an add made anywhere on the page, so a wishlist watching it would delete the wrong row.
- **Over the API's 200-slug cap the request is truncated and the page says so.** A 400 would make a
  shopper's own list unviewable with nothing they could do about it, and trimming their stored entries
  to fit would be destroying saved items to make a request smaller.
- **The page gates on having looked, not on the list being empty.** `WishlistPage.localTaken` flips in
  `afterNextRender`; until then the page says "Loading your wishlist", never "Your wishlist is empty".
  The `afterNextRender` is guarded by `isPlatformBrowser` as well — not a fix, since Angular skips it on
  the server anyway, but it makes "the server never takes the list up" a property of the file and
  therefore testable.
- **No `[disabled]` anywhere on the page.** Nothing needs one (every action is synchronous), and a spec
  asserts that none arrives — a `disabled` attribute on the focused button throws focus to `<body>`,
  which this project has shipped three times.
- **#111: swap the heart with the badge.** The float keeps its corner; the only thing left in its column
  is a label nobody taps. The four alternatives `docs/04` already rejected were all still worse, and a
  fifth — insetting the heart from the right edge by one tap target — leaves about four pixels of
  overlap at 320 px, which is a collision that is merely harder to measure.

## Round 2: the tester's three Majors and three minors

The verdict was FAIL with 3 Majors. All six findings are fixed; no new migration was needed.

**MAJOR 1 — focus.** Every removal destroys the control that was pressed, which throws focus to
`<body>` exactly as `[disabled]` does. Round 1 kept the attribute off this page, has a spec asserting
it stays off, and then produced the same harm by node destruction on all three removal controls — so a
keyboard shopper clearing a wishlist lost their place on every single item. **The lesson worth keeping:
banning the attribute was necessary and not sufficient**, and the next person to quote that rule should
read it as "do not destroy the focused control either". `WishlistStore.lastRemoval` now reports what
went and where it was; the page moves focus to the successor row's Remove, or to Start shopping when
the list empties. It refuses to take focus that was not already on the page, and a refused write moves
nothing. Browser tests drive it from the keyboard.

**Round 2 got the move-to-bag case wrong**, and said so confidently: "the page's handler runs after the
render that removed it, so it wins". The drawer wins, not the page — see round 3 below.

**MAJOR 2 — the product page's heart.** It sent a bare slug while the listing card sent
`{ slug, name }`, so the one surface that definitely knows the colourway recorded the least of the two,
and two withdrawn entries both read "This item … no longer available" with two identically labelled
Remove buttons. It now sends the name and the selected colourway. **This was not the absent-field rule
being bent**: that rule is for a caller which does not know (a listing card has colour dots and no
selection, so it omits the field), and this caller knows.

**MAJOR 3 — the 414.** `GET /api/wishlist?slug=…` could not carry a full wishlist. Kestrel's default
request line is 8,192 bytes, nothing in the API raises it, and 200 slugs exceed it at about 32
characters each — `womens-high-rise-straight-leg-jeans-indigo` is 42 — so a shopper's own page answered
414 behind a Try again button that failed identically forever. The endpoint's justification was wrong
by a factor of 5.6 and had never been measured, which is the worst kind of comment: it stopped the next
reader checking. The slugs now travel in a **POST body** at `/api/wishlist/products`. A body also keeps
a shopper's whole wishlist out of the access log of every hop it passes, which was an argument for it
all along and was missed first time.

**And the test that was meant to guard it could not fail on it.** `A_list_over_the_cap_is_truncated…`
used short slugs *and* ran on `WebApplicationFactory`'s in-memory `TestServer`, which has no request
line to overflow — the W1-12 shape again, a fixture that cannot express the defect. `KestrelApiHost`
is the cure: a real Kestrel on a kernel-chosen loopback port, serving the application's own endpoint
mapping with a stub handler. `WishlistTransportTests` sends the old shape and gets 414, **finds the
break-even slug length by asking the server** rather than computing it, sends the new shape and gets
200, holds that the request line no longer grows with the wishlist, and includes two guards on itself:
a source scan proving the API raises no Kestrel limit (so the bare host's defaults are the deployed
ones), and the counter-proof that the in-memory server does not enforce a request line at all. The
suite touches **no database**, so it runs anywhere and cannot disturb the shared one.

`WebApplicationFactory` with Kestrel swapped in was tried first and does not work: it casts the
resolved `IServer` to `TestServer` the moment anything touches `Services`, so replacing the server is
an `InvalidCastException` rather than a configuration choice. That is written on `KestrelApiHost` so
the next person does not spend the same half hour.

**m1** — `rows()` mapped every saved entry while `load()` asked about the first 200, so an entry past
the cap rendered as a row stuck on "Loading…" indefinitely: 201 saved drew 201 rows under a note saying
200 are shown. `rows()` is sliced at the cap; the count and the note still read the whole list, because
nothing is deleted.

**m2** — the version-1 read did not de-duplicate while the version-2 branch did, so a repeated slug
became two rows for one product and the first Remove press destroyed both. Two lines. The test that
goes with it asserts the **delta** rather than the end state: `without()` filters every match, so the
list after the press is the same either way, and the first version of that test passed over the defect.

**m3** — the card's heart wrote the stored list directly, so a row vanishing from the wishlist page
announced nothing while the same row's Remove button announced a full sentence. The heart goes through
`WishlistStore` now, which is also what lets the page re-home focus for it. **Round 2 then claimed
"every heart in the storefront" had moved, which was false — the product page had not.** Round 3 moved
it; see below.

**Also corrected:** `GetWishlistQuery`'s case-sensitivity reasoning (it claimed only one spelling could
match, when the database collation is `Latin1_General_100_CI_AS_SC` and `ProductCatalogReader` handles
the case-insensitive match deliberately); this journal's claim that two mutations broke the same test;
the test counts above; and `docs/04` §4's understatement of the badge's exposure, now carrying the
tester's measured 6 of 99 and 7 of 113 — slightly *more* often than the heart used to, because a badge
is wider.

**The badge trade, and what is with the owner.** A **Sale** product is flagged three other ways outside
the float's column, so hiding the Sale flash hides no sale. **New**, **Best seller**, **Online
exclusive** and **Low stock** have no second signal and can be briefly invisible as a card passes the
float. That residue is the owner's call and is recorded in `docs/04` §4; nothing is designed around it.

**Round-2 mutations, 14 more:** no focus re-homing at all; focus moved when it was elsewhere; focus
always sent to Start shopping; the card heart announcing nothing; `rows()` unsliced; the version-1
branch not de-duplicating (both of its tests now catch it); the product page heart back to a bare slug;
the slugs back in the query string (24 specs fail); a body limit below a full wishlist; a shorter
maximum slug length; and the four browser ones — no focus re-homing (3 of 4 tests), unsliced rows, a
wishlist control positioned in the float's corner, and the slugs back in the URL.

## Round 3: the last of MAJOR 1, and the bound the POST took away

**MAJOR 1, the move-to-bag path.** Round 2's reasoning was wrong and its test could not fail. Both are
worth writing down, because the second is the failure mode this branch keeps catching in other people's
work.

*What actually happens.* Moving a row to the bag destroys that row's Move to bag button. Quick View
closes and declines to restore focus to it (correctly — it is detached), so focus is on `<body>`. The
mini bag then opens, records `document.activeElement` as its return target — **`<body>`, which is
connected** — and on dismissal "restores" it: `body.focus()` changes nothing, and the drawer reports a
success it did not achieve. The page's own handler cannot help; by the time it runs focus is inside the
drawer, so its "do not steal focus" guard correctly declines, and nothing re-runs when the drawer later
closes.

*Two things were tried and measured before the fix.* A synchronous `=== body` check on the `closed`
output: declines, because focus is still in the drawer. The same check deferred to the `read` render
phase, on the theory that it runs after the drawer's `mixedReadWrite`: also too early — a probe read
`active=BUTTON`, the drawer's own close button. Angular's phase order was not the deciding factor, so
the ordering argument was abandoned rather than tuned.

*The fix, in two parts, both in the shared drawer where the knowledge is.* `sd-drawer` no longer records
`<body>` as a return target — that is the absence of one, and treating it as one is what made the whole
path invisible — and when it has nothing to return focus to it raises a new **`focusLost`** output. The
mini bag relays it and `SiteHeader.recoverBagFocus` puts focus on the bag anchor. The host decides,
because only a host knows where focus should go; a drawer that picked for itself would be wrong on some
page. The anchor rather than the row the shopper was on: only the page knows that, and the page has no
view of the drawer's lifecycle.

*The test.* Round 2's asserted `activeElement !== body` **immediately after the add**, while the mini
bag held focus — so it passed with the entire fix removed, and its name said "in the list" when focus
was in a drawer. It now dismisses the drawer first and asserts the control focus lands on, and a second
test holds the other half: a **surviving** opener is still restored to, so the recovery is a net and not
a takeover. Four mutations prove them: no host recovery, no `focusLost`, `<body>` recorded again, and
the drawer recovering unconditionally.

**The minor: the POST removed the only bound on input size.** The old `GET` was refused at 8,192 bytes
by the transport before anything was allocated; a `POST` is accepted to Kestrel's 30 MB default and
`System.Text.Json` materialises the whole array before `MaxSlugs` trims it — 20.68 MB and 2,192 ms for
200,000 slugs, as the tester measured. The catalogue was never at risk, because the cap holds the
database work at 200 either way; what had nothing in front of it was parse-and-allocate. **A fix for an
input that was too large should not remove the only bound on input size**, which is the part worth
recording rather than the line of code. `WishlistEndpoints.MaxBodyBytes` is 64 KiB — about 40% over a
full wishlist and 480 times tighter than the default — applied per endpoint rather than server-wide,
because lowering Kestrel's ceiling would silently cap media uploads (ADM-14).

Two of the transport tests had to be re-shaped once that limit existed, which is its own small lesson:
the "handler trims an over-cap body" test was sending worst-case slugs and started getting 413, quietly
becoming a second copy of the body-limit test; and the body-limit test sent 20,000 slugs, which the
server stops reading part way through, so whether the client sees the 413 or the connection reset was a
race — it failed in the suite and passed alone. It now sends just over the limit, where the declared
`Content-Length` is refused before the body is read and the answer is deterministic.

**The four corrections.** The product page's heart now goes through `WishlistStore` too, so "every heart
in the storefront" is true rather than nearly true. It still raises no live-region sentence, and that is
deliberate: the heart there is a persistent toggle whose `aria-pressed` and accessible name both change,
which a screen reader reads on the press — a sentence would say it twice. What it gains is the single
code path, the shared refusal wording, and a correct `lastChange` for whoever reads it. `WISHLIST_URL_BYTES`
is deleted: it was a constant whose docstring asserted a test that did not exist, which is exactly the
shape this branch keeps catching. The stub's stale "the slugs arrive on the query string" is fixed. And
the `AuditLogEndpointTests` attribution is corrected above.

**`AuditLogEndpointTests` -> "can list entries sorted newest first" is a real intermittent and it is
not W2-08's.** Round 2 implied that making the transport suite database-free had dealt with it; it had
not, and the attribution was wrong. The tester reproduced it afterwards: `Assert.Equal() Failure:
Expected: 3, Actual: 1`, on 986/1 in a first full run and 987/0 in a second, with 8/8 three times in
isolation. Making the transport suite database-free was right for its own sake and is unrelated. It is
**#114**, and the captured assertion is the useful part - the reader saw one entry where three were
expected, which is a visibility or ordering race between test classes rather than a wrong `ORDER BY`.

**`--repeat-each` generalises further than I said.** The tester reproduced it with `bag.e2e.ts` and
`search.e2e.ts` together — 2 failed / 4 passed on default workers, 6 passed with `--workers=1`, same
bundle. Six distinct victims across seven full runs between us. #115, and neither of us should spend
more on it.

  customers (`UserType = 1`), one per call with a unique address.
- `MEMORY.md` and `TASKS.md` deliberately untouched, per doc 14.

## Not done, and knowingly left

- **The merge on login.** W3-01's. See above.
- **A wishlist of more than 200 items** shows the 200 most recently saved, with a note. Nothing is
  deleted. Paging the request would be the fix if a real shopper ever reaches it.
- **The bag page's own `[disabled]` buttons.** `bag-page.ts` puts `[disabled]` on Remove and "Move to
  wishlist" while a line is in flight, which is the same focus-to-`<body>` defect as #109 one row up.
  Not touched: it is W2-09's page and out of this task's scope, and fixing it means rewriting that
  page's busy-state tests. Worth an issue.
- **Two controls remove an item** on the wishlist page: the card's own heart (which reads "Remove … from
  wishlist" when saved) and the row's Remove button. Deliberate — the heart is the control a shopper
  used to get here — and both are fully labelled, so a screen reader reads two distinct controls. As of
  round 2 both also announce and both re-home focus, so the asymmetry the tester found is gone. A
  reviewer may still think it is one control too many.
- **The shell already carries five live regions** before this page adds its own (announcement bar,
  header search, mini bag twice, footer newsletter). `mini-bag.spec.ts` noticed the same thing on
  `/bag`. Nothing here makes it worse, and the page's own region now has a test id so a test can
  address it, but "how many polite live regions should one document have" is a question for whoever
  looks at GLB-04 next.
