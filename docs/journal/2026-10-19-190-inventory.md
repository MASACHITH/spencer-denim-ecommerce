## Semantics chosen (and why)

- **Adjust/Receive by delta**: `SET OnHand = OnHand + @d WHERE OnHand + @d >= Reserved AND OnHand + @d <= 1,000,000` (bigint arithmetic). A delta commutes, so two people adjusting at once never lose an update; no figure from the screen is needed.
- **Set count (stock-take) is absolute and conditional**: `SET OnHand = @new WHERE OnHand = @expected AND @new >= Reserved` (doc 08 §5.8). If on hand moved since the screen loaded, the answer is **Changed** with the current figure; the screen updates the row and the staff member re-confirms.
- **Reserved floor**: no manual change may leave on hand below reserved, i.e. available never below 0 and no unit held by an unpaid order is taken away. Enforced only inside the UPDATE's predicate under the row lock (never read-then-write); `CK_StockLevels_ReservedLeOnHand` is the backstop. The refusal says "N units are reserved for unpaid orders".
- **Bulk = validation all-or-nothing, application per row, one transaction.** A malformed request (missing key, bad quantity, no reason, duplicate variant, >500 rows) is a 400 naming every bad field and applies nothing. A well-formed one applies each row in VariantId order (doc 08 §5.3 lock order) and answers each row Applied / Refused / Changed / NotFound, in the order sent; refused rows change nothing, the rest commit. Justification: doc 08 §5.8 and doc 11 P2 step 7 specify per-row results with applied rows staying applied, and an order placed a minute ago is no reason to refuse the delivery on the next line. Multi-row requests share one `BatchId`.
- **Reason required for every manual change** (doc 08 requires it for Adjust/CountCorrection; the brief for all), trimmed, ≤250.
- **Limits**: receive 1–100,000; adjust ±1–100,000; count 0–1,000,000; threshold 0–10,000 or null.
- **Audit**: every applied stock change writes one `ops.AuditLogs` row (`Update`, `StockLevel`, before/after on hand, movement type, reason, batch); a threshold change writes one with before/after threshold (read from the UPDATE's OUTPUT); an unchanged threshold writes none. Threshold changes are audit-only — the ledger records stock, and doc 08's movement types have no threshold type.
- **A variant with movements can no longer be hard-deleted** (ledger is never deleted, FK is NO ACTION). `VariantReferences` declares it BlocksTheDelete and the product save's guard reports it as "stock recorded against it" and asks to switch it off.

## Decisions for the owner (safe choice taken)

1. **The inventory report stays on `Reports.View`; it was not widened to accept `Inventory.View`.** Doc 11 P16 (line 1695) says Order Staff see the dashboard and not Reports; the stock they need is now on this screen. If you want Order Staff in the report too, it is one `AnyPermissionRequirement` policy.
2. **No CSV upload/download for the bulk update.** Doc 11 P2 part B calls the CSV layout "a proposed default, not yet in doc 08 (§7 G-04)". Bulk update here is select-rows-and-apply. CSV can be added on the same endpoint.
3. **No `Initial` movement type is written.** Seeded and new variants start with a stock row and no movement; the first manual entry is Receive/AdjustIn/CountCorrection. Writing "Initial" reliably needs a rule for seeded stock.
4. **Orders placed before this branch merges have no movements** (#108's hole stays for that window); from merge on, every order stock change writes one.
5. **Inactive variants are not on the list** (same scope as the inventory report). Their history and threshold are reachable by id through the API; a stock change to one still works by API. If staff need to zero stock on switched-off sizes from the screen, add an "include switched off" filter.
6. Bulk threshold editing is not built (threshold is per variant).
